## 제가 판단한 것

- **축약의 기준은 기능 수가 아니라 발표 흐름이었습니다.** 10분 안에 문제·해결 방식·검증 결과·한계를 이해할 수 있도록, 같은 내용을 반복하는 설명과 구현 세부사항은 줄이고 사용자 흐름과 검증 근거는 남겼습니다.
- **측정하지 않은 결과는 비워 두거나 좋게 해석하지 않았습니다.** 정확한 발음 비교처럼 기록이 없는 항목은 표에서 삭제하지 않고 `측정 기록 없음`으로 표시했습니다. 비교 범위와 한계를 함께 보여 주는 편이 발표의 신뢰성을 높인다고 판단했습니다.
- **식당 문장은 실제 매장 정보나 안전을 단정하지 않도록 설계했습니다.** 가격·영업시간·메뉴를 사실처럼 만들지 않고, 알레르기는 직원·주방에 확인하도록 표현했습니다. 카드번호·여권 같은 민감 정보 요청, 공격적이거나 무례한 표현도 생성 기준에서 제외했습니다.
- **발표 용어는 평가에 필요한 개념만 남겼습니다.** 멀티모달, STT, VAD, Long-term Memory처럼 과제 요건과 직접 연결되는 말은 처음 한 번 풀이하고, 제품명과 코드 이름은 질문 대응용 부록으로 옮겼습니다.

## 어려웠던 것

- 실제 사용자 테스트의 수치와 화면 문구가 어긋나지 않도록 설문 14명, 교통 9명, 식당 5명, 앱 사용 8명 기준의 4.6→3.9를 슬라이드별로 다시 확인해야 했습니다.
- 구현 가능한 범위와 발표에서 말할 수 있는 범위를 구분하는 일이 어려웠습니다. 특히 정확한 발음 비교, 일부 도시의 장소 결과 공백, 녹음 자동 종료처럼 검증하지 못했거나 미구현인 항목은 기능처럼 보이지 않게 한계로 남겼습니다.
- 서비스 화면과 발표 자료를 함께 고치면서도 10분 분량을 넘지 않도록, 화면 설명은 짧게 두고 근거와 변경 이유는 협업 기록·부록으로 분리했습니다.

## 문서화 원칙

이 문서는 이영애가 맡은 식당·카페 AI 기획과 발표 자료 정리 과정에서의 판단을 기록한다. 구현 코드의 세부 이름보다, 어떤 사용자 문제를 줄이려 했는지와 검증하지 않은 내용을 어떻게 표시했는지에 초점을 둔다.
