# 배포 런북 (Deployment Runbook)

여행영어 AI 서비스 — Render + FastAPI + Gemini

> **이 문서의 목적은 "장애를 없애는 것"이 아니라 "장애가 났을 때 3분 안에 판단하고 되돌리는 것"입니다.**
> 배포 직후 `/health` 게이트를 통과하지 못하면 **거기서 멈춥니다.** 다음 단계로 넘어가지 않습니다.

---

## 0. 원칙 (읽고 시작)

1. **롤백은 3계층입니다.** ① 배포 롤백(Render) → ② 코드 롤백(git) → ③ **무배포 완화(환경변수)**.
   구현자가 1명인 팀에서는 ③이 가장 빠르고 안전한 경우가 많습니다. 배포 없이 스위치만 바꿉니다.
2. **"동작하는 척"과 "동작"을 구분합니다.** 목업은 `usable: "sample"`로 표시됩니다.
   목업으로 돌면서 "AI가 동작한다"고 말하면 그 순간 프로젝트가 무너집니다. **차라리 시연을 줄이세요.**
3. **프론트 연동 코드는 구현돼 있고(`mockup/ai.js`), 없는 것은 실환경 검증입니다.** 현재 상태는 **"연동 구현 완료, 실환경 검증 대기"**. 배포 URL 확보 → 실제 생성·말하기 1회 → score 빈도 측정(`backend/scripts/measure_score_rate.py`) 순서로 검증합니다.
4. 모든 조치는 **기록**합니다 (9장 양식). 같은 장애가 두 번 나면 문서가 틀린 것입니다.

## 2. 정상 배포 절차

```bash
# 0) 로컬 상태 확인 — 확인만 한다. 지우거나 되돌리는 명령을 습관으로 치지 않는다.
cd codyssey_final
git status --short            # 깨끗하면 여기서 끝
git diff --stat               # 의도하지 않은 변경이 있는지 본다
git clean -n -d               # (필요할 때만) 추적 안 되는 파일 목록 — dry-run, 지우지 않음
```

> 미커밋 변경이나 추적되지 않는 파일(`.venv/` 등)이 있으면 **내용을 확인한 뒤 파일 단위로** 처리하세요.
> `git checkout -- .` / `git clean -fd` 를 한 번에 실행하지 마세요 (8장과 같은 이유로 작업이 사라집니다).

1. **머지 선행 (필수)** — **Render가 연결한 저장소의** `main`에 배포 설정이 있어야 Blueprint가 동작합니다.
   병목은 권한이 아니라 **머지**일 수 있습니다(PR #1 장기 미머지). 요청은 "collaborator 추가 + PR 머지"를 함께 하세요.
   - `feat/memory-and-speak` → `main`
   - `New-add-backend` → `main`
   - 머지 후 확인: `git ls-tree -r --name-only main | grep -E 'backend/|render.yaml'`
2. Render → **New → Blueprint** → 저장소 선택 (`render.yaml` 자동 인식)
3. 빌드/기동 로그에 오류 없음 확인
4. **3장 게이트** 통과 → 그때만 프론트 연동으로 진행

## 4. 장애 시나리오별 대응

각 항목: **증상 → 확인 → 즉시 조치 → 롤백 → 재발 방지**

### F01. Blueprint가 `render.yaml`을 못 찾음 (배포 자체가 안 됨)

- **증상**: Render New → Blueprint에서 `render.yaml not found`, 또는 서비스가 생성되지 않음
- **원인**: `render.yaml`이 **배포 브랜치(main)**에 없음. 백엔드 브랜치에만 있는 상태
- **확인**
  ```bash
  git ls-tree -r --name-only origin/main | grep render.yaml || echo "main에 없음"
  ```
- **즉시 조치**: 머지 PR을 만든다. (`New-add-backend` → `main`)
- **롤백**: 해당 없음 (배포 전 실패)
- **재발 방지**: 머지 전 `main` 기준으로 위 명령을 습관화. `render.yaml`은 **저장소 루트**에 둔다
- **주의**: Blueprint는 저장소의 **기본 브랜치**에서 `render.yaml`을 찾습니다. 임시로 브랜치를 바꾸려면
  `render.yaml`에 `branch:`를 명시하는 방법도 있지만, **팀원이 10/8에 `main` 기준으로 PR을 올리므로 main 머지가 정답**입니다

### F02. 배포는 됐는데 `/generate`가 전부 404 (`categories: []`)

- **증상**: `/health`의 `categories`가 빈 배열. `/generate`가 404 (`unknown category`)
- **현재 코드**: `main.py` 는 이미 저장소 루트의 `agent_contract/` 를 기본값으로 봅니다
  (`CONTRACT_DIR = REPO_ROOT / "agent_contract"`). 코드 수정이 필요한 경우는 거의 없습니다.
- **확인 (이 순서로)**
  1. `/health` 의 `contract_dir` 이 `.../agent_contract` 를 가리키는가
  2. Render **Environment** 에 `CONTRACT_DIR` 이 잘못 들어 있지 않은가 (있으면 그 값이 코드 기본값을 덮어씀)
  3. 배포된 브랜치(`main`)에 `agent_contract/categories/restaurant.json` 이 실제로 있는가
     ```bash
     git ls-tree -r --name-only origin/main | grep agent_contract
     ```
  4. `render.yaml` 의 `startCommand` 가 `cd backend && uvicorn ...` 이고 `rootDir` 를 쓰지 않는가
     (`rootDir: backend` 를 쓰면 루트의 `agent_contract/` 가 배포에 포함되지 않을 수 있음)
- **즉시 조치**: 원인에 맞게 하나만 고친다 — 잘못된 `CONTRACT_DIR` 삭제 / 누락 파일 머지 / `rootDir` 제거
- **롤백**: 직전 정상 배포로 되돌리기(5장 A). 첫 배포에서 나면 되돌릴 대상이 없을 수 있음
- **재발 방지**: `/health` 게이트에 `categories` 확인을 **필수 항목으로 고정** (3장)

### F03. 검증이 꺼진 채 "정상"으로 보임 (가장 위험)

- **증상**: 서버는 응답하지만 `status: "degraded"`, `config_problems`에 항목 존재,
  또는 `schema_checker: false`
- **원인**: `agent_contract/schema.json` 누락 / `jsonschema` 미설치 / `categories/*.json` 없음
- **왜 위험한가**: **검증 없이 돌면 "검증했다"고 말할 수 없습니다.** 품질 문제가 아니라 신뢰 문제입니다
- **확인**
  ```bash
  curl -s https://<앱>.onrender.com/health | python3 -c "import sys,json;d=json.load(sys.stdin);print(d['status'],d['config_problems'],d['schema_checker'])"
  ```
- **즉시 조치**
  1. `requirements.txt`에 `jsonschema`가 있는지 확인 → 없으면 추가 후 재배포
  2. `schema.json`이 `main`에 있는지 확인 → 없으면 머지
  3. 재배포 후 `status: "ok"` 확인
- **엄격 모드**: 발표 전에는 `CONFIG_STRICT=1`로 두어 설정 누락 시 `/generate`가 **503**으로 거부하게 한다
  (조용히 잘못된 결과를 내보내는 것보다 낫습니다)
- **롤백**: 설정 문제는 롤백 대상이 아님. **고쳐서 재배포**
- **재발 방지**: `CONFIG_STRICT=1` + `/health` 게이트. 시연 당일에는 `0`으로 완화 가능(6장)

### F04. `has_api_key: false` (목업으로 돌고 있음)

- **증상**: `/generate` 응답이 `mock: true`, `usable: "sample"`. 실제 AI가 아님
- **확인**: `/health`의 `has_api_key`
- **즉시 조치**
  1. Render → Environment → `GEMINI_API_KEY` 등록 (값 붙여넣기 후 저장 → 자동 재시작)
  2. 재시작 후 `/health`에서 `has_api_key: true`
  3. `POST /generate` → `mock: false` 확인
- **롤백**: 해당 없음
- **주의 (중요)**: `/generate`가 `mock: true`인 상태로 시연하면 **"AI가 동작한다"고 말하면 안 됩니다.**
  키가 없으면 **F06과 동일하게 취급**하고(장애), 시연 스크립트를 축소하세요.
- **재발 방지**: 시연 T-30분 점검에 `has_api_key` 포함 (7장)

### F05. Gemini 429 — 할당량·레이트 초과

- **증상**: `/generate`가 `degraded: true`, `attempts: 3`. `issues`는 비었는데 결과가 `sample`.
  또는 응답의 `error`에 `429`, `RESOURCE_EXHAUSTED`, `quota`
- **원인**: 분당 요청 초과 / 무료 할당량 소진 / 동시 테스터 몰림
- **확인**: 서버 로그에서 상태 코드 확인. `/generate` 응답의 `error` 문자열 확인
- **즉시 조치 (순서대로)**
  1. **기다린다** — 분당 제한은 1분이면 풀립니다. 재시도 간격을 늘리고 순차 호출
  2. Google AI Studio에서 현재 할당량 확인
  3. 자체 호출 제한 완화 (우리 서버가 429를 내는 경우): Render → `RATE_LIMIT` 상향 (예: `60`)
     > 우리 서버의 429와 Gemini의 429를 **구분**하세요. 우리 것은 `RATE_LIMIT/60s` 문구가 나옵니다
  4. 카테고리 생성은 **사전 생성 후 저장**으로 전환 (테스트 중 재호출 금지)
- **롤백**: 필요 없음. **할당량은 시간이 지나면 회복**됩니다
- **재발 방지**: 테스트 시간을 나눠서 진행. 결과를 저장해 재호출을 줄임. 할당량 한도를 콘솔에서 확인

### F06. Gemini 503 / 500 — 모델 장애

- **증상**: `/generate`가 `degraded: true` + `usable: "rejected"`. `error`에 `503`, `UNAVAILABLE`, `overloaded`
- **원인**: Google 측 일시 장애 (내 코드 문제가 아님)
- **확인**: [Google Cloud 상태 페이지](https://status.cloud.google.com/) 확인
- **즉시 조치**
  1. **기다린다.** 5~15분 내 회복되는 경우가 많습니다. 우리 재시도(최소 30회, 모델을 돌아가며)는 이미 돌았습니다
  2. 특정 모델로 우선 시도: Render → `GEMINI_MODEL`에 Actions "Gemini 모델 목록"에서 확인한 이름을 넣음 (목록에 있을 때만 맨 앞에 쓰임)
  3. 그래도 안 되면 **시연 축소** — 미리 생성해 둔 결과(스냅샷)로 카드 학습·음성 연습만 시연합니다
     > 이때 화면에 **"실시간 생성은 현재 불가하여 저장된 결과로 시연합니다"**를 명시하세요.
     > 숨기면 더 나쁩니다.
- **롤백**: 배포 롤백은 무의미 (외부 장애). **우회 또는 축소**
- **재발 방지**: **시연 전날 생성 결과를 스냅샷으로 저장**해 둔다. 이게 F06의 실질적 대비책입니다

### F07. 콜드스타트 — 첫 요청이 30~60초

- **증상**: 15분 이상 요청이 없다가 첫 요청이 매우 느림. 브라우저에 로딩 페이지가 보임
- **원인**: Render 무료 플랜은 **15분 무트래픽이면 스핀다운**되고, 다음 요청 시 **약 1분** 걸려 다시 뜹니다
  → [Render Free 플랜 문서](https://render.com/docs/free)
- **확인**: 스톱워치로 첫 요청 시간 측정
- **즉시 조치**
  ```bash
  # 시연 10분 전 예열
  curl -s https://<앱>.onrender.com/health > /dev/null && echo "warmed"
  ```
- **롤백**: 해당 없음
- **재발 방지**: **T-10분 예열을 시연 런북에 고정.**
  프론트는 **90초 타임아웃, 자동 재시도 없음**입니다(코드 기준). 짧은 타임아웃 뒤 재시도는 첫 요청을 끊고
  서버를 다시 깨워 **콜드스타트를 더 길게** 만듭니다. 10초가 넘으면 화면에 "첫 요청은 시간이 걸릴 수 있어요"가 뜹니다.
  실패하면 로컬 템플릿으로 폴백하고, 그 문장에는 "AI 생성" 배지가 붙지 않습니다.
- **주의**: 무료 플랜은 Render가 **언제든 재시작할 수 있고**, 로컬 파일시스템 변경은
  재배포·재시작·스핀다운 시 **소실**됩니다. 우리 설계는 상태를 서버에 두지 않으므로 영향 없음 —
  **서버에 파일을 저장하는 기능을 추가하지 마세요.**

### F08. 빌드 실패

- **증상**: Deploys 페이지에서 빌드가 실패(빨강). 서비스는 **직전 정상 배포를 계속 실행**(무중단)
- **원인 후보**: `requirements.txt` 오타 · 경로 불일치 · 파이썬 버전
- **확인**: 빌드 로그 마지막 30줄
- **즉시 조치**
  1. 로컬에서 동일 명령 재현: `pip install -r backend/requirements.txt` (또는 `python -m py_compile`)

- **참고**: 빌드 명령 타임아웃 120분, 시작 명령 15분. 실패 시 **그 배포 전체가 실패**하고

### F09. 검증 실패 결과가 학습 화면으로 넘어감 (품질 사고)

### F11-a. 알려진 위험 — 재시도 정책 현행 유지 (결정: 2026-10-07)

- **현황(코드 기준)**: Gemini 호출은 **최소 30회** 시도하고 전체 제한 시간이 없으며, 시도당 최대 60초(`AI_CALL_TIMEOUT`)다.
  계속 실패하면 대기만 약 107.5초, 최악은 약 **31분**(30×60 + 107.5초). 화면(`GEN_TIMEOUT_MS`)은 **90초**에 포기하고 로컬 문장으로 폴백한다.
- **위험**: 클라이언트가 끊어도 서버 호출은 멈추지 않는다(`/generate`는 동기 `def`). 도시가 N개면 `/generate`가 **동시에 N개** 나가므로 한 번의 화면 요청이 최대 `N × 30`회의 Gemini 호출이 될 수 있다.
  → 화면 증상은 없고 **할당량(F05)·비용(F11)·인스턴스 시간(F10)** 만 새는 형태다. 로그의 `시도 n/30 실패` 반복으로만 보인다.
- **결정**: 정책은 **현행 유지**. 위험은 이 문서에 기록하고 코드는 바꾸지 않는다.
- **완화 수단(코드 변경 없이)**: Render Environment의 `RATE_LIMIT` 하향(IP당 `/generate` 동시 유입 제한), 필요하면 `GEMINI_API_KEY` 제거로 목업 전환(→ F04 주의), 키 재발급(F11).
  `AI_MIN_ATTEMPTS`는 **올리기만** 할 수 있고 30 미만으로 줄일 수 없다.
- **시연 전 점검**: Gemini 429/503이 계속 나는 상태(F05·F06)에서 화면을 여러 번 열지 않는다. 로그에 `시도 n/30` 이 반복되면 그 요청이 아직 서버에서 돌고 있는 것이다.

### F11. 비용 폭주 / API 키 노출 의심

  2. 사용 API의 **할당량(quota) 한도**를 낮춰 실질 상한 설정

- **재발 방지**: 예산 **알림**(경고용) + **할당량 한도**(실질 상한)를 **둘 다** 설정. 문서에 절차로 남김

### F12. 화면이 서버에 연결되지 않음

- **증상**: 화면이 로딩만 되거나 `Failed to fetch`, 또는 상단에 "외부 서버" 표시
- **기본 구조**: 화면(`mockup/`)과 API 가 **같은 Render 서비스·같은 주소**입니다. 이 구성에서는 CORS 문제가 생기지 않습니다.
- **원인 후보**
  1. 서비스가 중지/스핀다운 → F07
  2. `file://` 로 열었음 → API 없이 폴백 전용으로 동작(정상). 배포 URL 로 열 것
  3. 주소창에 `?api=<다른 서버>` 가 붙어 있음 → 상단에 **"외부 서버 <host>"** 가 표시되고 **녹음이 그 서버로 전송**됨. 의도한 게 아니면 `?api=` 를 지움 (값은 저장되지 않음)
  4. 별도 프론트를 따로 배포한 경우 → `ALLOW_ORIGINS` 에 그 주소 추가
- **확인**
  ```bash
  curl -sI https://<앱>.onrender.com/health | head -1     # 200?
  curl -sI https://<앱>.onrender.com/ | head -1           # 200? (화면 서빙)
  ```
- **즉시 조치**: 위 원인 순서대로. 백엔드가 죽었으면 5장 A/B/C. 그동안 화면은 폴백으로 카드 학습을 계속할 수 있음
- **롤백**: 5장 A
- **재발 방지**: 시연은 항상 배포 URL(`?api=` 없이)로 연다

### F14. 우리 서버의 429가 여러 사용자에게 한꺼번에 남 (프록시 뒤 IP)

- **증상**: 한 사람이 몇 번 쓰지 않았는데 `요청이 너무 많습니다` (우리 서버 429). 여러 테스터가 동시에 겪음
- **원인**: 앱은 Render 프록시 뒤에 있어 연결 상대(`request.client`)가 프록시입니다. `TRUSTED_PROXY_HOPS=0`(기본)이면 모든 사용자가 **한 IP 로 묶여** `RATE_LIMIT` 를 나눠 씁니다.
  uvicorn 은 `127.0.0.1` 에서 온 `X-Forwarded-For` 만 믿으므로 Render 에서는 자동으로 풀리지 않습니다
- **확인 (배포 후 1회, 2분)**
  1. 내 공인 IP 확인: 브라우저로 `https://ifconfig.me`
  2. 배포 주소 `/health` 를 한 번 열기 (아무 요청이나 됩니다. 프로세스마다 첫 요청 한 번만 기록)
  3. Render → Logs 에서 `프록시 확인:` 한 줄 찾기. IP 는 마지막 자리를 가리고 `(공인)`/`(사설)` 을 붙여 둡니다. 예:
     `프록시 확인: 연결 상대=10.214.3.x(사설), X-Forwarded-For=211.234.10.x(공인) , 172.71.0.x(공인), TRUSTED_PROXY_HOPS=0`
  4. **`연결 상대` 가 내 IP(앞 세 자리 일치)면** uvicorn 이 이미 사용자 IP 를 쓰고 있는 것입니다. 할 일 없음(`0` 유지)
  5. 아니면 `X-Forwarded-For` 에서 **내 IP 가 끝에서 몇 번째인지** 셉니다. 위 예에서는 끝에서 2번째 → `2`
- **조치**: Render → Environment → `TRUSTED_PROXY_HOPS` 를 그 값으로 추가 → 자동 재시작. 재시작 뒤 `/health` 를 다시 열어 3번 로그의 `TRUSTED_PROXY_HOPS` 값이 바뀐 것을 확인
- **주의**
  - 값을 **크게** 잡으면 체인 앞쪽, 즉 사용자가 위조할 수 있는 값을 읽게 됩니다. 헤더만 바꿔 제한을 우회할 수 있습니다. 센 값 그대로 넣으세요
  - 체인이 값보다 짧은 요청은 연결 상대 IP 로 셉니다(모두 묶이는 쪽 = 더 엄격)
  - 확인 전 급하면 `RATE_LIMIT` 상향(아래 C절)이 임시 완화입니다
- **롤백**: `TRUSTED_PROXY_HOPS` 삭제 = 예전 동작
- **재발 방지**: 실사용자 테스트(10/19~) 전에 한 번 확인해 값을 넣어 둡니다

## 5. 롤백 절차 (3계층)

### A. 배포 롤백 — Render 대시보드 (가장 빠름)

1. Render Dashboard → 해당 서비스 → **Deploys**
2. **최근 성공한 배포**를 찾아 **Rollback** → **Rollback to this deploy**
3. 끝 — Render가 그 배포의 **빌드 산출물을 재사용**하므로 새 빌드보다 훨씬 빠릅니다

**반드시 알아야 할 제약 (공식 문서 기준)**

| 제약 | 내용 | 대응 |
|---|---|---|
| 무료 플랜 롤백 범위 | **직전 2개 배포만** 롤백 가능 | 중요한 안정 버전은 **태그(release)로 표시**해 두고, 필요 시 그 커밋으로 재배포 |
| 대시보드 롤백 | **자동 배포가 꺼집니다** | 원인 해결 후 Settings → Auto-Deploy **다시 켜기** |
| API 롤백 | 자동 배포를 **끄지 않음** | push하면 문제 커밋이 다시 들어옵니다 — 대시보드 롤백을 쓰세요 |
| 환경변수 | 공식 문서는 롤백이 서비스의 **현재 설정을 덮어쓰지 않는다**고 설명합니다. 다만 환경변수가 어느 시점 값을 따르는지는 **확정하지 못했습니다** | 가정하지 말고 롤백 직후 `/health` 의 `has_api_key` 를 **직접 확인** |
| 디스크 | 디스크는 롤백되지 않음 | 우리는 디스크를 쓰지 않음 (상태를 서버에 두지 않음) |
| 서비스 중단 | 롤백은 **무중단** | 급하면 망설이지 말고 롤백 |

### B. 코드 롤백 — git (롤백 대상이 없을 때)

```bash
git log --oneline -10                      # 문제 커밋 찾기
git revert <문제커밋SHA>                    # 기록을 남기며 되돌리기 (reset --hard 금지)
git push origin main
```

> **`git reset --hard` + 강제 푸시는 쓰지 마세요.** 팀 협업 기록(평가 항목)이 사라집니다.
> 지금까지의 커밋이 "역할·기여 증빙"이라는 점을 잊지 마세요.

### C. 무배포 완화 — 환경변수 (가장 안전, 배포 없음)

구현자가 1명일 때 **가장 빠른 복구**입니다. Render → Environment → 값 변경 → 자동 재시작.

> **기본값 주의 (코드 기준)**: `RATE_LIMIT=20`, `RATE_WINDOW=60`, `TRUSTED_PROXY_HOPS=0`, `CONFIG_STRICT=0`, `ALLOW_ORIGINS=*`, `AI_MIN_ATTEMPTS=30`(하한, 낮출 수 없음).
> 현재 `render.yaml` 에는 `PYTHON_VERSION`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `OPENAI_API_KEY`, `ASSEMBLYAI_API_KEY` 가 정의돼 있습니다. 모델은 실행 중 목록에서 고릅니다. `STT_SELFTEST=1` 은 검증할 때만 넣고 끝나면 지웁니다.
> 아래 표의 "평상시" 값은 **Render Environment 에 직접 추가해야** 적용됩니다.
> 교육장처럼 한 공용 IP 에서 여러 명이 테스트하면 `RATE_LIMIT=20/60s` 에 걸릴 수 있으니 테스트 전에 올려 두세요.

| 스위치 | 평상시 | 장애 시 | 효과 |
|---|---|---|---|
| `RATE_LIMIT` | `20` | `120` | 테스터 몰릴 때 429 방지 |
| `RATE_WINDOW` | `60` | `60` | 유지 |
| `TRUSTED_PROXY_HOPS` | F14 로 확인한 값 (기본 `0`) | `0` | 사용자별 호출 제한. 0 이면 모든 사용자가 한 IP 로 묶임 |
| `CONFIG_STRICT` | 기본 `0` → 발표 전 `1`로 설정 | `0` | 설정 누락이어도 200 (시연 우선) |
| `ALLOW_ORIGINS` | 기본 `*` (같은 서비스 서빙이면 불필요) | `*` | 별도 프론트를 쓸 때만 좁힘. CORS 문제 즉시 해소 (**임시**) |
| `GEMINI_MODEL` | 비워 둠 (동적 선택) | 목록에 있는 모델명 | 특정 모델 우선 시도 (고정 아님) |
| `AI_MIN_ATTEMPTS` | `30` | `40` 등 | 일시 오류 흡수 (응답 느려짐). 30 미만은 무시됨 |
| `GEMINI_API_KEY` | 등록됨 | (제거) | **최후 수단** — 목업 전환. 4장 F04 주의사항 참조 |

> ⚠️ **키 제거로 목업 전환은 "복구"가 아닙니다.** 서비스가 죽는 것보다는 낫지만,
> 그 상태로 "AI가 동작한다"고 말하면 안 됩니다. **시연을 축소하세요.**

| **T-10분** | `/health` 재예열 (콜드스타트 방지) | `warmed` |
| **시연 중** | 첫 요청이 느리면 멘트로 흡수 | "무료 서버라 첫 호출에 잠깐 준비 시간이 있습니다" |

**시연 중 원칙**

  심사위원은 에러 자체보다 **대응**을 봅니다.
- 목업/샘플 결과에는 **배지를 띄웁니다.**
- 목표를 줄이는 것이 거짓말하는 것보다 낫습니다.

## 7. Go / No-Go 판단 기준

| 상황 | 판단 |
|---|---|
| 3장 게이트 전부 통과 | **Go** — 프론트 연동 진행 |
| `categories: []` | **No-Go** — F02 즉시 수정 (서비스 자체가 깨진 상태) |
| `schema_checker: false` 또는 `degraded` | **No-Go** — F03 수정 후 재확인 |
| `has_api_key: false` | **제한 Go (AI 미검증)** — F04. 서비스는 살아 있음. 목업·샘플 배지 표시, "AI 동작"이라 말하지 않고 시연 축소 |
| `/generate`가 계속 `rejected` | **제한 Go** — F05/F06. 스냅샷 시연으로 전환 |
| `/speak-check` 실제 오디오 실패 | **조건부 Go** — 멀티모달 요건이 걸림. 발표에서 "확장 단계"로 정직하게 |
| 프론트만 안 붙음 | **Go (백엔드 단독 검증)** — 백엔드 데모(`/docs`)로 시연 가능 |

## 8. 하지 말아야 할 것

- ❌ `git add -A` — 깨진 이름 파일·대용량 동영상이 이력에 영구히 박힙니다. **경로를 지정**하세요
- ❌ `git reset --hard` + 강제 푸시 — 협업·기여 기록이 사라집니다
- ❌ 검증을 끈 채 배포하고 "검증 통과"라고 말하기
- ❌ `mock: true`인 상태로 AI가 동작한다고 설명하기
- ❌ 서버 로컬 파일시스템에 상태 저장 (재시작·스핀다운 시 소실)
- ❌ 상시 크론·핑으로 "깨어 있게" 유지 (750 인스턴스 시간 소진 → 정지)
- ❌ 예산 알림만 믿기 (자동 차단이 아닙니다)
- ❌ 시연 당일 새 기능 배포. 무료 플랜 롤백은 **직전 2개 배포만** 가능하므로 규칙은 시간이 아니라 **횟수**: **마지막 정상 배포 이후 추가 배포 2회 초과 금지**(패닉 배포가 안전한 배포를 롤백 창 밖으로 밀어냄). 롤백 자체가 창을 소모하는지는 문서 문구상 소모하지 않는 것으로 읽히나 확정 아님
