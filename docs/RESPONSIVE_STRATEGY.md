# 반응형 웹 앱 전략 (모바일 · 태블릿 · PC / 다크·라이트 / 유동 크기)

> 상태: **설계안 (구현 전)**. 화면 구현에 들어가기 전에 이 문서의 결정 항목(§10)을 확정해야 한다.
> 작성 기준: `New-add-backend` @ 01c6944, 현재 `mockup/` (바닐라 HTML·CSS·JS, FastAPI가 정적 서빙, Node 빌드 없음).
> 근거 구분: **[측정]** = 이 저장소 현재 목업을 Playwright(Chromium)로 직접 측정한 값 · **[계산]** = 대비·clamp 수식을 스크립트로 계산한 값 · **[규격]** = WCAG 2.2 / 플랫폼 가이드 · **[미검증]** = 실기기(iOS Safari·Android Chrome)에서 아직 확인하지 않은 항목.

## 0. 결론 먼저

1. **다른 세션이 준 "반응형 전략" 초안(DC 문서)은 방향은 맞지만 그대로 쓰면 안 된다.** React + Vite + Tailwind v4를 전제로 쓰여 있는데, 이 저장소는 바닐라 JS/CSS이고 Render에는 Node 빌드 단계가 없다(기획서도 HTML·CSS·JavaScript). 전략은 **순수 CSS(커스텀 프로퍼티·미디어/컨테이너 쿼리·`clamp()`)** 로 다시 표현해야 한다.
2. **현재 목업은 반응형이 아니다 [측정].** 폰 프레임(`.device` 392×812 고정) + 288px 데모 사이드 패널 + `100vh` 고정 셸 구조라서 320/360/390px 뷰포트에서 **12개 화면 전부 가로 스크롤**(`scrollWidth` 618px)이 생긴다. 반응형 전환의 첫 작업은 "화면을 늘리는 것"이 아니라 **데모 셸과 제품 셸을 분리하는 것**이다.
3. 브레이크포인트는 **레이아웃이 실제로 바뀌는 3개(600 / 900 / 1200)** 만 둔다. 초안의 5개(360/480/768/1024/1280)는 360·480이 레이아웃 전환점이 아니라 **테스트 폭**이어서 과하다.
4. 폰트는 `rem + vw` 조합의 `clamp()`로 유동화하되(사용자 글자 크기 설정이 먹히도록), **본문은 사실상 15→17px 사이**에서만 움직인다 [계산]. 진짜로 변하는 건 제목·학습 카드 문장이다. 지금 가장 큰 문제는 "유동"이 아니라 **작은 글씨 과다**다: 사용자 화면 텍스트 노드의 **37%가 12px 미만, 83%가 14px 미만** [측정].
5. 다크 모드는 색을 뒤집는 게 아니라 **의미 토큰(semantic token)으로 재정의**해야 한다. 현재 `--ink`가 "글자색"이면서 "기본 버튼 배경"이라 그대로 반전하면 버튼이 깨진다. 그리고 `#fff` 리터럴이 CSS에 **58곳**, 색 리터럴 총 **148곳** [측정] 있어 토큰화가 선행돼야 한다.
6. 초안의 대비 보정색 일부는 **여전히 AA 미달**이다 [계산]: `#c9472a`를 본문 크기 글자색으로 쓰면 크림 배경 위 4.48:1(기준 4.5). `#676c7a`는 `--paper`(#efe9dd) 위에서 4.34:1. 아래 §7에서 수정값을 제시한다.

## 3. 핵심 구조 결정

### 3.1 데모 셸과 제품 셸 분리 (가장 중요)

지금: `.shell = [데모 사이드 288px | .main(topbar + stage[notes | .device(폰프레임) ])]`. 이 전체가 **발표/설명용 목업**이다.

제안:

```
<body>
  <div class="app-root">          ← 제품 (모든 폭에서 실제 반응형)
    <nav class="nav">…</nav>      ← 탭바 / 레일 / 사이드 (폭에 따라 변신)
    <main class="view">…</main>
  </div>
  <aside class="demo-panel">…</aside>   ← 데모 전용: ?demo=1 일 때만 DOM 생성, 모바일에선 하단 시트/드로어
</body>
```

- 폰 프레임(`.device`), 상태바(9:41), 노치는 **`?demo=1&frame=1`에서만** 그린다. 제품 모드에서는 존재하지 않는다.
- 데모 사이드 패널은 1200px 이상에서만 오른쪽 고정 패널, 그 미만에서는 `<dialog>` 드로어(버튼으로 열기).
- 이유: 반응형 요구를 "프레임 안 화면이 줄어든다"로 구현하면 실제 모바일에서 프레임 위에 또 프레임이 생긴다.
- **약점/반론**: 데모 패널(날짜 이동, 실패 시뮬레이션 등)은 심사·시연에서 필수일 수 있다. → 제거하지 않고 `?demo=1`로 격리한다. 기본 URL은 제품 모드.

### 3.2 브레이크포인트 (모바일 우선, `min-width`)

| 이름 | 폭 | 내비게이션 | 콘텐츠 | 대표 기기 |
|---|---|---|---|---|
| **base** | 0–599 | 하단 탭바(4칸) | 1열, 거터 16px | 폰 세로 (320~430) |
| **md** | 600–899 | 좌측 **레일 72px**(아이콘+짧은 라벨) | 1열 읽기 폭 최대 640px 중앙, 또는 2열(일부 화면) | 소형 태블릿, 폰 가로(예: 844×390) |
| **lg** | 900–1199 | 레일 72px | **2열 마스터-디테일**(일정표·문장 모음), 읽기 폭 최대 720px | 태블릿 가로(1024×768), 소형 노트북 |
| **xl** | ≥1200 | **사이드 240px**(펼침 라벨) | 2열 + 우측 보조 패널 가능, 콘텐츠 컨테이너 최대 1120px | 노트북/데스크톱 |

- 전환 근거: 600은 Material 3 compact→medium 경계, 900은 medium 상단(= expanded 직전), 1200은 expanded→large 경계 [규격: Material 3 window size classes 600/840/1200]. 우리는 840 대신 900을 쓴다 — 마스터-디테일에 최소 `list 320px + detail 480px + 레일 72px = 872px`가 필요하기 때문이다(실제 콘텐츠에서 역산).
- **폰 가로(844×390)** 는 폭이 md라 레일이 되지만 **높이가 390**이라 레일이 넘친다 → `@media (max-height: 480px)`에서 레일 라벨 숨김+스크롤, 학습 카드 `min-height`를 `dvh` 기반으로.
- 컨테이너 쿼리(`@container`)는 **카드 내부 요소**(예: 일정 행, KPI)에만 사용한다. 지원 범위는 최신 Chrome/Safari 16+/Firefox 110+ [규격]. 필수 레이아웃은 미디어 쿼리로 둔다(폴백 안전).

### 3.3 "% 배분" — 폭을 어떻게 나누는가

원칙: **고정 px는 내비게이션(72/240)·최대 폭·최소 터치 대상에만**, 나머지는 `fr`/`%`/`minmax()`.

레이아웃 변수:

```css
:root {
  --gutter: clamp(16px, 4vw, 32px);   /* 600px에서 24, 1024에서 32 */
  --nav-rail: 72px; --nav-side: 240px;
  --read-max: 40rem;                  /* 640px: 학습 카드·폼 */
  --wide-max: 70rem;                  /* 1120px: 대시보드/마스터-디테일 */
}
```

폭별 실제 배분 (거터 포함, 계산 [계산]):

| 뷰포트 | 내비 | 콘텐츠 영역 | 콘텐츠 | 비고 |
|---|---|---|---|---|
| 360 | 하단 탭(높이 56+safe) | 360 | 거터 16×2 → **328 (100%−32px)** | |
| 430 | 하단 탭 | 430 | 398 | |
| 768 | 레일 72 (9.4%) | 696 | 읽기열 **640 중앙**, 좌우 여백 각 28 | 2열로 늘리지 않음 — 줄이 너무 길어짐 |
| 1024 | 레일 72 (7%) | 952 | 거터 32×2 → 888: 마스터 **5fr : 디테일 7fr**, gap 24 → 약 **370 : 494** | 일정표/문장 모음 |
| 1280 | 사이드 240 (18.8%) | 1040 | 거터 32 → 976: **5fr:7fr** → 약 **397 : 555** | 컨테이너 최대 1120 이하라 꽉 참 |
| 1920 | 사이드 240 (12.5%) | 1680 | 컨테이너 **1120 중앙** (66.7%), 좌우 여백 각 280 | 더 넓히지 않는다: 줄 길이·시선 이동 |

- 읽기 폭(한글 한 줄 약 30~45자 = 대략 `40rem`)을 넘기지 않는다. 학습 카드는 1920에서도 최대 `40rem`.
- 마스터:디테일 `5fr:7fr`는 **초기 가정**이다. 일정표 행 최소 폭(날짜 54 + 내용 + 상태 배지 약 80 = 약 300px)이 정한 하한이므로 `grid-template-columns: minmax(300px, 5fr) minmax(0, 7fr)` 로 쓴다.

## 5. 메뉴 잘림·깨짐 방지 규칙 (체크리스트)

1. **flex/grid 자식에는 `min-width: 0`** 기본 적용 (`.main`, `.srow .ct`, `.window`, `.admin-main`은 이미 있음 — 전 구성 요소에 규칙화). 이게 빠지면 긴 영어 문장이 컨테이너를 밀어낸다.
2. **탭바**: `grid-template-columns: repeat(4, minmax(0, 1fr))`, 라벨 `white-space:nowrap; overflow:hidden; text-overflow:ellipsis`, 라벨 최대 4자(현재 "문장 모음"=4자 OK, 번역/추가 시 5자 초과 금지). 높이는 px 고정 대신 `min-height: 3.5rem` + `padding-bottom: env(safe-area-inset-bottom)` — 글자 확대 시에도 늘어난다.
3. **레일**(md/lg): 세로 목록 + `overflow-y:auto`, 아이콘 위 라벨 아래, 라벨 12px 하한. 높이 < 480이면 라벨 숨김(아이콘만 + `aria-label` + `title`).
4. **사이드**(xl): 라벨 전체 표시, 긴 항목은 말줄임 + `title`.
5. **가로로 넘치는 칩/도시 탭**: 줄바꿈하지 않고 `overflow-x:auto; scroll-snap-type:x proximity`, 양 끝에 **fade 마스크**(`mask-image`)로 "더 있음" 단서 제공. 스크롤바 숨김(`scrollbar-width:none`)은 마스크가 있을 때만.
6. **긴 텍스트**: 한글 `word-break: keep-all` + `overflow-wrap: break-word`(긴 영문 토큰·URL 대비). 영문 학습 문장은 `text-wrap: balance`(제목·카드 문장), 본문은 `text-wrap: pretty` (미지원 브라우저는 무시되므로 안전).
7. **모달**: 폭 `min(420px, 100% - 2*var(--gutter))`, 최대 높이 `calc(100dvh - 2rem)` + 내부 스크롤. base에서는 바텀시트(현재 방식 유지), md 이상은 중앙 다이얼로그.
8. **토스트**: `left: calc(50% + 144px)`(사이드 288px 가정) 제거 → `inset-inline: var(--gutter); margin-inline:auto; width:fit-content; bottom: calc(var(--tab-h) + env(safe-area-inset-bottom) + 12px)`. 탭바/액션바 위에 뜬다.
9. **높이**: `100vh` → `100dvh` (미지원 시 `100vh` 폴백 선언 먼저). 키보드가 올라오는 입력 화면은 `interactive-widget=resizes-content`(viewport meta) 또는 VisualViewport 확인 [미검증: iOS는 이 값 미지원일 수 있음 → 하단 고정 버튼이 키보드에 가려지는지 실기기 확인 필요].
10. **Safe area**: `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` + 탭바/하단 액션 바/풀스크린 모달에 `env(safe-area-inset-*)` 패딩. 가로 모드는 좌우 inset도.
11. **글자 200% 확대/320px 리플로우**(WCAG 1.4.4/1.4.10): 모든 간격·높이를 가능하면 `rem`. 데이터 표 외에는 2차원 스크롤 금지. 수용 기준에 "브라우저 글자 크기 200% + 폭 320px에서 가로 스크롤·잘림 없음" 포함.
12. **고정 px 제거 목록**(§1의 위험 요소 표): `.flip` 360 → `clamp`, `.login h1` 150px 마진 → 제거, `.stamp` → `clamp(120px, 45vw, 220px)`, `.admin min-height:640px` → 제거.

## 6. 글자·컴포넌트 크기의 유동화

### 6.1 규칙

- **루트는 건드리지 않는다** (`html { font-size:100% }`). 사용자의 브라우저/OS 글자 설정을 존중한다. 모든 폰트·간격은 `rem`.
- `clamp(min, rem + vw, max)` — `vw` 단독 사용 금지(확대 무력화).
- 한글 본문 `line-height` 1.55–1.65 (영문 1.4~1.5보다 크게), 학습 카드 영어 문장은 1.2–1.3.
- **본문 하한 15px, 캡션 하한 12px** (제안). 현재 10~11px 텍스트(탭 라벨 11, `.no` 10.5, 배지 11 등)를 12px로 올린다. 12px 이하를 허용하는 곳은 "순수 장식 의사 텍스트"뿐이며 예외 목록으로 관리.
- 사용자가 직접 바꾸는 "글자 크기"(작게/보통/크게)는 **루트가 아니라 `--font-scale` 변수를 토큰에 곱한다** (예: `calc(1rem * var(--font-scale))` 대신 토큰 값 자체에 `* var(--fs)`) — 브라우저 설정과 앱 설정이 곱으로 합쳐지는 점을 문서화(§9-4).

### 6.2 타입 스케일 (제안 토큰) — 폭별 계산값 [계산]

- 캡션/본문의 `vw` 항은 효과가 거의 없다(최대 1px 안팎). "폭에 따라 부드럽게 커지는 본문"은 사실상 **허상**이고, 이 토큰들은 `rem` 하한·상한이 실질 값이다. 그래도 유지하는 이유는 큰 화면에서 15→17px로 올려 1280px 읽기 편의를 확보하기 위함이며, 단순화하려면 본문은 고정 `1rem`으로 둬도 무방하다. (→ 결정 항목 §10-6)
- 제목·표시용(`title/study/display`)에서만 `vw`가 실질 효과(22→30, 26→36, 36→52).
- 현재 값(제목 26, 학습 KO 25, EN 30, hero 46, 본문 14~15)과의 차이: **모바일에서 제목·학습 문장이 작아지고(26→22, 30→26), 데스크톱에서는 커진다.** 학습 카드 영어 문장이 핵심 콘텐츠이므로 모바일 26px이 기존 30px보다 작아져도 읽기에 충분한지 확인이 필요하다 [미검증, 실기기].

## 7. 라이트 / 다크 / 시스템

### 7.1 메커니즘

```html
<!-- <head> 최상단 인라인 (깜빡임 방지) -->
<script>try{var t=localStorage.getItem('cd_theme');if(t==='light'||t==='dark')document.documentElement.dataset.theme=t}catch(e){}</script>
<meta name="color-scheme" content="light dark">
<meta name="theme-color" content="#fbf8f1" media="(prefers-color-scheme: light)">
<meta name="theme-color" content="#12151c" media="(prefers-color-scheme: dark)">
```

```css
:root { color-scheme: light; /* 라이트 토큰 */ }
@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { color-scheme: dark; /* 다크 토큰 */ } }
:root[data-theme="dark"] { color-scheme: dark; /* 다크 토큰 (위와 동일 — 중복 방지 위해 빌드 없이 CSS 변수 블록을 두 번 선언하는 비용 감수) */ }
```

- 3택(시스템/라이트/다크): `data-theme` 없음 = 시스템. `localStorage('cd_theme')`에 `light|dark`만 저장, "시스템"이면 키 삭제. 저장 실패(시크릿 모드 등)는 try/catch로 세션 내 메모리만.
- `color-scheme`을 선언해야 **폼 컨트롤·스크롤바·기본 배경**이 따라온다. 데모 패널 `input[type=date]`는 이미 `color-scheme: dark`를 쓰고 있다.
- **주의(약점)**: `theme-color` 메타의 `media` 속성은 사용자가 앱 안에서 수동으로 다크를 고른 경우를 반영하지 못한다 → 수동 선택 시 JS로 `theme-color` 갱신 필요.
- `cd_theme`는 개인정보가 아닌 환경설정이다. 동의 화면(`CONSENT_ITEMS`)의 "브라우저 저장" 항목 문구에 포함할지 결정 필요(최소한 철회 시 삭제 대상에 넣을 것).

### 7.4 다크 모드에서 같이 해야 하는 것

- **하드코딩 색 제거**: CSS 색 리터럴 148곳 + app.js 인라인 `style=""` 77곳(그중 색 포함분)을 토큰으로 치환. 이것이 다크 모드 작업량의 대부분이다.
- **그림자**: 다크에서는 `--shadow`가 안 보인다 → 표면 밝기 차(`--surface` vs `--bg`)와 1px 경계로 계층 표현. (다크 `surface #1b2030` vs `bg #12151c` = 1.13:1 — 의도적으로 약함, 경계선으로 보강.)
- **순수 검정/순수 흰색 금지**: 다크 배경 `#12151c`, 텍스트 `#ece7dc`.
- **이미지/SVG**: 아이콘은 `currentColor` 사용 확인(현재 SVG `I.*`), 래스터 이미지 없음(확인).
- **카드 뒷면(`--ink` 배경)**: 라이트에서는 어두운 카드, 다크에서는 `--surface-2`+밝은 글자로. "뒤집었을 때 대비" 유지.
- **히어로(`.hero` ink/sea/accent 단색)**: 두 모드 모두 어두운 단색 유지 가능(글자 흰색) — 다크에서 `--ink` 토큰이 밝아지므로 `--hero-bg` 별도 토큰 필요.
- **`prefers-contrast: more`**: 후순위. 토큰 구조상 나중에 추가 가능.

## 8. 입력 방식·접근성·성능 규칙

- 터치 대상: 터치 우선 기기(`pointer: coarse`)에서 **44×44px 이상**(Apple HIG 44pt, WCAG 2.5.5 AAA 44px). WCAG 2.2 AA(2.5.8)의 최소선은 **24×24px**(간격 예외 있음) — 데스크톱 마우스에서는 24~32px 허용. 폭이 아니라 `pointer`/`hover` 미디어 특성으로 분기.
- `:hover` 효과는 `@media (hover: hover)` 안에서만(터치에서 hover 고착 방지) — 현재 `.btn:hover`, `.nav-item:hover` 등 다수.
- 포커스: `:focus-visible` 2px 아웃라인(현재 입력 `outline:none` + 박스섀도 3px 8% 불투명 → 약함). 키보드로 데스크톱 사용(탭 이동)이 가능해야 함.
- `prefers-reduced-motion: reduce`: 오빗 회전, 카드 플립, 모달 `up/fade` 애니메이션 단축/제거.
- 가로 모드 폰: 학습 카드가 `dvh` 기반이라 짧은 높이에서 줄어듦, 하단 액션 바는 `position:sticky`.
- 스크롤 컨테이너는 **문서 스크롤을 기본**으로(주소창 자동 숨김 동작 유지), 내부 `overflow:auto` 영역은 모달/마스터-디테일 패널에만. 현재 `.app`이 내부 스크롤인데(`overflow-y:auto`), 폰 프레임 시절 구조이므로 제품 셸에서는 문서 스크롤로 바꾼다. (⚠️ 이 변경은 `scroll-behavior`/`scrollTop` 복원 로직 `render()`(app.js ~L623)에 영향 — 같이 수정해야 한다.)
- 성능: Pretendard dynamic-subset + Fraunces + JetBrains Mono 3개 폰트가 CDN. 모바일 첫 로드에서 FOUT 대비 `font-display: swap`(Google Fonts URL에 이미 `display=swap`). 반응형 때문에 새로 늘어나는 비용은 없음.

- **선택 UI**: 홈(·종료 후) 화면 "화면 모드" 시스템/라이트/다크. `localStorage cd_theme`(light|dark, 시스템이면 키 삭제), `<head>` 인라인 스크립트가 CSS 전에 `data-theme` 과 `theme-color` 를 정해 깜빡임 없음, 시스템 설정 변경은 새로고침 없이 따라감. 개인정보가 아닌 화면 설정이라 동의·철회 흐름과 무관.
- **입력 경계** `--border-input`(라이트 `#8f8a7d` 3.44:1 / 다크 `#6b7385` 3.41:1), 키보드 포커스 링 `:focus-visible`(라이트 `#161b26` / 다크 `#8fb4ff`).
- **측정**: `mockup/audit/contrast_audit.js`(모든 텍스트의 실제 배경 대비) — 라이트 기준 **58종 미달 → 0**, 다크 0, 폭 320/390/768/1280 · 화면 13종. `tokens.test.js` 가 토큰 조합 대비(라이트·다크 각 70여 쌍)·두 다크 블록 동일·주소창 색=`--bg` 를 검사. e2e `test_shell.py` 57/57(시스템 다크, 수동 선택·저장·복원, 깜빡임 없음, 시스템 변경 추적, 관리자 다크).
- **부수 발견·수정**: 사이트 데이터 차단 환경(`window.localStorage` 접근 자체가 예외)에서 앱이 아예 뜨지 않던 결함 — `STORE` 래퍼로 수정, 테스트 추가.
- **한계**: 대비 감사는 배경 이미지·그라데이션 위 글자, SVG 내부 글자, 데모 패널을 건너뛴다. 큰 글자 3:1 기준은 계산 크기로 판정. 색 구분 외 단서(색약), `prefers-contrast: more`, 인쇄는 미검토. 실기기 다크 렌더링(OLED 번짐 등)·`theme-color` 의 iOS 반영은 미확인. 다크 값은 눈으로 본 스크린샷 + 계산으로 정했고 팀 디자인 검수는 받지 않았다.

### 10.2-5 실기기 보고 수정: iOS 날짜 입력 넘침 (2026-10-10)

- **증상** (아이폰, 배포본): 날짜 입력 두 칸이 카드 오른쪽 밖으로 삐져나오고 서로 겹침, 학습 시작일 입력은 화면 오른쪽 밖까지 늘어남, 날짜 글자가 가운데 정렬.
- **원인**: iOS Safari 의 `<input type="date">` 는 기본 모양에서 **고유 폭(≈180px)을 고집**해 `width`·`min-width:0` 를 무시한다. 우리는 ①한 칸 최소폭을 `minmax(130px,1fr)` 로 하드코딩해 폰에서도 두 칸으로 나눴고(칸 ≈165px < 고유 폭) ②P2 에서 입력 글자를 16px 로 올려 고유 폭이 더 커졌다. Chromium 으로만 검증해서 잡지 못했다 — **이 환경에는 WebKit 이 없다**(설치 시도 실패).
- **수정**: `input[type=date]{appearance:none; display:block; inline-size:100%; min-inline-size:0}` + `::-webkit-date-and-time-value{text-align:start}`, 두 칸 최소폭을 `min(100%, 12rem)`(rem 이라 글자 확대에도 맞음)로 바꿔 폰 폭에서는 한 줄씩 쌓임. e2e 회귀 테스트(320~768px, 입력이 카드 안·appearance none·폰에서 1열) 추가.
- **미검증**: 수정 후 실제 iOS Safari 에서의 모습은 확인하지 못했다. 배포 뒤 아이폰에서 확인해야 한다.

### 10.2-6 P4 구현 결과 (2026-10-10) — 마스터-디테일

- **범위**: 일정표·학습·문장 모음. **≥900px(제품·데모 모드)** 에서만 2열, 그 미만과 legacy 레이아웃은 기존 1열 그대로. 관리자 화면은 P1 의 전체 폭 레이아웃 유지(별도 마스터-디테일 없음).
- **방식**: 라우터를 만들지 않았다. 새 상태 없이 기존 `S.studyDate` 를 "선택한 날"로 재사용한다. `isWide()`(matchMedia 900px)가 참이면 `scrSched`/`scrStudy` 가 `scrSplit()` 으로 왼쪽 일정 목록 + 오른쪽 `studyView(r)`(학습 카드·완료 버튼; 기존 `scrStudy` 본문을 함수로 뺀 것)를 그린다. 날짜를 눌러도 `S.screen` 은 그대로이고 오른쪽만 바뀐다(좁은 화면은 예전처럼 학습 화면으로 이동). 폭이 바뀌면 재렌더.
- 일정표·학습 탭은 넓은 화면에서 같은 2열을 보여 준다(탭 강조만 다름). 말하기·TTS 상태 갱신 가드(`studyShown()`)가 두 화면을 모두 학습 중으로 취급한다 — 2열에서 말하기 동의→녹음→이탈 시 정리까지 확인.
- **문장 모음**: 왼쪽 = 탭·상황/도시 필터(세로 목록), 오른쪽 = 문장.
- 폭 배분: 열 `minmax(18.75rem, 5fr) : minmax(0, 7fr)`, 최대 폭 70rem(1120px), 목록은 sticky + 자체 스크롤(선택·재렌더에도 스크롤 위치 유지).
- 검증: e2e `test_shell.py` 86/86(2열 구성·선택 시 화면 유지·목록 스크롤 유지·카드 뒤집기·학습/문장 모음 탭·768 로 줄면 1열·다시 넓히면 2열·legacy 는 2열 아님), 가로 스크롤 0(320~1920), 글자 대비 라이트·다크 1024/1280 미달 0.
- **한계**: 상세에서 카드를 넘기거나 뒤집은 상태는 다른 날짜를 눌렀다 돌아오면 초기화(기존 학습 화면과 같은 동작). 브라우저 뒤로가기는 날짜 선택을 기억하지 않는다(라우터 없음). 태블릿 세로(≈768)는 1열이다. 실기기(iPad 가로 등) 미확인.

### 10.2-7 접근성 마무리: 글자 확대·모션 줄이기 (2026-10-10)

- **font-size 의 px → rem 일괄 변환**(CSS 148곳 + app.js 인라인 17곳). 기본 16px 기준 값이 정확히 같도록 k/32 정밀도로 변환(스냅샷 32장 × 라이트·다크·legacy 픽셀 동일 확인; legacy 1장은 기존에도 흔들리던 로고 안티앨리어싱). 효과: 브라우저/OS 의 기본 글자 크기 설정이 **모든** 글자에 반영된다(그 전에는 rem 토큰 글자만 커지고 px 글자는 그대로였다 — 200% 시뮬레이션에서 확인).
- **200% 확대 리플로우**(WCAG 1.4.4/1.4.10): 320px + `html{font-size:200%}` 에서 11개 화면 가로 스크롤 0. 이 과정에서 잡은 것: 관리자 상태 칩·필터·헤더 버튼·타임라인 장소 행 줄바꿈, 하단 탭 라벨을 말줄임 대신 줄바꿈. (`ZOOM=200 node mockup/audit/responsive_audit.js` 로 재현). 300% 는 홈 배지·관리자 사용자 표 등에서 넘침이 남아 있다 — WCAG 요구(200%) 밖이라 미처리.
- **prefers-reduced-motion**: 애니메이션·전환을 사실상 끔(제품·데모 모드). 상태는 글자로도 표시된다.
- e2e `test_shell.py` 89/89(200% 11화면, 탭 라벨, 모션 줄이기 추가).

## 11. 이 문서의 한계

- 측정은 Chromium(헤드리스) 1종 + 폭만 바꾼 것이다. **실기기 렌더링, iOS Safari 고유 동작(주소창, 입력 확대, safe area, `interactive-widget` 미지원 가능성)은 확인하지 않았다.**
- 대비·clamp 수치는 계산값이다. 실제 렌더링(안티앨리어싱, 폰트 굵기)에 따른 체감은 다를 수 있다.
- Material 3 창 크기 클래스·WCAG 2.2 기준·브라우저 지원 범위는 외부 규격에 대한 기억에 기반하며(이 환경에서 외부 문서 접근이 막혀 재조회하지 못함) **구현 전에 원문으로 재확인**해야 한다.
- 폭 배분 비율(5fr:7fr)과 폰트 상·하한은 **초기 가정**이며, 실제 콘텐츠(긴 영문 문장, 도시명)와 사용자 테스트로 조정해야 한다.
- 이 설계는 "제품 UI"를 전제로 한다. 현재 목업이 팀 시연용이라면 P0~P1(셸 분리)만으로도 시연 가능한 최소 반응형이 되는지 먼저 결정해야 한다.
