# 에이전트 작업 규칙

이 문서는 이 저장소에서 작업하는 에이전트가 매번 따르는 절차다. 제품이 무엇을 해야 하는지는 [`docs/product/requirements.md`](../product/requirements.md)가 정한다. 이 문서는 그 요구를 어떤 순서로 고칠지만 정한다.

## 1. 아이디어를 가져오는 곳

아이디어는 아래 둘에서만 가져온다.

| 위치 | 무엇을 보나 |
|---|---|
| `.` (저장소 루트) | 지금 제품. `README.md`, `docs/product/requirements.md`, `mockup/`, `backend/`, `agent_contract/` |
| `./other` | 이전 자료. 디자인 DC, 기획 PDF, 발표, 예전 스냅샷 |

`other/Project261000/codyssey_final` 은 루트보다 오래된 사본이다. 루트와 다르면 루트의 코드와 `docs/product/requirements.md`를 따른다. `other/Project261000/transcribe_app` 은 다른 프로그램이라 이 제품의 기능으로 가져오지 않는다.

저장소 밖에 있는 기능 아이디어로 범위를 늘리지 않는다. 필요한 디자인·참고 파일이 트리 안에 없으면 구현을 멈추고 사용자에게 그 파일을 요청한다.

## 2. 세션을 열면

1. `git status`, 브랜치, 원격, `HEAD`를 다시 읽는다. 조사 도중에도 브랜치가 움직일 수 있다.
2. [`docs/workflow/REPO_STATE.md`](REPO_STATE.md)를 그 시점의 사실로 고친다. 구조, 열린 요구사항, `.`와 `./other`에서 고를 수 있는 다음 작업, 문서끼리 다른 점을 적는다.
3. 사용자에게 이번 세션 디렉터리의 절대 경로를 밝힌다.
4. 이번 세션이 어떤 파일을 왜 만지는지 구체적으로 말한다.

세션 파일은 사용자 홈의 Grok 세션 디렉터리에 있다. 경로는 세션마다 바뀌므로, 그 회차의 경로는 `REPO_STATE.md`의 "최근 세션"에 적고 사용자에게도 그대로 말한다. 세션 디렉터리 안의 대화·설정 파일은 저장소에 복사하지 않는다.

## 3. 구현 전 계획과 단계별 교차검증

코드, 제품 문서, 설정을 바꾸기 전에 단계 계획을 적는다. 계획은 세션 설명과 `REPO_STATE.md`의 "이번 작업"에 같이 남긴다.

각 단계는 다음을 가진다.

- 목적
- 손댈 파일
- 완료 조건
- 무엇을 읽고 맞는지 볼지

단계를 구현한 에이전트는 그 단계를 통과로 적지 않는다. 다른 에이전트가 완료 조건과 근거 파일(코드, `docs/product/requirements.md`, 해당 단계가 따른 디자인 자료)을 대조한다.

- 통과하면 다음 단계로 간다.
- 불일치가 있으면 고친 뒤 같은 단계를 다시 검증한다.
- 검증 결과(통과·불일치, 무엇을 봤는지)를 `REPO_STATE.md`의 이번 작업에 남긴다.

한 단계의 검증이 끝나기 전에 다음 단계의 구현을 시작하지 않는다. 조사와 계획 작성은 구현이 아니다.

## 4. 디자인과 참고 파일

단계에 필요한 파일이 `.` 또는 `./other`에 있으면 그 파일을 쓴다. 이미 있는 파일을 다시 요청하지 않는다.

없거나, 트리 안의 자료가 그 단계의 완료 조건을 정하기에 오래되었으면 구현을 멈추고 요청한다. 요청에는 파일 이름, 쓰는 단계, 없으면 무엇을 못 하는지 적는다.

## 5. 작업이 끝나면

- 이번 작업의 파일만 커밋한다. 작업과 무관한 수정, 비밀, `__pycache__`는 넣지 않는다.
- 그 작업용 브랜치에 커밋한다. 진행 중인 다른 수정 브랜치에 절차 문서나 무관한 기능을 섞지 않는다.
- 푸시 원격은 `origin` (`https://github.com/seongbin45/codyssey_final`)이다.
- `team` (`https://github.com/01044402345o-beep/codyssey_final.git`)은 사용자가 그 원격을 지정한 작업에서만 푸시한다.
- 커밋 메시지에는 무엇을 왜 넣었는지 적는다.
- 사용자에게 커밋 해시, 브랜치 이름, 푸시한 원격을 말한다.

### 5.1 팀 `main` 에는 직접 푸시하지 않는다

팀 저장소 `main` 반영은 **PR 을 거쳐** 한다. PR 을 열기 전에 로컬에서 두 검사를 통과시킨다.

```
node --test mockup/ai.test.js mockup/tokens.test.js
python e2e/test_shell.py <배포 또는 로컬 주소> <스크린샷 폴더>
```

이유는 기록이다. 2026-10-12 `c76335a` 가 팀 `main` 에 직접 들어갔고, 그 커밋에서 `mockup/styles.css` 941줄(반응형·다크 모드 토큰)이 사라져 `mockup/tokens.test.js` **6개가 실패한 채로 배포**됐다(`/api/health` 의 `deploy.commit` 이 그 커밋). PR 이었다면 CI 가 막았을 경로다. 복구는 `7065dc9`, 이후 같은 유형의 재발을 막는 터치 스와이프 E2E 가 `e18cb77`(PR #55)에 들어갔다.

같은 이유로, 브랜치 하나에 여러 성격의 변경을 섞지 않는다. `c76335a` 는 커밋 메시지가 "스와이프 블록 중복 제거"였지만 실제 변경은 CSS 대체(−941/+471)를 포함했다.

PR 은 `gh pr create --fill --base main` 으로 연다. 대상 저장소는 `01044402345o-beep/codyssey_final` 이고 base 는 `main` 이다. 이 클론에서는 `gh repo set-default` 가 그 저장소다. 헤드는 포크 `seongbin45:<브랜치>` 이며, 그 명령은 `team` 원격에 푸시하지 않는다.
## 6. 사실이 서로 다를 때

1. 현재 코드와 테스트
2. `docs/product/requirements.md`
3. `README.md`
4. 설계 문서 (`docs/design/RESPONSIVE_STRATEGY.md`, `docs/product/ENRICHMENT_PIPELINE.md` 등)
5. `other/Project261000/design/`
6. `docs/planning/prd.md`, `docs/planning/시나리오완료.MD`, `docs/planning/기술스택.md` (초기 기획, 이력)

위에 있는 것을 따른다. 차이를 발견하면 `REPO_STATE.md`에 적고, 고친 문장이 있으면 그 커밋에 함께 넣는다.

## 7. 사용자에게 항상 말할 것

- 세션 디렉터리 절대 경로
- 이번 단계의 목적과 손댄 파일
- 검증 에이전트가 무엇을 보고 통과했는지, 또는 무엇을 고쳐 다시 봤는지
- 커밋 해시와 푸시한 브랜치
- 다음 구현 전에 필요한데 트리에 없는 파일
