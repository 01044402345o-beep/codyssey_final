# 장소 목록 0건 조사 메모 (2026-11-02)

## 조사 범위와 결론

팀장 메일의 첫 번째 항목인 “일부 도시에서 장소 목록이 0개로 나오는 현상”을 코드와 운영 문서 기준으로 구분해 살펴봤다.

**현재 자료만으로 실제 장소 추천 오류의 재현 사례나 원인을 특정할 수 없다.** 사용자는 도쿄와 요코하마에서 장소 추천과 학습 내용이 정상 표시되는 것을 확인했다. 따라서 두 도시는 현재 재현 사례가 아니다.

## 1. Firestore의 `geo_countries.city_count=0`은 무엇인가

- `docs/ops/GEO_REFRESH.md`에 따르면 `geo_countries/{ISO2}`는 국가 정보, `geo_cities/{ISO2}_{nnn}`는 GeoNames 도시·마을 행을 압축한 샤드다.
- `city_count`는 수도의 유무나 관광 명소 수가 아니라 **해당 국가에 수집된 도시·마을 행 수**다.
- `backend/app/geo.py`는 `city_count`가 0인 국가를 도시 선택 목록에서 제외한다. 코드 주석은 BV·HM·AN·CS를 도시가 없는 무인도 또는 폐지 코드의 예로 든다.
- 그러므로 앞서 확인된 AN, BV, CS, HM의 0은 그 자체로 장소 검색 오류의 증거가 아니다. 수도명이나 국가 문서가 존재해도, 이 도시 데이터 수집 기준에 해당하는 행이 없으면 0일 수 있다.

## 2. 도시·마을 목록과 추천 장소는 다른 흐름이다

- 도시 선택 자료: Firestore `geo_countries` / `geo_cities` → `backend/app/geo.py`.
- 여행지 추천 자료: `POST /research` → `backend/app/research` 파이프라인.
- 추천 장소는 Wikivoyage 자료를 먼저 쓰고, 부족하면 설정된 대체 소스(국내 TourAPI, Wikidata 주변 장소, 설정된 경우 Google Places)를 차례로 조회한다. 이 경로는 `geo_countries.city_count`를 추천 장소 개수로 사용하지 않는다.

따라서 “도시 선택 목록에서 특정 국가가 보이지 않는다”와 “도시를 선택했지만 추천 장소가 0개다”는 별도로 확인해야 한다.

## 3. 현재 코드에서 확인한 복구 장치와 남은 진단 공백

- 좌표가 있고, 기본 장소와 대체 소스 모두 결과가 없으며, 소스 장애가 아니면 주변 검색형 소스를 더 넓은 반경으로 한 번 재시도한다 (`backend/app/research/nodes.py`, `chain.WIDER_SCALE`).
- 이전 정상 캐시가 있고, 새 결과가 장애로 기존의 절반보다 작아지면 이전 결과를 유지한다 (`backend/app/research/chain.py:keep_last_good`). 만료된 캐시도 유예 기간 동안 읽을 수 있다 (`backend/app/research/cache.py`).
- 보고서에는 `place_status`, `none_reason`, 소스별 `chain.status/outcome/count`, Wikivoyage 제목, stale 여부, fallback 정보가 포함된다 (`backend/app/research/report.py`).

실제 0건 사례가 나오면 아래 정보를 같은 요청 시점의 조사 보고서에서 확인해야 원인을 나눌 수 있다.

1. 나라·도시 입력값과 선택된 도시의 좌표 또는 도시 식별 정보
2. 배포 커밋 또는 확인 시각
3. `place_status`, `none_reason`, `stale`, `fallback`
4. `wikivoyage.title/url`과 소스별 `chain` 결과
5. 화면에서 장소가 비어 있었는지, API 응답의 `places` 자체가 비어 있었는지

이 정보 없이 Firestore의 국가별 도시 수만 보고 추천 장소 오류를 판정하면 원인을 혼동할 수 있다.

## 4. 데이터 갱신·복구 제안

운영 데이터는 건드리지 않았다. geo 데이터 갱신은 현재 변경된 문서만 쓰고 오래된 샤드를 삭제하며, `geo_meta/current`를 마지막에 기록한다 (`docs/ops/GEO_REFRESH.md`). 자동 삭제 전에 복구할 과거 데이터가 별도로 보존되는지는 해당 문서만으로 확인되지 않는다.

다음 정비 시에는 다음을 권한다.

- 갱신 전 `geo_meta/current`의 버전·해시·국가별 개수와 기존 샤드 목록을 복구용으로 보관한다.
- 갱신 결과의 국가 수·도시 행 수가 직전 버전보다 크게 줄면 삭제·반영을 중단하고 검토한다.
- 문제가 확인되면 보관한 이전 버전의 샤드와 메타데이터를 함께 복원한다.
- 장소 검색 캐시는 현재의 마지막 정상 결과 보존 동작을 유지하고, 실패·빈 결과·정상 결과를 보고서에서 구분해 확인한다.

이 제안은 운영 데이터 수정이나 코드 변경이 아니다. 별도 구현 전에 팀에서 복구 기준과 보관 위치를 정해야 한다.

- **미확인:** 실제로 장소가 0건인 도시, 그때의 API 보고서/소스 결과, geo 갱신본을 과거 버전으로 복원할 수 있는지.
