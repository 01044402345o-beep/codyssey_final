# 장소 목록 0건 조사 및 복구 제안 (2026-11-02)

## 목적과 결론

팀장 요청의 첫 번째 문제인 “도시 장소를 찾지 못하거나 장소 목록이 0개가 되는 현상”을 코드 경로, 운영 문서, 현재 확인된 사용자 사례로 나눠 조사했다.

**현재 확인 자료만으로 실제 0건 장애의 발생 도시나 단일 원인을 확정할 수 없다.** 사용자는 도쿄와 요코하마에서 장소 추천이 정상 표시되는 것을 확인했다. 두 도시는 재현 사례가 아니다. 따라서 이 문서는 원인 확정이나 수정 완료 보고가 아니라, 확인된 흐름과 재현 시 증거를 남기고 복구하는 제안이다.

## 1. 먼저 구분해야 할 두 가지 “장소 검색”

### A. 도시 선택 목록

- Firestore의 `geo_countries/{ISO2}`와 `geo_cities/{ISO2}_{nnn}`를 `backend/app/geo.py`가 읽는다.
- `docs/ops/GEO_REFRESH.md`에 따르면 `city_count`는 관광명소 수가 아니라 GeoNames의 도시·마을 행 수다.
- `geo.py`는 `city_count == 0`인 나라를 도시 선택 목록에서 제외한다. 코드 주석의 BV·HM·AN·CS는 무인도나 폐지 국가 코드 사례다.
- 그러므로 국가 문서의 수도 이름이 있어도 `city_count`가 0일 수 있고, 그것만으로 관광 장소 검색 오류라고 할 수 없다.

### B. 실제 추천 장소

이 저장소에는 별개의 경로가 두 개 있다.

1. **여행 조사/보고서: `POST /research`**
   - `backend/app/research`의 소스 체인을 사용한다.
   - Wikivoyage를 먼저 확인하고, 설정된 대체 소스를 차례로 조회한다. 현재 기본 순서는 Wikivoyage 국제 자료, 한국 국내 TourAPI, Wikidata 주변 장소, 설정된 경우 Google Places다.
   - 결과와 상태는 보고서에 `place_status`, `none_reason`, 소스별 `chain`의 상태·결과·개수, stale/fallback 정보 등으로 나타난다.
   - 재조회 결과가 장애 때문에 기존 정상 결과의 절반 미만이면 `keep_last_good`가 이전 결과를 보존한다. 만료 캐시도 유예 기간에 사용할 수 있다.
   - Google Places 결과는 공급자 이용정책 때문에 일반 장소 콘텐츠처럼 Firestore 캐시에 저장하지 않으며 Place ID 등 정책상 허용된 값만 별도 취급한다.

2. **일정 생성: `POST /itinerary`**
   - `backend/app/agents/itinerary.py`에서 Google Places Text Search를 직접 사용한다. API 키와 기능 설정이 필요하다.
   - 현재 검색 문구는 도시명과 장소 종류를 조합한다. 도시 좌표·국가를 명시한 검색 편향(location bias)은 이 경로에서 전달되지 않는다. Google 문서상 bias/restriction을 지정하지 않으면 IP 기반으로 결과를 편향하며, 같은 요청도 항상 같은 결과를 보장하지 않는다.
   - 응답 중 폐업, 장소 ID/이름/좌표/지도 URL 누락 등 검증에서 제외되는 항목이 있을 수 있다. 현재 코드는 제외 사유별 개수를 모두 반환하지 않는다.
   - 화면의 일정이 비어 있어도 장소 검색 결과 자체가 0건이라는 뜻은 아니다. `no_verified_places` 외에도 키 누락, 일일 제한, Gemini 키 누락, 문장 생성·검증 실패 등으로 일정이 비어질 수 있다.

즉 “도시 선택 자료가 없음”, “장소 공급자 검색 결과가 없음”, “검색 결과가 검증에서 빠짐”, “장소는 찾았지만 일정 생성이 실패함”을 구별해야 한다. Firestore의 국가별 `city_count` 하나만으로 이 네 경우를 판정할 수 없다.

## 2. 재현될 때 기록할 정보

문제가 발생한 화면에서 아래 정보를 한 묶음으로 기록하면 빈 결과가 시작된 단계를 좁힐 수 있다.

- 화면/기능과 API 경로: 도시 선택, 여행 조사(`/research`), 일정 생성(`/itinerary`) 중 무엇인지
- 입력 국가·도시 원문, 선택된 도시 식별자와 좌표, 장소 종류, 요청 시각, 배포 커밋
- HTTP 상태와 응답의 `place_status`, `none_reason`, `stale`, `fallback`, `chain`, `queries`
- 각 공급자의 원시 결과 수, 검증 통과 수, 제외 수와 사유
- 장소 응답은 있었지만 일정/보고서 생성이 실패했는지 여부

현재 화면이나 서버 로그에 없는 값은 추측해서 채우지 않는다. 로그에 API 키, 이메일 등 비밀 값이나 불필요한 개인정보를 남기지 않는다.

## 3. 장소 데이터 공급원 비교와 선택 제안

| 공급원 | 현재/가능한 역할 | 장점 | 주의점 |
|---|---|---|---|
| Wikivoyage | `/research`의 여행 가이드 기반 장소 | 여행자용 맥락과 설명 | 도시/장소별 문서 편차가 있어 모든 도시를 채우지는 못함 |
| Wikidata | `/research`의 주변 장소 대체 소스 | 구조화된 공개 데이터와 좌표 검색 | 관광 추천의 최신성·영업 여부를 보장하지 않음 |
| Google Places | 현재 `/itinerary` 직접 검색, 설정 시 `/research` 대체 소스 | 상호·종류·지도 정보가 풍부함 | 키·쿼터·비용과 저장/표시 정책 준수 필요. 검색 결과는 변동 가능 |
| TourAPI | 국내 장소 대체 소스 | 한국 관광 공공데이터에 적합 | 국내 범위 중심이며 이용 조건과 필드별 출처 표시를 확인해야 함 |
| OpenStreetMap/Overpass | 추가 조사 후보 | 공개 지도 데이터에서 직접 질의 가능 | 공개 Overpass 서버는 소규모 용도이며 과부하될 수 있어 무조건 새 대체 서버로 붙이지 말 것 |
| Foursquare Places API | 추가 비교 후보 | 별도 장소 검색 API로 교차 비교 가능 | 서비스 키·요금·데이터 이용 조건을 검토하고, 비용 승인 전 운영 연동하지 말 것 |

**제안:** 먼저 기존 두 경로에서 요청별 진단 정보를 남기고 실제 실패 사례를 재현한다. 그 후에만 공급자별 커버리지와 결과 품질을 같은 도시·종류·시각으로 비교한다. 새 유료 공급자를 먼저 추가하면 호출비와 데이터 정책이 늘고, 원래 실패 지점을 가릴 수 있다. Google은 위치 편향을 설정하지 않으면 IP 기반 편향을 사용한다고 설명한다. OpenStreetMap 문서도 공개 Overpass 서버가 과부하될 수 있다고 안내한다. Foursquare는 현재 Places API 요금표를 별도로 공지하고 있으므로 도입 전 현행 요금·약관을 재확인해야 한다.

## 4. 복구와 데이터 안전 제안

### 검색·캐시 복구

- 성공 응답, 정상적인 검색 결과 0건, 공급자 장애, 검증 후 0건, 후속 일정 생성 실패를 서로 다른 상태로 기록한다.
- 결과가 갑자기 0건 또는 큰 폭으로 줄면 기존 정상 캐시를 즉시 덮어쓰지 않는다. 원인이 확인될 때까지 이전 정상 결과를 stale 표시로 제공하고 재시도한다.
- 현재 `keep_last_good`는 장애로 기존 결과가 절반 미만이 된 경우를 다룬다. **장애 표시는 없지만 정상 응답이 갑자기 0건인 경우까지 보존하는지는 별도로 확인·보완할 항목**이다.
- 결과가 실제로 비어 있는 것이 확인됐을 때만 새 버전을 명시적으로 확정한다. 복구는 기존 결과/새 결과를 버전으로 남겨 되돌릴 수 있게 한다.

### Firestore 지리 데이터 복구

- `docs/ops/GEO_REFRESH.md`의 갱신 절차는 변경 문서 기록, 오래된 샤드 삭제, 마지막에 `geo_meta/current` 갱신을 설명한다.
- 그 문서만으로 삭제 전 전체 스냅샷이 남는지는 확인되지 않았다.
- 다음 갱신 개선안: 반영 전에 현재 manifest, 해시, 국가·도시 개수, 샤드 목록을 보관하고, 직전 버전 대비 큰 감소가 감지되면 삭제와 current 포인터 변경을 중단한다. 검토 통과 후 새 버전을 활성화하고, 이전 버전은 정한 보존 기간 동안 되돌리기 가능하게 둔다.
- 이는 운영 데이터나 쓰기 절차를 이번 조사에서 변경했다는 뜻이 아니다. 구현 전 팀장이 임계치, 보존 기간, 복구 책임자를 정해야 한다.

## 5. 다음 조치 순서

1. 실제 빈 장소 사례 1건의 입력·기능·시각·배포 버전·응답 상태를 확보한다.
2. `/research`인지 `/itinerary`인지 확인하고, 원시 검색 수 → 검증 통과 수 → 최종 화면 수를 비교한다.
3. 원인이 특정된 뒤에 검색 편향, 공급자 오류 처리, 후속 AI 생성 상태 중 필요한 부분만 수정한다.
4. 같은 입력으로 정상 표시와 실패/복구 흐름을 재현해 확인한다.
5. Firestore 지리 데이터 갱신에 대해서는 별도로 사전 스냅샷과 버전 복구 절차를 정한다.

## 검증 상태와 범위

- **코드에서 확인:** 도시 목록과 추천 장소가 별도 흐름임, `/research` 다중 소스/캐시, `/itinerary` Google Places 직접 호출, 주요 결과 상태.
- **사용자 확인:** 도쿄와 요코하마는 정상. 현재까지 재현된 0건 도시·장소 사례는 제공되지 않음.
- **확정하지 않은 것:** 실제 운영에서 0건이 발생하는 단계/원인, 모든 공급자에 공통인 실패 여부, 지리 데이터 스냅샷 복구 가능 여부.
- **변경:** 조사 문서만 작성. 애플리케이션 코드와 Firestore 운영 데이터는 수정하지 않음.
- **외부 참고:** [Google Places Text Search 위치 편향 문서](https://developers.google.com/maps/documentation/places/web-service/text-search), [OpenStreetMap Overpass API 사용 안내](https://wiki.openstreetmap.org/wiki/Overpass_API), [Foursquare Places API 검색 및 요금 안내](https://docs.foursquare.com/developer/reference/upcoming-changes). 실제 연동 전 이용 조건과 요금은 다시 확인한다.
