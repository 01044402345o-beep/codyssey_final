# 응답 지연 분석과 측정 (멘토 지적: "대화 속도로 응답이 와야 한다")

> 작성: 2026-10-11. 상태: **원인 후보를 코드로 좁혔고, 측정 도구(`timing_ms` + `measure_latency.py`)를 넣었다. 실제 배포 서버의 숫자는 아직 없다.**
> 근거 구분: **[코드]** 코드를 읽어 확정 · **[로컬 측정]** 이 저장소를 4코어 개발 환경에서 직접 돌린 값 · **[추정]** 검증 못 한 가정.

## 1. 지금 "1분"이 어디서 나올 수 있나

| 후보 | 근거 | 확인 방법 |
|---|---|---|
| **A. Render 무료 플랜 콜드스타트** | 무료 웹 서비스는 일정 시간 요청이 없으면 잠들고 첫 요청이 깨우는 시간(수십 초)을 기다린다 **[추정: Render 정책, 이 환경에서 재확인 못 함]**. 사용자 테스트는 대개 오래 쉰 서버에 첫 요청을 보낸다. | 15분 쉰 뒤 `measure_latency.py` — 첫 `/health` 시간 |
| **B. `/generate` 한 번의 모델 호출 + 재시도 꼬리** | [코드] (도시×카테고리)마다 한 번, 모든 상황을 `max_output_tokens=8192` 로 통째 생성. 검증에서 block 이 나면 **팩 전체를 다시 생성**. 서버는 호출당 **최소 30회** 시도·시도당 60초 타임아웃, 클라이언트는 90초 대기. | `timing_ms.attempt_ms` — 시도별 모델 호출 ms·검증 통과 여부 |
| **C. 가짜 대기(코드 확정)** | [코드] 보고서·방문 순서·문장 단계가 AI 와 무관하게 `500ms + 단계 수×700ms` 씩 진행: 보고서 ≈4.7초 + 방문 순서 ≈2.6초 + 문장 단계 가짜 부분 ≈3.3초 = **약 10초**. 초기 목업의 연출이 남은 것. | 코드 |
| D. 말하기 로컬 검출(VAD 2개) | **[로컬 측정]** 4코어 환경에서 디코딩 약 35ms, Silero 5~37ms, pyannote 48~104ms — 1.3초~10.6초 음성에서 서버 합계 **0.09~0.18초**. Render 무료(CPU 점유율이 훨씬 낮음)에서 수십 배 느려진다 해도 **수 초** 수준이지 1분이 아니다 **[추정]**. | `timing_ms.silero/pyannote` |
| E. 말하기 전사·피드백 | [코드] 전사 2개는 **병렬**(지연 = 느린 쪽 하나, 합이 아님). 각 최소 30회 재시도·시도당 타임아웃이 꼬리를 만든다. 피드백 모델은 한 번 더 호출. 크레딧 부족(402) 때 114초가 실제로 관측됨. | `timing_ms.stt/feedback` |

**"1분은 VAD 설계의 결과"라는 주장은 로컬 측정과 맞지 않는다**(D). "검증 실패 시 최대 3회 재시도"도 코드와 다르다 — `/generate` 는 최소 30회 시도다(B).

## 2. 측정 도구

- 서버 응답에 `timing_ms` 추가(기존 필드는 그대로, 순수 추가):
  - `/generate`: `{total, attempt_ms:[{model, call_ms, validate_ms, ok}]}` — 재시도가 지연을 만드는지 보인다.
  - `/speak-check`: `{read, decode, silero, pyannote, stt, compare, feedback, total}` — 거부 응답에도 들어간다(`stt` 는 병렬 전사 중 느린 쪽).
- `backend/scripts/measure_latency.py`: 콜드스타트(첫 /health), `/generate`·`/speak-check` 벽시계 + 서버 단계별 p50/p95/max, 원본 jsonl.

```bash
BASE_URL='여기에_Render의_실제_URL'
# 15분 이상 쉰 뒤 처음 한 번 — 첫 /health 가 콜드스타트
python3 backend/scripts/measure_latency.py --base "$BASE_URL" --n 5 --audio good.wav --target "I have a peanut allergy."
```

## 3. 이미 넣은 완화

- 앱이 열리면 **`/health` 를 한 번 불러 서버를 미리 깨운다**(사용자가 여행을 입력하는 시간에 겹침). 개인정보 없음, `?api=` 외부 서버에는 부르지 않음. 이것이 A 가 원인이라면 가장 싼 개선이다.
- 더 확실한 방법(미적용): 외부 cron(예: GitHub Actions 스케줄)으로 10분마다 `/health` 호출 — 무료 월 시간(750h) 안에서 상시 기상 가능하나 URL·운영 결정이 필요하다.

## 4. 측정 결과를 보고 정할 것

| 관찰 | 의미 | 다음 |
|---|---|---|
| 첫 /health 가 수십 초 | A 가 원인 | 미리 깨우기(적용) + 상시 기상 검토 |
| `attempt_ms` 에 실패 시도가 여럿 | B 의 재시도 꼬리 | 프롬프트·검증 규칙 조정, 상황별 분할 호출, 재시도는 백그라운드로 분리(30회 규칙은 과제 요건이면 유지) |
| 성공 시도 1회인데 `call_ms` 가 20초+ | 모델 호출 자체가 김 | 상황별 병렬 분할·작은 모델·부분 결과 먼저 표시 |
| `stt` 가 대부분 | 전사 지연 | 재시도 정책·스트리밍 전사 검토(별도 설계) |
| `silero+pyannote` 가 수 초 | 로컬 검출 비용(Render CPU) | 그때 검출기 하나로 줄이는 안 검토 |

## 5. 한계

- 위 [로컬 측정]은 4코어 개발 환경이라 Render 무료 플랜 숫자가 아니다. 키 없는 서버라 모델·전사 시간은 포함되지 않는다.
- **실제 배포 서버 측정은 사용자가 해야 한다**(이 환경은 외부 네트워크가 막혀 있다).
- 연속(실시간) 어순 피드백은 별도 설계가 필요하다 — 스트리밍 전사, 어순 비교를 코드로 하는 방식 등은 이 문서의 범위 밖.
