# 침투 가정 · 통제권 유지 (assume breach)

작성 2026-11-07. 이 문서는 "언젠가 뚫린다"를 전제로, **무엇을 잃고 무엇을 되찾을 수 있는지**를 미리 정해 둔다.
제로 트러스트의 핵심은 '못 뚫리게'가 아니라 **뚫려도 통제권을 잃지 않는 것**이다.

## 1. 영가설(null hypothesis)을 어떻게 세우나

"우리는 뚫렸다"를 영가설로 두고, **반증 가능한 형태**로 적는다. 막연한 '아마 안전하다'는 검증할 수 없다.

| 영가설 | 반증하는 관측 | 지금 상태 |
|---|---|---|
| H1. 공격자가 토큰 하나를 얻었다 | 토큰만으로 파괴적 작업이 되면 채택 | **부분 완화** — `/account/erase` 는 `auth_time` 기반 최근 로그인 검사를 통과해야 하며, 오래된 토큰은 `recent_login_required`로 거부된다 |
| H2. 공격자가 서버 환경변수를 읽었다 | 서명·봉인 키가 같은 프로세스에 있으면 채택 | **채택** — 한 프로세스가 서명키·봉인키·토큰을 모두 갖는다. 앱 계층 분리 없음 |
| H3. 공격자가 증거 저장소를 지웠다 | 오프사이트 사본이 없으면 채택 | **부분 완화** — GitHub 관리 plane 앵커가 Render·Firebase 자산·체인 위치를 기록한다. 앵커가 켜져 있지 않으면 여전히 채택 |
| H4. 공격자가 배포 권한을 얻었다 | 브랜치 보호가 없으면 채택 | **채택** — `main` 보호 없음, 자동 배포 |
| H5. 공격자가 관리자 콘솔 계정을 얻었다 | MFA 가 없으면 채택 | 미확인 — Firebase 콘솔 MFA 설정은 저장소에 없다 |

**H1·H2·H3·H4 가 채택된 상태**다. 즉 "뚫리면 통제권을 잃는다"가 현재 사실이다. 이걸 코드로 다 막을 수는 없으므로, 아래 3층으로 나눈다.

## 2. 3층 방어 — 격리 / 탐지 / 복구

| 층 | 목표 | 지금 있는 것 | 비어 있는 것 |
|---|---|---|---|
| **격리** | 하나가 새도 옆으로 안 번진다 | 역할별 키 분리(`keycheck` 가 재사용을 잡는다), 토큰 uid 로만 데이터 접근 | 앱 계층 분리 없음(한 프로세스가 전부), 관리자 토큰이 정적 |
| **탐지** | 새는 중임을 안다 | 증거 체인 + 영수증 서명(위조 감지), GitHub 관리 plane 오프사이트 앵커 | `EVIDENCE_AUTO_ANCHOR=on`과 GitHub Issues 기록이 꺼져 있으면 탐지 공백 |
| **복구** | 되찾을 수 있다 | 탈퇴 영수증(사용자 손에 남는 증거), 계정 칸 분리 | 비상 경로(break-glass) 문서·절차 없음 |

## 3. 비상 경로 (break-glass)

**원칙: 비상 경로는 평상 경로와 다른 신뢰 영역에 있어야 한다.** 같은 곳에 두면 같이 잃는다.

| 자산 | 평상 경로 | 비상 경로 | 준비 상태 |
|---|---|---|---|
| 소스 코드 | GitHub `main` | 로컬 작업 사본 + 패치 파일 | 있음(패치 배포) |
| 서버 설정 | Render 대시보드 | `render.yaml` (37개 `sync:false` 키 제외) | 부분 — 값은 대시보드에만 |
| 증거 무결성 | Firestore 체인 | **없음** | **비어 있음. 최우선** |
| 서명키 | Render env | 오프라인 봉인 사본 | 비어 있음 |
| 판정 근거 | 이 저장소 | 사용자가 내려받은 영수증 파일 | 있음(Ed25519 서명) |

### 즉시 할 수 있는 오프사이트 앵커 (코드 변경 없이)
1. 매일 `/health` 의 `evidence.key_id`·`fingerprint`·`generation` 을 **저장소 밖**에 기록한다(개인 노트·메일).
2. 관리자 CLI 로 `verify-chain` 을 돌려 나온 마지막 `seq`·`digest` 도 같은 곳에 남긴다.
3. 사고 시 이 기록과 서버 상태를 비교한다. **서버 체인이 이 기록보다 짧으면 삭제된 것이다.**
   오프사이트 기록이 없으면 "짧아 보인다"고 말할 근거조차 없다.

## 4. 키를 '갈고 또 가는' 것에 대한 판단

**하지 않는다.** 이유:

- 안전성은 길이가 아니라 **엔트로피**다. CSPRNG 32바이트는 2^256 이고, 같은 값을 46번 이어 붙여도 엔트로피는 늘지 않는다.
- 키를 다시 암호화하면 **새 키가 하나 더 생긴다.** 그 새 키를 어디 둘지가 다시 문제다. 키 관리 지점만 늘어난다.
- 여러 번 겹쳐 암호화(cascade)는 표준 구성이 아니고, 검증된 이득이 없다. 구현 실수 위험만 커진다.
- 대신 **회전**을 한다. 회전은 실제로 공격자의 시간을 끊는다: 옛 키로 서명한 영수증은 유효하되 새 작업은 못 한다.
  그래서 `EVIDENCE_SIGN_KEYS_OLD` 로 옛 공개키 이력을 남기고 `verify_any()` 가 골라 쓴다
  (회전 후 옛 영수증을 '위조'라고 답하면 그 기능이 거짓말을 한다).

**키를 강하게 만드는 실제 수단**: CSPRNG 32바이트, 역할별 분리, 회전 이력, 그리고 **점검**(`python -m app.keycheck`).

## 5. 오프사이트 앵커 판정

`evidence-anchor`가 켜져 있으면 6시간마다 GitHub 관리 plane에 Render `/health`의 `deploy.commit`과 증거 지문, Firebase Hosting `/`, `/index.html`, `ai.js`, `auth.js`, `app.js`의 SHA-256·ETag·CSP 모드·캐시 정책을 기록한다. `ai.js`의 Hosting origin guard가 사라지거나 Hosting CSP가 Report-Only로 돌아가거나 루트가 한 시간 이상 캐시되면 앵커가 실패해야 한다.

서버의 체인 `seq`가 마지막 오프사이트 기록보다 작으면 삭제 또는 롤백의 증거다. 기록이 없으면 어떤 판정도 할 수 없다. Firebase Hosting과 Render가 서로 다른 커밋을 보고하면 배포를 정상으로 간주하지 않는다.
