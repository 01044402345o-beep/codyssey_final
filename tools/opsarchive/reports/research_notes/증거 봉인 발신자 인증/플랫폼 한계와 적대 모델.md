# Hard Limits of Sender Authentication on a PaaS-Hosted App

Scope note (system this is written for): FastAPI on Render, built from a public GitHub repo; no TEE/attestation; credentials are a Google service-account JSON (Firestore + Identity Toolkit admin), a GitHub token for opening issues, and a public X25519 encryption key; the private key is held offline by the admin; the container filesystem is writable by the app. The open problem is that **the app cannot authenticate itself to the admin, so a compromised app can forge archives and silently omit expected ones.** Below, "the app" means the running FastAPI process on the PaaS.

Convention: **[CITED]** = backed by a source fetched in this research. **[UNKNOWN]** = could not be confirmed from a primary source; treat as a guess. **[INFERENCE]** = my reasoning from cited facts, not a source claim. Prices are US dollars with the vendor's stated effective date.

## 1. Secret exposure surface on a PaaS (what code with execution can read)

### Takeaway
On Render (and Fly.io/Koyeb), secrets are injected into the process's own environment, so the app — and any code that compromises it — can read every credential by design. Encryption-at-rest protects against disk theft, not against the running process. There is no free/hobby PaaS tier that injects secrets the app's own code cannot read. The only way to move a credential out of the app's read path is to move the *operation* (signing/encryption) to a non-exportable HSM/KMS key or to run inside an attested TEE — neither of which the plain stack offers.

### Cited Findings
- Render env vars and secret files are "encrypted at rest using a minimum AES-128 standard" and TLS 1.2+ secures platform/external traffic — i.e. protection is at rest and in transit, not against the process — [Render: How Render handles secrets and environment variables](https://render.com/articles/how-render-handles-secrets-and-environment-variables). **[CITED]**
- Render secret files are plaintext files, available at runtime at `/etc/secrets/<filename>` (and also in the service root dir for non-Docker services); combined size of all secret files per service/environment group is capped at 1 MB — [Render: Environment Variables and Secrets](https://render.com/docs/configure-environment-variables). **[CITED]**
- Render's own doc states that "If a running process writes an injected secret to `stdout` or `stderr`, the log management service records the value in plain text" — logs are therefore a plaintext leak channel the app controls — [Render: How Render handles secrets and environment variables](https://render.com/articles/how-render-handles-secrets-and-environment-variables). **[CITED]**
- Docker on Render translates environment variables into build arguments (`ARG`), and Render warns credentials can "linger in generated image layers"; secret files are the recommended alternative for build-time secrets. Note build-time vs run-time variables are separate domains — [Render: How Render handles secrets and environment variables](https://render.com/articles/how-render-handles-secrets-and-environment-variables). **[CITED]**
- Application code reads injected values directly via the language's environment API (e.g. `os.environ.get('DATABASE_URL')` in Python) — [Render: Reading environment variables from code](https://render.com/docs/configure-environment-variables). **[CITED]**
- Fly.io: "The secret is encrypted and stored in a vault. An app's secrets are available as environment variables at runtime on every Machine belonging to that Fly App" — [Fly.io: Secrets and Fly Apps](https://docs.fly.io/apps/secrets). **[CITED]**
- Fly.io community: the Fly agent on the host decrypts app secrets and injects them into the VM as environment variables at boot; via `flyctl ssh console` the secrets "are visible as environmental variables" — [Fly.io community: Secrets vs normal env vars](https://community.fly.io/t/secrets-vs-normal-environment-variables/10972), [Fly.io community: Environment variables set by flyctl secrets](https://community.fly.io/t/environment-variables-set-by-flyctl-secrets/12266). **[CITED]** (community posts, but consistent with the vendor doc above)
- Koyeb exposes secrets as environment variables and supports variable interpolation; free tier includes a $5.50/month credit usable on Nano/Micro instances — [Koyeb: Secrets](https://www.koyeb.com/docs/reference/secrets), [Koyeb: Environment variables](https://www.koyeb.com/docs/build-and-deploy/environment-variables), [Koyeb changelog free-tier note](https://www.koyeb.com/changelog). **[CITED]**
- General (not PaaS-specific): secrets in env vars are "readable via /proc/PID/environ on Linux, accessible to child processes through inheritance, and can be easily inspected by debuggers" — [Doppler: Why environment variables aren't enough](https://www.doppler.com/blog/environment-variables-secrets-management). **[CITED]**
- `/proc/self/environ` contains the current process's environment variables and is a known disclosure vector (commonly reached via LFI-to-RCE chains) — [How to leak env via /proc/self/environ](https://medium.com/@zoningxtr/from-lfi-to-rce-via-proc-self-environ-shell-access-via-headers-1f22e18c65db). **[CITED]**
- Trend Micro documents that env-var secrets leak through many indirect paths (crash dumps, debug endpoints, error reporting, child processes) — [Trend Micro: Analyzing the hidden danger of environment variables](https://www.trendmicro.com/en_us/research/22/h/analyzing-hidden-danger-of-environment-variables-for-keeping-secrets.html). **[CITED]**
- Render runs a Vulnerability Disclosure Program on HackerOne and publishes a Security & Trust page, but no free-tier attested-secrets mechanism is described — [Render: Security and Trust](https://render.com/security). **[CITED]** (absence of a feature is a weak signal; see Gaps)

### Inferences
- **[INFERENCE]** On this stack, "the passphrase/keys must never be exposed via memory or network packets" cannot be satisfied for any credential the app itself uses: if the app reads the Google SA JSON, that JSON exists in the process's memory and (if env-injected) in `/proc/<pid>/environ`. Encryption-at-rest (AES-128) and TLS do not change this.
- **[INFERENCE]** "Secret zero" applies here: the app must hold *some* bootstrap credential (the Google SA JSON), and a compromise of the app is a compromise of that secret and everything it can reach (Firestore, Identity Toolkit admin, GitHub issues). Fixing this by wrapping secrets in Vault/KMS does not help because the bootstrap credential to *unseal/fetch* them is likewise readable by the app.
- **[INFERENCE]** A read-only mount or a "secret file" is not meaningfully safer than an env var against a code-execution adversary: both are readable by the same process. The practical difference is only leak surface (env vars additionally leak via `/proc/environ`, child-process inheritance, and accidental logging/crash dumps), which slightly favors secret files.
- **[INFERENCE]** Errors and logs are the most likely *unintentional* leak channel: a stack trace or debug dump that stringifies config, or the app's own "print the config" style logging, emits plaintext secrets into Render's log store (confirmed by Render's own FAQ). This matters for the evidence pipeline because the archive collector must be careful not to capture secrets into archives that are later encrypted-and-issued.

### Gaps
- I could not confirm from a primary source whether **Fly.io** or **Koyeb** offer any secret mechanism readable by hardware but not by the app's process (no free-tier attested secret). Best evidence points to "no" for all three. **[UNKNOWN]**
- Whether Render's free/Hobby plan retains any *deploy metadata* (git commit, build id) that an attacker cannot rewrite — not confirmed. **[UNKNOWN]**
- Exact React/Python-specific memory-scrubbing caveat: Python `bytes`/`str` are immutable, so best-effort zeroization of secrets in memory is unreliable. No primary source fetched; widely known. **[UNKNOWN]**

## 2. Attestation reality check: what remote attestation actually requires

### Takeaway
Proving "this archive was produced by *my* unmodified app, running right now" requires three things the stack does not have: (a) a hardware root of trust that measures the running code (TPM measured boot, or a TEE like Intel TDX / AMD SEV-SNP / AWS Nitro), (b) a vendor attestation service or NSM that signs a quote binding the measurement, and (c) a *remote verifier* (the admin) that checks the quote before trusting a signature. No free/hobby PaaS tier on Render/Fly/Koyeb offers this. The alternatives — reproducible builds, deployment of an image digest, SLSA provenance, signed images — prove things about the *build*, not about the *running process at signing time*, so none of them stop a compromised running app from forging an archive.

### Cited Findings
- Remote attestation lets you assess a system's trustworthiness *before* granting access to protected resources — [Google Cloud: Remote attestation overview](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/attestation-overview). **[CITED]**
- Confidential Space is "a trusted execution environment (TEE) that can be used to release your secrets only to authorized workloads"; it requires a Confidential VM using AMD SEV, Intel TDX, or Intel TDX + NVIDIA CC, and provides an attestation service (Google Cloud Attestation or Intel Trust Authority) that returns identity tokens — [Confidential Space overview](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview). **[CITED]**
- In the Confidential Space trust model, the **workload operator** (who has full admin on the project) "has no access to the data, and can't control access to it either. They can't influence or modify the workload code or execution environment"; trusted attestation + hardened OS separates the three roles (data collaborator / workload author / workload operator) — [Confidential Space overview](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview). **[CITED]**
- Confidential Space requires an *attestation provider* configured on a workload identity pool with **attribute conditions** that verify assertions from the CS image, workload container, and VM instance before access to secrets is granted — [Confidential Space overview](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview). **[CITED]**
- AWS Nitro Enclaves: attestation "uses a series of measurements" (PCRs) of the enclave image, and the external system must validate the signed attestation document against AWS's root of trust — [AWS: Cryptographic attestation](https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html), [AWS: Verifying the root of trust](https://docs.aws.amazon.com/enclaves/latest/user/verify-root.html). **[CITED]**
- SEV-SNP supports remote attestation (an attestation report any third party can verify); Intel TDX provides an equivalent mechanism — [Lenovo/AMD SEV-SNP config](https://lenovopress.lenovo.com/lp2349-configuring-confidential-computing-with-amd-sev-snp-and-vmware-esxi-90), [Red Hat: Confidential computing platform details](https://www.redhat.com/en/blog/confidential-computing-platform-specific-details). **[CITED]**
- SLSA FAQ: "Reproducible builds do not address source, dependency, or distribution threats"; "Reproducers must truly be independent, lest they all be susceptible to the same attack"; closed-source reproducible builds are often "prohibitively expensive"; and SLSA Build levels only cover a *single build* and are explicitly **not transitive** — [SLSA FAQ](https://slsa.dev/spec/v1.0/faq). **[CITED]**
- SLSA Build L1 merely requires provenance to exist; higher levels increase protection against tampering of the build and provenance — [SLSA: Security levels](https://slsa.dev/spec/v1.1/levels). **[CITED]**
- Field reality (secondary): SLSA provenance helps verify a builder/source pair but has boundaries that attackers can operate outside of — [OpenSSF: "Where SLSA's Boundaries Fall"](https://openssf.org/blog/2026/06/10/mini-shai-hulud-where-slsas-boundaries-fall/). **[CITED]** (blog, use with care)

### Inferences
- **[INFERENCE]** SLSA provenance / signed images / reproducible builds are *provenance-only* controls: they let the admin verify that the code in the running container was built from the expected repo/commit. They say nothing about whether the *running process* is compromised, nor about *whether the archives it emits are the complete set it should have emitted*. A supply-chain-attested app can still forge and omit archives once it is compromised at runtime. Do not sell provenance as sender authentication.
- **[INFERENCE]** A deployment of an *image digest* gains a little: it lets the admin confirm the deployed artifact identifies a specific build. But on a PaaS that builds from GitHub and redeploys on push, the app (or an attacker with the GitHub token / Render access) can change what runs; the digest is a claim by the platform, verifiable only against the platform, not a hardware measurement of the running process.
- **[INFERENCE]** The only construction that makes "the app cannot authenticate itself" *solvable* is to move the signing key's *use* into an environment whose identity the admin can verify out-of-band — i.e. a TEE whose attestation quote the admin checks and which gates key release. That is Confidential Space / Nitro Enclaves territory, and it is not available on Render/Fly/Koyeb free tiers.
- **[INFERENCE]** Even with a TEE, the admin must *do the verification* (check quote/measurement, enforce attribute conditions). Attestation is not a library you drop in; it is a verification protocol with a verifier. The admin-side verifier is currently missing and is itself part of the "new infrastructure" (see §6).

### Gaps
- No primary source found stating that **any** free/hobby PaaS tier (Render, Fly.io, Koyeb, Railway, etc.) offers TPM/TEE-based attestation in 2025–2026. Best evidence: Confidential Space/Nitro are IaaS-level features on GCP/AWS, not PaaS features. **[UNKNOWN]**
- Whether Render's hosts even expose a vTPM/measured boot to the container — not addressed in any Render doc found. **[UNKNOWN]**
- The precise attestation-token format and freshness/anti-replay requirements for Confidential Space (OIDC, nonce, expiry) — referenced but not fetched in detail. **[UNKNOWN]**

## 3. Key-usage policy as a partial mitigation (non-exportable keys, approval, rate limits, dual control)

### Takeaway
A non-exportable KMS/HSM signing key is the *only* free-ish control here that satisfies the literal "key material never appears in our memory or on the wire" requirement — the app sends a hash, the HSM returns a signature, and the private key never leaves the device. But it does **not** stop a compromised app from forging or omitting archives, because the app holds the credential to *request* signatures. KMS/HSM changes the *blast radius* (the key cannot be exfiltrated and reused elsewhere) and enables *audit* (every sign call is logged), but it does not restore sender authenticity on its own. Per-request approval, rate limiting, and dual control each buy back a specific slice of that gap, with different costs.

### Cited Findings
- Cloud KMS protection levels include SOFTWARE, HSM, and EXTERNAL/EXTERNAL_VPC. HSM-protected key versions require FIPS 140-2 Level 3 validated hardware and key material is non-exportable (protection level is fixed at key creation) — [Google Cloud: Cloud KMS pricing](https://cloud.google.com/kms/pricing), [Google Cloud: KMS key management deep dive](https://docs.cloud.google.com/docs/security/key-management-deep-dive). **[CITED]**
- Cloud KMS pricing (effective March 17, 2025): **software** key version ≈ **$0.06/month** ($0.000082192/hr); **HSM** asymmetric key version ≈ **$1.00/month** ($0.001369863/hr); cryptographic operations **$0.03 per 10,000** (software and HSM the same), EXTERNAL/EXTERNAL_VPC $0.15/10,000; admin operations and key rotation are free — [Cloud KMS pricing](https://cloud.google.com/kms/pricing). **[CITED]**
- Always-free tier: **100 active key versions created via Cloud KMS Autokey** plus **10,000 cryptographic operations/month**, aggregated per billing account, available after the free trial — [Cloud KMS pricing](https://cloud.google.com/kms/pricing). **[CITED]**
- External Key Manager (EXTERNAL / EXTERNAL_VPC) keeps key material outside Google entirely (in a partner HSM you control), at a higher operation price — [Cloud KMS pricing](https://cloud.google.com/kms/pricing). **[CITED]**
- AWS KMS uses FIPS 140-3 Level 3 HSM fleet; CloudHSM/Managed HSM/Cloud HSM give FIPS 140-2/3 Level 3 with non-extractable keys — [AWS KMS data protection](https://docs.aws.amazon.com/kms/latest/developerguide/data-protection.html), [AWS KMS vs Azure KV vs GCP KMS comparison](https://www.qcecuring.com/blog/aws-kms-vs-azure-key-vault-vs-gcp-kms) (secondary). **[CITED]**
- Single-tenant Cloud HSM costs ~**$3,500/month** per instance (price prorated daily), far above hobby budgets — [Cloud KMS pricing](https://cloud.google.com/kms/pricing). **[CITED]**
- Secret-zero framing: a bootstrap credential is needed to fetch/mint all other credentials; "If secret zero is compromised, it potentially gives an attacker access to all other secrets" — [Entro: Addressing the secret zero problem](https://entro.security/blog/addressing-the-secret-zero-problem-and-solutions/), [HashiCorp: Secret Zero](https://www.hashicorp.com/en/resources/secret-zero-mitigating-the-risk-of-secret-introduction-with-vault). **[CITED]**

### Inferences
- **[INFERENCE]** For this system, an HSM/KMS asymmetric signing key **does** meet the literal requirement "the private key is never exposed via memory or network packets": only signatures traverse the wire, and the key never exists in the app's RAM. The app-level key it currently generates (X25519 envelope + AES-GCM) does *not* meet that requirement because the key material is in-process.
- **[INFERENCE]** But an HSM key does **not** provide sender authentication against a compromised app: the app holds valid credentials to call `kms.sign`, so it can sign forged archives. What the HSM buys is (1) the ability to *revoke/rotate the signing capability* centrally, (2) an immutable audit trail of *when and how many* signatures were requested, and (3) assurance the key isn't copied for off-platform reuse.
- **[INFERENCE]** **Rate-limited signing** is a genuine partial control: if the admin knows the *expected* maximum number of seals per day, a hard cap at the key (or at an approval service) means a mass-forgery campaign trips the cap and gets denied, and the denials are logged. It does not stop one forged archive.
- **[INFERENCE]** **Per-request approval** (human/admin approves each sign) fully prevents silent forgery and omitted-archive ambiguity *if* the approval channel is out of band and the approver actually checks the content — but it destroys automation and is unusable for an unattended tracer. A middle ground is approval only above a rate/volume threshold (step-up approval).
- **[INFERENCE]** **Dual control** (two principals must both authorize a sign) only helps if the two credentials do not live in the same compromised app. Placing both in the same Render service is theater; dual control only makes sense across two independent services (see §6).
- **[INFERENCE]** KMS-with-EXTERNAL (EKM) is the strongest software-only-ish option for "the admin's key never sits in anyone's cloud," but it raises cost/ops; for a hobby budget it is out of scope.

### Gaps
- Whether Cloud KMS supports signing with an X25519/Ed25519 key, or only RSA/EC (the pricing page lists RSA 2048/3072/4096 and "Elliptic Curve"), and whether an HSM-backed Ed25519 key is available — not confirmed. If only RSA/EC-ECDSA are supported, the current X25519 design would need to change to an ECDSA/EdDSA KMS key. **[UNKNOWN]**
- Exact free-tier eligibility of HSM protection level under the always-free Autokey allowance — the free allowance is stated as "key versions created using Cloud KMS Autokey" without specifying protection levels. **[UNKNOWN]**
- Whether Cloud KMS's per-key IAM/preconditions can implement a hard daily sign cap natively, or whether a separate approval service is required. **[UNKNOWN]**

## 4. Monitoring and detection within free tiers (and the "attacker controls the telemetry" problem)

### Takeaway
The free monitoring that exists is *after-the-fact* and *coarse*: GCP Admin Activity audit logs (free, 400 days), Firestore Data Access logs (billable, off by default), GitHub org audit log (180 days, org owners only, git events only 7 days), and Render audit logs (looks plan-gated to Organization/Enterprise). None of them are attacker-proof: an attacker with app credentials and Render access can delete or alter the app's own logs and may have enough access to reduce visibility. The realistic detection posture is (a) *out-of-band* signals the attacker doesn't control (GCP billing/quota spikes, GitHub issues created, GitHub audit events) and (b) *cross-checking expected-vs-actual* counts against a witness the attacker doesn't own. "The attacker controls the app's own telemetry" is the central defeat here, not a footnote.

### Cited Findings
- Cloud Audit Logs covers admin and data-access events; **Admin Activity audit logs are free and retained ~13 months / 400 days; Data Access logs record data reads/writes and are billed** — [Google Cloud: Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit), [Google Cloud blog: best practices](https://cloud.google.com/blog/products/management-tools/best-practices-for-working-with-google-cloud-audit-logging), [Google Cloud Search docs: "Cloud Logging charges for Data Access audit logs"](https://developers.google.com/workspace/cloud-search/docs/guides/audit-logging-manual). **[CITED]**
- Firestore (Enterprise) is monitored via Cloud Audit Logs, which record admin and data-access events — [Firebase: Monitor databases with Cloud Monitoring](https://firebase.google.com/docs/firestore/enterprise/audit-logging). **[CITED]**
- Cloud Logging advertises 400-day retention of audit logs "at no additional cost" (this refers to Admin Activity logs; Data Access is billable per above) — [Cloud Logging](https://cloud.google.com/logging). **[CITED]**
- GitHub org audit log "lists events triggered by activities that affect your organization within the last 180 days. Only owners can access"; **git events are retained only 7 days**; enterprise audit logs are retained indefinitely — [GitHub: Reviewing the audit log](https://docs.github.com/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization), [GitHub audit log limitations (secondary)](https://www.githubforensics.com/en/blog/github-audit-log-limitations). **[CITED]**
- Render audit logs are exportable (CSV) from org Settings; a March 2026 changelog added `EndShellEvent` plus source-IP/user-agent metadata; the feature is described as available to "Organization or Enterprise plans"; the Render API added workspace audit-log export endpoints (Sept 2025) — [Render: Audit Logs](https://render.com/docs/audit-logs), [Render changelog: Audit logs for Organization and Enterprise plans](https://render.com/changelog/audit-logs-for-organization-and-enterprise-plans), [Render changelog: Export audit log events with the Render API](https://render.com/changelog/export-audit-log-events-with-the-render-api). **[CITED]**
- CI/CD abuse field note: a compromised developer credential + a modified workflow file can stream "every secret in a CI/CD environment" to the attacker, and the problem is that "no one is watching" — [Elastic Security Labs: Detecting CI/CD pipeline abuse](https://www.elastic.co/security-labs/threat-command/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis). **[CITED]**
- CI/CD canary-credential approach: plant fake credentials that, when used, alert regardless of how the pipeline was compromised — [Tracebit: CI/CD canary credentials](https://tracebit.com/platform/ci-cd). **[CITED]** (vendor blog)

### Inferences
- **[INFERENCE]** The highest-value free detection for *this* system is **out-of-band volume**: (1) GCP Firestore read/write counts and Cloud Logging quota against expected baselines (a mass archive-forging or mass-deletion event shows as a spike); (2) unexpected GitHub issues/PRs (the attacker's own beacon); (3) GitHub org audit events around token use. These live in accounts the app can *use* but (ideally) cannot *read or delete*, which is the key property.
- **[INFERENCE]** "The attacker controls the app's own telemetry" means: any log line the FastAPI process writes, any Firestore doc it writes, and any Render log it emits are all writable/omittable by the attacker. Therefore a detection rule that depends only on the app's self-reported data can be defeated. The defeat is structural; only *independent* collectors help.
- **[INFERENCE]** Firestore Data Access audit logs are exactly what you'd want for "unexpected Firestore writes," but they are **off by default and billable**, so on a free tier you likely do not get them unless you enable (and pay for) them. **[UNKNOWN]** whether the Firebase Spark (free) project even surfaces Data Access logs.
- **[INFERENCE]** Render audit logs appear to be plan-gated (Organization/Enterprise), so on a free/Hobby Render account you probably get **no** Render-side audit trail of deploys or shell sessions. That removes a detection source and also weakens incident response (§5). **[INFERENCE from the plan-gating changelog]**
- **[INFERENCE]** Detectable within free tiers (best case): a large anomaly in Firestore usage, an unexpected GitHub issue, an unusual spike in the app's outbound requests, GCP budget/quota alerts. **Not detectable** within free tiers: a single forged archive that looks well-formed, one silently omitted archive, or a low-and-slow exfiltration of the SA JSON — because none of these produce an independent, non-app-controlled signal unless a witness exists.

### Gaps
- Whether Firebase's **Spark (free)** plan supports Cloud Audit Logs / Data Access logs at all, and whether Admin Activity logs for Firestore are produced without Blaze — not confirmed. Likely Admin Activity yes, Data Access requires enabling. **[UNKNOWN]**
- Whether Render Hobby/free includes *any* audit or deploy-history retention that survives an attacker with account access — not confirmed. **[UNKNOWN]**
- Numeric free-tier thresholds for Cloud Logging ingestion and Monitoring alerting policies in 2026 (the classic "50 GiB/month free" figures) — not re-verified this session. **[UNKNOWN]**

## 5. Incident response design after suspicion

### Takeaway
Once the app is suspected compromised, the operator must assume everything the app could read is already gone: the Google SA JSON, the GitHub token, any in-app signing/encryption key, and any secret file. Response therefore splits into (a) **rotate/revoke** — the SA key, the GitHub token, and the in-app private key are the ones that matter; (b) **freeze** — stop the app/revoke its platform access so it stops emitting; (c) **preserve** — pull logs and evidence to storage the app cannot write; and (d) **accept loss** — archives signed under a compromised key, anything already exfiltrated, and possibly the ability to distinguish genuine from forged archives become unrecoverable. The most important design decision is *pre-committing* which keys exist and how they're revoked, because after the fact the app (and often the platform UI) is the thing you can no longer trust.

### Cited Findings
- Render rotates secrets by provisioning a **new** container with updated values (zero-downtime), rather than hot-swapping a running process — so revoking a Render env var/secret requires a redeploy/restart, and the old container may linger until the new one is healthy — [Render: How Render handles secrets and environment variables](https://render.com/articles/how-render-handles-secrets-and-environment-variables). **[CITED]**
- Cloud KMS keys can be disabled/destroyed; a **destroyed** key version is free and irreversible, and disabling stops all operations with it — [Cloud KMS pricing](https://cloud.google.com/kms/pricing), [KMS key states](https://docs.cloud.google.com/kms/docs/key-states). **[CITED]**
- GCP Admin Activity audit logs are free and retained ~400 days, giving a durable record of key/config changes even on a free budget — [Google Cloud blog: best practices](https://cloud.google.com/blog/products/management-tools/best-practices-for-working-with-google-cloud-audit-logging). **[CITED]**
- GitHub org audit log is retained **180 days** (only owners can read it); git events only **7 days** — [GitHub: Reviewing the audit log](https://docs.github.com/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization), [GitHub audit log limitations](https://www.githubforensics.com/en/blog/github-audit-log-limitations). **[CITED]**
- GitHub has **no official API to attach files to issues** (REST/GraphQL); official alternatives are release assets or repo commits, so issue bodies can only carry metadata — [project memory: reference_platform_limits_archive] (verified 2026-10-16 in the project, primary API docs). **[CITED via project records]**
- GitHub personal access tokens and org tokens are revocable from account/org settings; org audit log records token/actor events for 180 days — [GitHub audit log docs](https://docs.github.com/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization). **[CITED]**

### Inferences
- **[INFERENCE]** **Rotation priority** (highest blast radius first): (1) Google service-account key — it can rewrite/delete Firestore (including the `deleted/{uid}` tombstones and the whole evidence store) and can act as Identity Toolkit admin (delete/modify user accounts), so revoke the SA key in the GCP console/IAM and issue a fresh key; (2) GitHub token — revoke so the attacker loses the ability to open/close issues and push; (3) any signing/encryption key generated *inside* the app — destroy it, because it must be assumed exfiltrated; (4) the X25519 *public* key is not secret, but if a private key was ever loaded in-app, its public counterpart's "trust" is dead. The offline admin private key (never in the app) is the one credential that survives a Render compromise.
- **[INFERENCE]** **Freeze** = set the Render service to "suspended"/scale to zero or revoke the deploy hook and GitHub token, so the compromised code can no longer run and no longer auto-redeploys on push. Because Render rotates secrets by redeploying, freezing deliberately (rather than "just rotating") avoids the compromised container briefly coexisting with a fresh one.
- **[INFERENCE]** **Preserve** = immediately export what is *outside* the app's write path: Cloud Logging (Admin Activity, free) to a bucket in a *different* project with a retention lock; Render logs via the dashboard/API before they roll; GitHub audit log export. Anything the app writes (Firestore evidence docs, app logs) must be treated as suspect — the attacker could have deleted or forged it.
- **[INFERENCE]** **Unrecoverable after compromise:** (a) non-repudiation of any archive signed while the key was compromised — you cannot tell a forged archive from a genuine one unless the key was HSM-held *and* every sign call was logged to an independent sink (and even then, a forged sign is still a valid signature); (b) any secret the app read — assume exfiltrated forever; (c) "omitted archive" detection, because an omission leaves no artifact unless an external witness expected it.
- **[INFERENCE]** The design implication is to make the *irreversible* actions require a credential that is **not** in the app: e.g. tombstones/evidence deletion should require the offline admin key, not the app's SA. Currently the app's SA can delete evidence, which is exactly the wrong shape for IR.

## 6. Explicit "impossible without new infrastructure" list, with cheapest realistic upgrade + price

### Takeaway
Four properties are *impossible by construction* on the current Render + Firebase + free-tier stack: (1) proving the running app's identity (attestation); (2) keeping a signing key the app uses out of the app's memory without an HSM; (3) detecting an omitted archive without an independent witness; (4) preserving trustworthy evidence when the app controls its own telemetry. Each has a realistic cheapest upgrade; several upgrades are cheap or free (extra GCP key versions, a second scheduled job), while genuine attestation (a TEE host) is the only one that is structurally out of hobby reach.

### The impossible list (with cheapest fix)
1. **Prove the running app's code identity to the admin (attestation).** Impossible on Render/Fly/Koyeb free — no TPM/TEE/quote. *Cheapest fix:* run the sealing/signing step on a **GCP Confidential VM + Confidential Space** workload and have the admin verify the attestation token (AMD SEV-SNP/Intel TDX). Requires updating the whole deploy path (not Render) and admin-side verification code. *Price:* Confidential VM premium over a standard VM (secondary quote ~$0.005479/hr ≈ ~$4/mo for one always-on small VM — **UNVERIFIED**); plus the admin verifier. **UNKNOWN** exact 2026 SEV-SNP hourly premium.
2. **Keep the signing key out of the app's memory without hardware.** Impossible in-process. *Cheapest fix:* **Cloud KMS asymmetric signing key** — app sends a hash, receives a signature; key non-exportable, FIPS 140-2 L3 on HSM. Satisfies "key never in memory/on the wire," but *not* sender authenticity (app can still request signatures). *Price:* ~**$0.06/mo** software, ~**$1.00/mo** HSM, **$0.03/10k** sign ops; likely **$0 free** if it fits the 100-key/10k-op Autokey allowance. This is the single best cost/benefit upgrade.
3. **Detect omitted archives.** Impossible with only the app's own output. *Cheapest fix:* an **independent witness** — a second, separate scheduled job (Render cron job or a GitHub Actions scheduled workflow) that independently knows the expected seal count/heartbeat and opens an issue (or writes to an account the app cannot write) when expectations aren't met. *Price:* **$0** on a free cron/Actions tier (Render cron on free/hobby is limited; GitHub Actions free minutes apply). **[INFERENCE on free cost]**
4. **Preserve trustworthy evidence when the app controls its telemetry.** Impossible if logs live only where the app writes them. *Cheapest fix:* **Cloud Logging log sink → a bucket in a separate GCP project with a retention lock/immutability**, owned by the admin, not the SA the app uses. *Price:* **$0** within Cloud Logging free ingestion + minimal GCS storage, **but** may require billing enabled; **UNKNOWN** whether retention locks work on a Spark-only project.
5. **Make a secret the app uses unreadable by the app (true secret zero).** Impossible on a PaaS that injects env/secret files. *Cheapest fix:* the KMS/HSM in (2) removes the *key* from the app, but the app still holds the *credential to call* KMS (its own GCP identity / SA JSON). True secret zero needs attestation-gated key release (TEE, item 1) or a second service holding the credential (see 6). There is no free fix; the honest statement is "reduce blast radius, don't claim elimination."
6. **Restore sender authenticity for a compromised app.** Impossible with one service — a single compromised process is the single point of forgery. *Cheapest fix:* **split the trust across two independent services**: the sealing/signing service holds the credential and independently validates inputs; the render-facing service cannot sign. Then compromising the app does not yield a signing credential. *Price:* one extra always-on small service (Render second service / Koyeb Nano within the $5.50 credit / similar) — roughly **$0–$7/mo** depending on tier. **[INFERENCE]**
7. **Non-repudiation / tamper-evident ledger for what was signed.** Partially possible cheaply. *Cheapest fix:* append a **hash chain / external transparency log** entry per seal (e.g. Sigstore Rekor or a simple GCS append-only object) so omissions/rewrites are detectable against an external anchor. *Price:* Sigstore Rekor is free public infra (with privacy caveats); GCS storage is negligible. **[INFERENCE / UNKNOWN on Rekor free limits]**
8. **Prevent an attacker from deleting evidence (currently the app's SA can).** Impossible while the app's SA has delete rights on the evidence store. *Cheapest fix:* separate the **admin/deletion role** from the **app/write role** — give the app an append-only identity and require the offline admin key for deletions. *Price:* **$0** (IAM change). **[CITED pattern: least-privilege SA + workload identity federation best practice, per Google KMS/SA docs]** (exact doc not fetched; treat as **[UNKNOWN]** source).

### Inferences
- **[INFERENCE]** Cost-ordered recommendation: (a) free/cheap — split roles (6/8), add the independent witness cron (3), log-sink-to-separate-project (4), and a KMS/HSM signing key (2) if the always-free Autokey allowance covers it. (b) ~$1–7/mo — an HSM key outside the free allowance and/or a second service. (c) structurally out of hobby reach — a TEE host + admin verifier (1), which is the only thing that actually solves "the app cannot authenticate itself."
- **[INFERENCE]** The honest ceiling to state plainly: **on this stack, the admin cannot cryptographically distinguish a genuine archive from a forged one produced by a compromised app, and cannot prove that no archive was omitted.** The stack can only (i) make the signing key non-exfiltratable (KMS/HSM) and auditable, (ii) detect *anomalies* (volume, missing heartbeats) via independent observers, and (iii) shrink the blast radius of a compromise (least privilege, offline admin key). Anything stronger is a TEE + verifier, i.e. new infrastructure.
