# Signature-based Sender Authentication and Signing-Key Management for Sealed Evidence Archives

Scope note: this is a research/notes file for a specific system — FastAPI on **Render** (plain container PaaS: no TEE, no confidential computing, no attestation), built from a **public GitHub repo**, secrets in environment variables. It periodically writes **sealed archives** (X25519 envelope + AES-256-GCM) into **Firestore** via the admin SDK / service account, and opens a **GitHub issue** with metadata. An **admin CLI on the operator's laptop** holds the X25519 private key; the app holds only the public key. Available credentials: a Google service-account JSON (Firestore/Auth), a GitHub fine-grained token, Render env vars. The Firebase project is on **Spark (free)**; Blaze requires linking a card. Dates are given where a pricing/version fact was observed; anything I could not verify is marked **UNKNOWN**.

Terminology used below:
- "**store-only attacker**" = can read/write/delete the archive store (Firestore docs, or an object store) and the GitHub issue, but **cannot read the app process** (no env vars, no memory, no service-account key). Example: someone who obtained a leaked/stolen copy of the SA JSON, a Firestore backup, or who is a co-tenant of the store.
- "**app-control attacker**" = fully controls the running app (reads env vars and process memory, can call any API the app can call, can run arbitrary code in the container).

## Q1 — What does app-side asymmetric signing actually prove? What does each attacker class defeat?

### Takeaway
A digital signature proves **integrity + authenticity + non-repudiation of the signed bytes relative to a public key** — nothing more ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)). Whether that helps depends entirely on **where the private key lives relative to the attacker**. Against a **store-only attacker**, an app-key signature makes *content forgery* **detectable** (not prevented) but does **not** stop **omission/deletion**. Against an **app-control attacker**, an app-held signing key (env var, secret file, or a KMS key the app is authorized to use) makes forgery **both unpreventable and undetectable** — the attacker simply signs what they want. Signatures can never prove *which code* produced an artifact on a platform without attestation.

### Cited Findings
- A digital signature is defined by two operations: a **signing** operation using a private signing key, and a **verification** operation a party can perform "who has no knowledge of the signing key"; its purposes are **integrity** and **non-repudiation** ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)).
- Firestore **security rules do not apply to the Admin SDK / service account**; the Admin SDK is initialized with a service account and "gives the SDK full access to your data" ([Firebase blog, "7 tips on Firebase security rules and the Admin SDK"](https://firebase.blog/posts/2019/03/firebase-security-rules-admin-sdk-tips/)). Another write-up states rules "only apply to client SDK access… Code using the Admin SDK or a service account bypasses them entirely" ([cloudwebschool](https://cloudwebschool.com/docs/gcp/storage-services/firestore-security-rules/)); AWS/GCP IAM for Firebase is described as having "full access to everything by default" ([safecontrols](https://safecontrols.blog/2022/01/11/firebase-iam-the-tale-of-excessive-permissions/)).
- SLSA's threat model treats "use or exfiltrate the provenance **signing key**… that should only be available to the build platform" as a first-class threat; the mitigation is that signing happens in a place the untrusted build **cannot reach** ([SLSA v1.0, Threats & mitigations](https://slsa.dev/spec/v1.0/threats)). Its draft text is explicit: "the Provenance signing key MUST NOT be reachable by any process that executed dep code. Signing happens in a [separate trusted step]" ([SLSA draft threats](https://slsa.dev/spec/draft/threats)).
- Independent analysis of SLSA: it "doesn't prevent tampering during the build," doesn't address insider threats, and its guarantee holds only when "the signing keys are isolated from the build steps" ([practical-devsecops, SLSA Framework Guide 2026](https://www.practical-devsecops.com/slsa-framework-guide-software-supply-chain-security/)). A post-mortem (Mini Shai-Hulud) frames the boundary the same way: a compromised build "cannot reach the signing key," and moving from L2→L3 "directly addresses" that class of attack ([OpenSSF blog, 2026-06-10](https://openssf.org/blog/2026/06/10/mini-shai-hulud-where-slsas-boundaries-fall/)). Sigstore's own compromise playbook notes signatures are stored forever but "software verification using Sigstore does support artifact revocation" ([Sigstore blog, "Don't Panic"](https://blog.sigstore.dev/dont-panic-a-playbook-for-handling-account-compromise-with-sigstore-ee299dca5144/)).

### Threat / capability matrix (the core deliverable of this section)

| Attacker | Action | App holds signing key (env/secret/KMS) | App holds only a **public** verification key; signing done outside app |
|---|---|---|---|
| **Store-only** | Alter an archive's bytes | **Detected** if ciphertext hash is signed (sig fails); prevention impossible | **Detected** |
| **Store-only** | Delete/omit archives | **Unpreventable**; detection only via external append-only anchor | **Unpreventable**; detection only via external anchor |
| **Store-only** | Replay an old valid archive as current | Depends on framing (signed timestamp + monotonic counter/log) | Same |
| **App-control** | Forge an archive | **Unpreventable and undetectable** (signs with its own/authorized key) | **Prevented** for the trusted signing key — attacker has no key to forge with |
| **App-control** | Omit/suppress honest archives | **Unpreventable** | Unpreventable unless every seal must be pushed to an external append-only sink under a different identity than the app |
| **App-control** | Read/decrypt archives | Already lost: AEAD key is in the app (AES-256-GCM) | Same (decryption key still in app) |

Two structural points that follow:
1. **Encryption ≠ authentication.** The AES-256-GCM envelope gives confidentiality + integrity-under-the-AEAD-key, but the AEAD key is symmetric and the app holds it, so it says nothing about *who* produced an archive to a third party. A signature is what carries a statement that *a specific public key's holder* endorsed these bytes. (This matches the project's own recorded "unresolved risk: no sender authentication".)
2. **Omission is not a signature problem.** No signature scheme can stop a party that controls the storage from dropping entries; you can only make omission *detectable* by publishing a signed, externally-anchored, append-only index (see Q4 replay/omission).

### Inferences
- For *this* system, an app-held signing key that is merely "not in the archive store" does add real value against the **most likely** realistic attacker here (a leaked Firestore/SA credential, or a co-tenant of the store), because that attacker cannot mint signatures. It buys nothing against a compromised Render container.
- Because the app stores archives in Firestore with an SA that "bypasses rules entirely," the **store and the app are guarded by the same secret** (the SA JSON). If that JSON lives in a Render env var, then "store-only" and "app-control" collapse into the same attacker the moment the env var leaks. This is the decisive fact for choosing where the signing key lives (Q2).
- The project's existing asset — an **X25519 private key that exists only on the operator laptop** — is already the strongest available "outside the app" anchor. The design question in Q6 is whether to *reuse that separation* for signing, rather than adding an app-held signing key.

### Gaps
- No primary source found that quantifies how often "leaked service-account JSON" vs "container compromise" is the actual breach path for small PaaS apps; the prioritization above is a judgment, not a measured statistic.
- I did not find an authoritative statement on whether **Render** injects any per-instance workload identity (it does not appear to; the app uses the SA JSON), so "store-only vs app-control" separation on Render is only as strong as where the SA JSON is placed.

## Q2 — Where should the signing key live so it is *not exportable*? (env var, secret file, Cloud KMS software/HSM, separate signing service) + cost/eligibility on Spark and free tiers

### Takeaway
"No new paid vendor" and "non-exportable signing key usable by the app" are in **fundamental tension**. The only genuinely **non-exportable** options are (a) **Google Cloud KMS asymmetric sign** — private key never leaves KMS, but it is **Blaze/billing-only** and does **not** stop a compromised app from signing, and (b) the **operator's offline key** (already present) — but the app cannot use it. **Env vars and Render secret files are exportable by design** (the app process can read them; Render only promises encryption *at rest*). A separate signing service/Cloud Function helps only if the app's identity is **not authorized** to ask it to sign arbitrary payloads — and the enforcement is access-control/policy, not cryptography.

### Cited Findings
**Env var / secret file (exportable):**
- Render: "Your environment variables and secret files are encrypted **at rest** using a minimum AES-128 standard" ([Render, "How Render handles secrets and environment variables"](https://render.com/articles/how-render-handles-secrets-and-environment-variables)). Encryption at rest does not make a value non-exportable to the running process; the canonical criticism is that env vars are readable by the process and its children and are a common leakage path ([nodejs-security, "Do Not Use Secrets in Environment Variables"](https://www.nodejs-security.com/blog/do-not-use-secrets-in-environment-variables-and-here-is-how-to-do-it-better); [GitGuardian, "Secure your secrets with env"](https://blog.gitguardian.com/secure-your-secrets-with-env/)).
- Project-verified platform constraint (prior notes): Render **secret files** are exposed at runtime as `/etc/secrets/<filename>`, capped at **1 MB total per service/environment group** — same readability problem as env vars.

**Google Cloud KMS asymmetric signing (non-exportable, Blaze-only):**
- Cloud KMS provides `ASYMMETRIC_SIGN` keys; you create a signature with the private key and verify with the retrieved public key using open tools like OpenSSL. **Cloud KMS does not directly validate signatures** — you fetch the public key and verify externally ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)).
- Supported signing: **elliptic curve (EC) and RSA** for classical signatures, plus post-quantum **ML-DSA (FIPS 204)** and **SLH-DSA (FIPS 205)**; Cloud KMS does **not** offer Ed25519 ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures); [Key purposes and algorithms](https://docs.cloud.google.com/kms/docs/algorithms)). The product blurb lists RSA 2048/3072/4096 and EC P256/P384 ([Google Cloud KMS product page](https://cloud.google.com/security/products/security-key-management)).
- **Protection levels:** `SOFTWARE` (keys in software) and `HSM` (Cloud HSM, FIPS-validated hardware). Pricing differs by protection level (see below). For `SOFTWARE`, asymmetric and symmetric keys cost the **same** ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)).
- **Cost (observed 2026, "prices effective March 17, 2025"):** active asymmetric EC/RSA-2048 key version **$0.000082192 / version / hour ≈ $0.06/version/month** at SOFTWARE level; asymmetric **RSA-3072/4096 or EC** versions are listed on the same SOFTWARE line ($0.000082192/hr). Cryptographic operations (sign, encrypt, etc.) **$0.03 / 10,000** at SOFTWARE, **$0.15 / 10,000** at HSM; **admin operations free**; **rotation (creating a new version) is free** ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)). A worked example: 50,000 asymmetric signatures = **$0.15** ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)).
- **Free tier caveat:** the GCP Always Free allowance for Cloud KMS applies only to "keys created using **Cloud KMS Autokey**" (100 active versions, 10,000 crypto ops/month, rotation always free) and still assumes a billing-enabled project ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)).
- **Eligibility on Spark:** the same pricing page states, "You **must sign up for billing** before you can start using Cloud KMS" ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)). A Firebase **Spark** project has no Cloud Billing account; upgrading to **Blaze = linking a Cloud Billing account** ([Firebase, pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)). ⇒ **Cloud KMS is not usable on Spark; it requires Blaze + a card.** Net cost at this app's scale is effectively **~$0.06/month + pennies of operations**, but the *eligibility gate* (a card on Blaze) is the real constraint.

**AWS KMS asymmetric (non-exportable, HSM-backed, not free for signing):**
- Every KMS key costs **$1/month** prorated hourly (same price for symmetric, asymmetric, HMAC, imported, and CloudHSM/XKS-origin keys); the **first two rotations each add $1/month**, capped after that ([AWS KMS pricing](https://aws.amazon.com/kms/pricing/)).
- **Free-tier gotcha:** AWS KMS gives **20,000 requests/month** free, but "requests to API operations such as **Sign, Verify**, Encrypt, Decrypt, and **GetPublicKey** that reference **asymmetric KMS keys are excluded from the free tier**" ([AWS KMS pricing](https://aws.amazon.com/kms/pricing/)). So asymmetric signing is **never** covered by the free tier. Worked example: 1 ECC-256 key signing 100,000 files/month = **$1.00 + $1.50 = $2.50/month** ([AWS KMS pricing](https://aws.amazon.com/kms/pricing/)).
- AWS KMS keys are protected by "a distributed fleet of **FIPS 140-3 Security Level 3**-validated HSMs," and all keys "regardless of their creation date or origin" are HSM-protected ([AWS KMS data protection](https://docs.aws.amazon.com/kms/latest/developerguide/data-protection.html); [AWS KMS FAQs](https://aws.amazon.com/kms/faqs/)). This is a stronger protection statement than GCP SOFTWARE level (GCP achieves comparable hardware protection only at the HSM level).

**Separate signing service / Cloud Function with its own identity:**
- Architectural value is **access control + audit + policy**, not cryptography: if the app can call the service with arbitrary input, the app-control attacker still forges. The service only helps when (i) it uses a **distinct identity** the app does not hold, (ii) the app's identity is **not** granted `kms.signerVerifier`, and (iii) the service **re-derives/validates** what it signs (e.g., reads the archive from Firestore and re-hashes it) rather than signing a caller-supplied digest. KMS additionally provides audit logging and easy disable of a key version ([Cloud KMS, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures); [Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation) — "disable it and revoke access to it as soon as possible").
- On Firebase, hosting such a broker is itself a Blaze question (see Gaps).

### Inferences
- **Ranking for this system (Spark, "no new paid vendor"):**
  1. **Operator offline key as the only signer** (zero cost, already exists) — fully non-exportable from the app's perspective because the app never has it. Loses real-time/app-originated signing.
  2. **GitHub Actions with a repo/workflow-scoped signing key** (zero new vendor) — signing happens outside Render, so a **Render-app compromise alone cannot forge**; the key is a GitHub Actions secret (still exportable to CI, but a *different* trust domain than the app). See Q6.
  3. **Cloud KMS asymmetric sign, SOFTWARE level** (near-free but Blaze-only) — non-exportable key + audit + disable; does **not** stop app compromise.
  4. **Env var / Render secret file** (zero cost) — **not** non-exportable; only raises the bar vs a store-only attacker.
  5. **AWS KMS** — genuinely HSM-backed and non-exportable, but **$1–$2.50/month and a new vendor**, i.e. violates "no new paid vendor."
- Because the SA JSON (full Firestore access) and any app-held signing key would live in the **same** Render env, an env-var signing key adds essentially **no** protection against the credential-leak scenario that already compromises the store. Its marginal value is limited to an attacker who can write to Firestore but genuinely cannot read the app — a narrow case.

### Gaps
- **UNKNOWN:** whether a **Cloud Function 2nd gen / Cloud Run** signing broker can be deployed on a **Spark** project, or whether it requires Blaze. Firebase's own docs tie Blaze to linking Cloud Billing, so my working assumption is **Blaze required**, but I could not verify the exact current Spark rule for Functions/Run in this session — **treat as needing confirmation**.
- **UNKNOWN / VERIFY:** the exact per-algorithm input rule for `AsymmetricSign` (commonly reported: **RSA takes a precomputed digest**, **EC takes the raw message which KMS hashes**). This matters for pre-hashing and framing; I did not fetch the `create-validate-signatures` page to confirm.
- **UNKNOWN:** whether any mainstream **free-tier** serverless platform (Cloudflare Workers, Deno Deploy, Fly.io) offers a **non-exportable asymmetric signing primitive** in its free plan. Cloudflare's keyless/Workers crypto is not obviously a signing-as-a-service with non-exportable keys; I found no reliable source.
- Cost figures are point-in-time (pages dated 2026 on fetch; GCP says "effective March 17, 2025"). Re-check before quoting.

## Q3 — Rotation and revocation: rotate without losing verification of old archives; revoke a leaked key; what the key-id/versioning scheme must record

### Takeaway
**Rotation of a signing key is cheap and safe only if you keep every retired *public* verification key forever** and embed a **key_id / key version** inside each signed payload. Cloud KMS **cannot auto-rotate asymmetric signing keys** — you must distribute the new public key yourself. **Revocation is inherently forward-only:** you can stop future trust in a leaked key (disable the version, publish a revocation statement), but you **cannot un-sign** archives already produced, and forgeries made during the pre-detection window remain valid-looking.

### Cited Findings
- **Cloud KMS does not support automatic rotation for asymmetric keys**, "because additional steps are required before you can use the new asymmetric key version." For signing keys, you "must distribute the public key portion of the new key version" and update applications to specify the new version in `asymmetricSign` calls ([Cloud KMS, Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)). (Symmetric keys can auto-rotate, e.g., a 90-day default is reported for GCP symmetric keys — [dev.to GCP KMS guide](https://dev.to/latchudevops/part-22-google-cloud-kms-key-management-service-create-use-keys-3k7c).)
- **Rotation does not re-encrypt and does not disable/delete old versions**: after rotating, "previous key versions remain active and incur costs until they are destroyed," and destroying a version still in use "can cause permanent data loss." You must ensure a version is no longer in use before destroying it ([Cloud KMS, Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
- **Rotation cost:** creating a new version ("rotating a key") is an **admin operation and always free**; key **versions remain billable while active** ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)).
- **On compromise:** "If you suspect that a key version is compromised, **disable it** and **revoke access to it** as soon as possible." Validate rotation procedures *before* an incident ("[validate] your key rotation procedures before a real-life security incident occurs") ([Cloud KMS, Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
- **TUF's compromise guidance** (a strong analogy for a small signed log): "The repo maintainer must revoke and replace compromised keys. If a Timestamp, Snapshot, Targets, or **Root** key is compromised, the Root role must re-sign its metadata to replace the compromised key. If a **threshold of Root keys** is compromised, the Root file must be re-issued **out of band**" ([TUF FAQ](https://theupdateframework.io/docs/faq/)). This is the "you need an out-of-band root" pattern: revocation authority must itself be rooted somewhere the attacker does not control.
- **TUF rotation cadence as a template:** rotate the frequently-used **online** key (Timestamp) most often; keep keys whose compromise is costlier (Snapshot/Targets/Root) **offline** and rotate less often; "a good rule of thumb is the more often the metadata changes, the sooner it should expire" (Timestamp/Snapshot ≈ 1 day, Root/Targets ≈ 1 year) ([TUF FAQ](https://theupdateframework.io/docs/faq/)).
- **NIST guidance exists but was only partially retrieved:** SP 800-57 Part 1 Rev. 5 (May 2020) is the canonical key-management/lifecycle reference ([NIST SP 800-57 Pt.1 Rev.5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final)); OWASP summarizes the operative rule: "Limiting cryptoperiods restricts the amount of data protected by a single key… (NIST SP 800-57 Part 1)" ([OWASP Key Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)). A Rev. 6 initial public draft exists (comment period through 2026-02-05) ([NIST SP 800-57 Pt.1 Rev.6 iPD](https://csrc.nist.gov/pubs/sp/800/57/pt1/r6/ipd)). **I did not retrieve the specific cryptoperiod numbers for signature keys from SP 800-57 itself — see Gaps.**
- **Non-repudiation vs key loss:** the purpose of a signature includes non-repudiation "if the signer claims the signature is not authentic" ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)) — which is exactly why verification keys must be retained: if you destroy a verification key, you destroy the ability to check (and thereby the evidentiary value of) archives signed by it.

### Design (concrete)
- **Signed payload MUST include:** `key_id` (stable logical name, e.g., `evseal-sign-2026a`), the **full key version identifier** (for KMS: `projects/<p>/locations/<l>/keyRings/<r>/cryptoKeys/<k>/cryptoKeyVersions/<n>`), the **algorithm** identifier, and a **scheme/format version** (existing `MFA1` analogue). This mirrors DSSE's opaque `keyid` and TUF's keyid-anchored role keys ([in-toto envelope.md](https://github.com/in-toto/attestation/blob/main/spec/v1/envelope.md); [TUF FAQ](https://theupdateframework.io/docs/faq/)).
- **Verifier keyring:** keep an append-only, signed **keyring manifest** mapping each `key_id` → public key → validity window (`not_before`, `not_after`, optional `revoked_at`). Store it in the repo and anchor it (see Q4). Never delete verification keys; only mark them expired/revoked.
- **Rotation runbook:** (1) create new key version; (2) fetch its public key; (3) append the new entry to the signed keyring with a start time; (4) deploy the app with the new key_id (or the new KMS version) via Render REST API/dashboard (Render CLI cannot change env vars — see project platform notes); (5) keep the old version **enabled for verification** (never destroyed); (6) verify a sample of old + new archives.
- **Revocation:** disable the KMS version (or delete the local key file) **and** publish a signed **revocation statement** `{key_id, revoked_at, reason}` into the anchored log. Verifiers must reject signatures from that `key_id` with `created_at > revoked_at`. Be explicit that signatures with `created_at ≤ revoked_at` remain cryptographically valid — you cannot tell a legitimate pre-revocation archive from a pre-revocation forgery by signature alone.
- **Root-of-trust caveat:** per TUF, revocation must be rooted **out of band**. Here the natural out-of-band root is the **operator's offline key + the Git commit history** (a place the Render app cannot rewrite under a *different* identity). If the same compromised app can also rewrite the revocation log, revocation fails.

### Inferences
- For a single-admin system, a practical cryptoperiod is **per deploy or per quarter**, whichever is sooner; the marginal cost is ~$0 (GCP rotation is free; new active versions cost ~$0.06/mo each). The dominant cost is **operational discipline** (distributing the public key, updating the keyring), which is why monthly auto-rotation of *asymmetric* keys is not even offered by KMS.
- If signing is done by the **operator CLI** (offline key), "rotation" means generating a new offline key and adding a keyring entry — cheaper and faster to reason about than KMS rotation, but with no automatic disable and higher risk of key loss (backup discipline required).

### Gaps
- **Specific cryptoperiod numbers** for signature-key lifetimes from **NIST SP 800-57 Part 1 Rev. 5** (e.g., recommended originator-usage periods) were **not retrieved verbatim**; the specific table values should be pulled from the PDF before quoting. Rev. 6 is a draft with a comment window closing 2026-02-05.
- **UNKNOWN:** whether GCP enforces any maximum lifetime on a signing key version, or whether versions can stay enabled indefinitely for verification (I found no limit; the docs stress cost and destruction safety, not lifetime caps).

## Q4 — Message framing: canonical serialization, domain separation, and the pitfalls (JCS/CBOR, ciphertext vs plaintext, replay)

### Takeaway
Sign a small, **explicitly-versioned, canonically-serialized manifest** whose central field is the **SHA-256 (or SHA-512) hash of the stored archive ciphertext** — not the plaintext — plus `key_id`, scheme version, and an issuer timestamp. **Do not rely on JSON canonicalization as a general fix**: RFC 8785 (JCS) only canonicalizes the I-JSON subset and mishandles large integers/lossy numbers. Use **domain separation** (an explicit ASCII tag or RFC 8032 context) so signatures cannot be replayed across protocols, and treat **replay/rollback** as a separate problem that a signature alone does not solve (needs a signed timestamp + an external append-only anchor).

### Cited Findings
- **What to sign / the pipeline:** the standard "sign the artifact, then wrap" flow (as in Sigstore) signs the artifact and stores the signature alongside it; DSSE/in-toto wrap a base64 payload in a signing envelope with a `payloadType` and a list of `{keyid, sig}` ([in-toto `envelope.md`](https://github.com/in-toto/attestation/blob/main/spec/v1/envelope.md); [Sigstore cosign signing overview](https://docs.sigstore.dev/cosign/signing/overview/)).
- **DSSE pre-authentication encoding (PAE):** the signature is computed over a domain-separated string derived from `("DSSEv1", payloadType, payload)` — i.e., length-prefixed type + payload with a fixed ASCII prefix — precisely to prevent ambiguity/cross-protocol reuse ([in-toto/DSSE, summarized in cilock.dev](https://cilock.dev/concepts/dsse-and-in-toto/); [Sigstore attestation docs cite DSSE](https://docs.sigstore.dev/cosign/verifying/attestation/)). DSSE is recommended by in-toto for envelopes ([in-toto `envelope.md`](https://github.com/in-toto/attestation/blob/main/spec/v1/envelope.md)).
- **RFC 8785 (JCS) constraints:** JCS "constrains data to the I-JSON \[RFC 7493] subset," and "JSON does not have a namespace concept and default values" ([RFC 8785](https://www.rfc-editor.org/info/rfc8785/)). Practitioners report the concrete failure modes: "JSON is not deterministic. Object key order, number formatting, and whitespace vary across serializers, languages, and runtime versions," and implementation pain centers on the **UTF-16 lexicographic key ordering** rule ([Go JCS implementation write-up](https://dev.to/lenny321/json-canon-a-strict-rfc-8785-implementation-in-go-for-deterministic-json-3mfg); [nlohmann/json discussion #2612](https://github.com/nlohmann/json/discussions/2612)). JCS serializes numbers per ECMAScript `Number` semantics, so integers beyond 2^53 and high-precision decimals do **not** round-trip. ⇒ Treat JCS as safe only for schemas whose numbers are all small integers or strings.
- **Deterministic CBOR** is the alternative: CBOR's deterministic encoding (a specified key ordering + preferred serialization) exists in RFC 8949 §4.2 — cited here as the recommended byte-level alternative to JCS for a fixed schema (secondary mention in the JCS ecosystem; primary spec is RFC 8949). For a **fixed field layout** the simplest robust option is a hand-defined binary layout (fixed-width big-endian integers, no floats), which sidesteps canonicalization entirely.
- **Domain separation in EdDSA:** RFC 8032 defines `Ed25519ctx` and `Ed25519ph`, which add a **context** (and, for `ph`, pre-hashing) explicitly to allow signatures to be scoped to a purpose ([RFC 8032](https://www.rfc-editor.org/info/rfc8032/); [crypto.SE on pure vs ph](https://crypto.stackexchange.com/questions/72035/difference-between-pure-eddsa-ed25519-and-hasheddsa-ed25519ph)). A documentation example notes that "the domain separation scheme adds a preprocessing" step and that contexts "can be used to differentiate signatures generated for different purposes" ([OASIS crypto docs](https://docs.oasis.io/core/crypto); [curdle-pkix draft](https://datatracker.ietf.org/doc/draft-ietf-curdle-pkix/03/)).
- **Replay/rollback is handled at the metadata/freshness layer, not by the signature:** TUF's Timestamp/Snapshot/Root roles and their expiration windows exist specifically to defeat replay/freeze attacks, and TUF keeps Timestamp short-lived (≈1 day) vs Root (≈1 year) ([TUF FAQ](https://theupdateframework.io/docs/faq/)). Sigstore's Rekor is a public **transparency log** that "records" signature events so a signature's existence/time can be checked independently of the signer ([Sigstore cosign overview](https://docs.sigstore.dev/cosign/signing/overview/); [GitLab keyless docs](https://docs.gitlab.com/ci/yaml/signing_examples/)).

### Design (concrete framing for MFA1-style archives)
Signed bytes (`SEAL-SIG-v1` payload) should be a canonical structure containing at minimum:
1. `domain` — a fixed ASCII tag, e.g. `"EVIDENCE-SEAL/v1"` (first field; hard domain separation).
2. `scheme` — archive container format, e.g. `"MFA1"`.
3. `archive_id` — the stable Firestore doc id / issue id.
4. `ciphertext_sha256` — **hex SHA-256 of the exact stored ciphertext bytes** (not the plaintext). Signing the ciphertext is correct because it binds the precise bytes at rest; AES-GCM already binds ciphertext↔plaintext under the AEAD key, so the signature transitively covers the plaintext *given the AEAD key*.
5. `ciphertext_len` — length in bytes (defends against truncation/ambiguity).
6. `recipient_key_fp` — fingerprint of the X25519 recipient public key (binds the intended decryptor).
7. `key_id` + `signing_key_version` + `signing_algorithm` — from Q3.
8. `created_at` — ISO-8601 UTC + integer epoch seconds (the *issuer* timestamp; not trusted for freshness by itself).
9. `prev_digest` — hash of the previous manifest (makes the manifest stream a hash chain → detects omission/deletion of entries).
10. `seq` — monotonically increasing sequence number (detects rollback within the chain).

**Framing rules:**
- Serialize with **explicit field order and encodings** — either a hand-defined binary layout, deterministic CBOR (RFC 8949 §4.2), or JCS **only if** every number is a small integer or a string. Do **not** sign raw `json.dumps(...)` of a dict.
- Prefix the signed message with the `domain` tag (or use an Ed25519/Ed25519ph **context**, or a DSSE-style PAE `"DSSEv1"|len(type)|type|len(payload)|payload`).
- Put the manifest's own `scheme`/`key_id`/`version` **inside** the signed bytes, not in an out-of-band wrapper.
- **Sign ciphertext, not plaintext** (binds what is stored); if you also want a statement about semantic content, sign both, but then you must bind the ciphertext↔plaintext linkage too.
- Anchor `prev_digest`/`seq` (and/or each `archive_id`) to an **external append-only sink** (Git commit, GitHub issue comment stream, or Rekor) so omission and replay become detectable.

### Inferences
- The `prev_digest` hash chain + an externally-anchored head is the cheapest omission detection available with existing credentials: commit the chain head (and each new manifest) to the GitHub repo, or post a comment per archive. A `store-only` attacker can delete Firestore docs, but cannot rewrite the Git history under the operator's identity (they hold only the SA JSON, not the GitHub token).
- Signing the ciphertext hash means the **admin CLI must verify against the ciphertext bytes it pulls from Firestore**, then decrypt; this matches the existing envelope+AEAD design and avoids a second canonicalization of the (large, gzip-compressed) plaintext.
- Because the archive plaintext is gzip-compressed before encryption (existing `MFA1` design), pre-hashing the plaintext would be non-deterministic across gzip implementations — another reason to sign the **ciphertext**.

### Gaps
- **UNKNOWN / VERIFY:** `AsymmetricSign` input semantics for RSA (digest) vs EC (message) in GCP KMS — this changes whether the framing signs a hash or the full message (Q2 gap).
- I did not retrieve the **exact RFC 8949 deterministic-encoding** normative text; the recommendation stands on its existence and general reputation, with the primary spec cited as RFC 8949 §4.2 for the report writer to confirm.
- No source found on the **exact** DSSE PAE byte string in this session beyond summaries; the canonical definition is in the DSSE spec repo (secure-systems-lab/dsse) — confirm before implementing.

## Q5 — Algorithm choices (Ed25519 / ECDSA P-256 / RSA-PSS) and implementation pitfalls

### Takeaway
For a **local/offline admin signer**, **Ed25519** is the best default: deterministic (no nonce-RNG failure mode), compact, fast, and **FIPS 186-5-approved** — but you must enforce **canonical verification** (reject non-canonical `S` and small-order points), because implementations legitimately disagree here. For a **cloud-managed key**, Cloud KMS offers **EC P-256 / RSA-PSS** (not Ed25519); prefer **EC P-256** (compact, `EC_SIGN_P256_SHA256`) or **RSA-PSS**. Avoid raw **ECDSA without deterministic or HSM nonces** (a reused/biased nonce recovers the private key).

### Cited Findings
- **FIPS 186-5 (published 2023-02-03)** specifies the DSS algorithm suite; it **removed DSA** and (per reporting) is the first FIPS standard to include **Ed25519** as approved ([FIPS 186-5](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.186-5.pdf); [Federal Register notice, 2023-02-03](https://www.federalregister.gov/documents/2023/02/03/2023-02273/announcing-issuance-of-federal-information-processing-standard-fips-186-5-digital-signature-standard); [CSRC FIPS 186-5](https://csrc.nist.gov/pubs/fips/186-5/final)).
- **Ed25519 (RFC 8032)** is deterministic (nonce derived from key+message), needs no external RNG for signing, and defines `Ed25519ctx`/`Ed25519ph` variants with a context for domain separation ([RFC 8032](https://www.rfc-editor.org/info/rfc8032/); [crypto.SE Pure vs ph](https://crypto.stackexchange.com/questions/72035/difference-between-pure-eddsa-ed25519-and-hasheddsa-ed25519ph)).
- **Malleability caveat (implementer disagreement):** "Ed25519 signatures are **trivially malleable unless the scalar component is constrained to `0 <= s < L`**" ([OASIS ADR 0009](https://docs.oasis.io/adrs/0009-ed25519-semantics)). The academic treatment "Taming the many EdDSAs" documents "ambiguity regarding signature verifcation equations, binding and malleability guarantees, and incompatibilities" and notes Ed25519's **non-canonical `y`** serialization and "transaction malleability on non-canonical `S` values" ([Chalkias et al., ePrint 2020/1244](https://eprint.iacr.org/2020/1244.pdf); [NIST CR Club slides](https://csrc.nist.gov/csrc/media/Presentations/2023/crclub-2023-03-08/images-media/20230308-crypto-club-slides--taming-the-many-EdDSAs.pdf)). Implementations differ on whether they check canonicity/order of inputs ([crypto.SE](https://crypto.stackexchange.com/questions/55656/should-ed25519-signature-verification-check-the-order-and-canonicity-of-its-inpu)). ⇒ Verify with a strict library and/or add a uniqueness check (e.g., reject a second valid `S` for the same message).
- **ECDSA nonce reuse is catastrophic:** with two signatures sharing a nonce, `k` is recoverable by a linear system, and then the private key ([Bitcointalk, nonce reuse across keys](https://bitcointalk.org/index.php?topic=5576534.0); [MEV-X, "ECDSA Nonce Reuse: Key Compromise via a Linear System"](https://medium.com/@MEV-X/ecdsa-nonce-reuse-key-compromise-via-a-linear-system-6e725539bbcd)). The fix is deterministic nonces per **RFC 6979** or an HSM's high-quality RNG: "Prefer signing schemes or modes that remove runtime RNG from nonce generation. For ECDSA, use deterministic nonce generation such as RFC 6979" ([LinkedIn, recovering ECDSA key from nonce reuse](https://www.linkedin.com/pulse/two-signatures-enough-recovering-ecdsa-private-key-from-collins-n0t4e)). RFC 6979 defines a deterministic signature-generation procedure compatible with DSA/ECDSA ([RFC 6979](https://www.rfc-editor.org/info/rfc6979/)).
- **Strength equivalence:** "a 256-bit ECDSA key offers comparable security to a 3072-bit RSA key" ([SSL.com, Comparing ECDSA vs RSA](https://www.ssl.com/article/comparing-ecdsa-vs-rsa-a-simple-guide/)). Teleport's comparison: "Ed25519 is the fastest performing algorithm across all metrics" and EdDSA gives "the highest security level relative to key length" ([Teleport, Comparing SSH keys](https://goteleport.com/blog/comparing-ssh-keys/)).
- **What KMS offers:** EC (`EC_SIGN_P256_SHA256` etc.) and RSA signing algorithms (`RSA_SIGN_PSS_2048_SHA256` etc., plus PKCS#1 v1.5 and PQC ML-DSA/SLH-DSA); **no Ed25519** ([Google Cloud, Key purposes and algorithms](https://docs.cloud.google.com/kms/docs/algorithms); [Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)). Note GCP's mixed reporting: the Digital signatures page lists only EC/RSA for classical signing (plus PQC), while the product page lists "RSA 2048/3072/4096 and EC P256/P384" ([product page](https://cloud.google.com/security/products/security-key-management)).

### Inferences
- Recommendation for this system: if the signer is **offline/admin**, use **Ed25519** with a strict verifier and an explicit context/domain tag; if the signer is **Cloud KMS**, use **EC_SIGN_P256_SHA256** (compact, non-exportable, deterministic nonces generated inside KMS). Avoid **ECDSA in Python with a home-grown nonce**. RSA-PSS is acceptable but bloats signatures and is only worth it for ecosystem-compatibility reasons.
- Ed25519's advantage for this project is precisely that it removes the RNG-failure class — important given the constraint "the password/keys must never leak via memory or network."

### Gaps
- I found **no** evidence in this session of a 2023–2026 **shipped** Ed25519 verification forgery affecting a widely used library; the malleability/ambiguity material is design-level (`Taming the many EdDSAs`, 2020) and ADR-level (OASIS, 2025). **Do not overstate** as an active CVE without a citation.
- **UNKNOWN:** whether every Google Cloud KMS region/key supports the full classical EC/RSA algorithm list at `SOFTWARE` protection (docs indicate yes, but not verified per-region).

## Q6 — Recommended design for THIS system (no new paid vendor; works with GitHub Actions + single admin)

### Takeaway
Because the app's store credential and any app-held signing credential share the **same** Render env, put the trust anchor **outside the app**. The cheapest credible design is: the **app computes and stores** each sealed archive plus a manifest, and a **separate, differently-identified process anchors the manifest** — either the **operator CLI** (which already holds the only private key) or a **GitHub Actions job** with a repo-scoped Ed25519 key — and commits each manifest to the GitHub repo (append-only, timestamped). Add a **hash chain + external anchor** to make omission and replay detectable. Cloud KMS is the upgrade path if/when Blaze is acceptable; it is **not** available on Spark.

### Cited Findings
- Signing is only trustworthy when done where the untrusted workload cannot reach the key: "the Provenance signing key MUST NOT be reachable by any process that executed dep code. Signing happens in a [separate step]" ([SLSA draft](https://slsa.dev/spec/draft/threats)); a compromised build "cannot reach the signing key" is exactly the L2→L3 guarantee ([OpenSSF, Mini Shai-Hulud](https://openssf.org/blog/2026/06/10/mini-shai-hulud-where-slsas-boundaries-fall/)).
- TUF's separation-of-duties model: keep the high-value keys **offline**, use **online** keys only for the freshness roles, and keep the **root** able to revoke out of band ([TUF FAQ](https://theupdateframework.io/docs/faq/)). This maps onto "operator offline key as root; GitHub-anchored log as the online freshness layer."
- An independent, append-only log of signing events is the Sigstore pattern (**Rekor** transparency log) and is explicitly compatible with **artifact revocation** ([Sigstore cosign overview](https://docs.sigstore.dev/cosign/signing/overview/); [Sigstore "Don't Panic"](https://blog.sigstore.dev/dont-panic-a-playbook-for-handling-account-compromise-with-sigstore-ee299dca5144/)).
- Cloud KMS private keys are non-exportable via the API (you can only retrieve the **public** key and create signatures) ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)) — the correct choice *if* app-self-signing is required and Blaze is acceptable.
- Firebase's own billing model: Blaze = linking Cloud Billing; Spark has no billing, and Cloud KMS requires billing ([Firebase pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans); [Cloud KMS pricing](https://cloud.google.com/kms/pricing)).

### Concrete recommendation (ranked)
**Option A — zero new vendor, strongest against app compromise (recommended):**
1. App seals the archive (existing `MFA1`) and writes it to Firestore; it computes the manifest (`SEAL-SIG-v1`, Q4) and **stores the manifest unsigned** alongside the ciphertext.
2. A **GitHub Actions job** (or the operator CLI) fetches new manifests, verifies the ciphertext hash locally, signs the manifest with an **Ed25519 key held as an Actions secret**, appends a `manifest` line and updates a `prev_digest`-chained log, and commits/pushes it (or posts an issue comment). GitHub commits give platform-timestamped, externally-visible anchoring.
3. The admin CLI verifies: signature over the manifest, hash chain continuity from a pinned root, and that every Firestore archive id appears in the anchored log (omission detection).
   - **Honest limit:** the Actions key is still "held by an operator identity"; a compromise of the **repo/CI** (not the Render app) could forge. That is a *different, smaller* trust domain than the Render app, and the Git anchor is external and erasable only under the operator's GitHub identity.

**Option B — near-free, app self-signs (requires Blaze + card):**
- Create a **dedicated SA** with only `kms.signerVerifier` on **one** Cloud KMS `ASYMMETRIC_SIGN` key (`EC_SIGN_P256_SHA256`, `SOFTWARE`). The app calls `AsymmetricSign` on each manifest; the key is non-exportable and disabling the version is instant. **Cost ≈ $0.06/version/month + $0.03/10k signs**. **This does not stop a compromised app from forging** — state that explicitly in the runbook.
- Optional: a **Cloud Run / Function broker** with a *distinct* SA that **re-reads the Firestore doc and re-hashes** before signing (policy, not crypto). Requires Blaze (**UNKNOWN** for Function/Run on Spark — verify).

**Option C — app holds an Ed25519/RSA key in a Render env var or secret file (not recommended as the trust anchor):**
- Non-exportable = **NO**; the app (and an app-control attacker) can read it. Only defensible as a *defense-in-depth* layer against a **store-only** attacker, and it must never be presented as sender authentication against a compromised app.

### Inferences
- With a **single admin**, Option A gives the best security-per-effort and reuses the existing offline-key separation; it also satisfies "independent CLI process" and "render/firebase CLI" constraints (the anchoring can be driven by CI/CLI). Its weakness is that "prove the *running app* produced it" is replaced by "prove the *operator* attested it" — which is the honest, achievable guarantee on a non-attested PaaS.
- If the requirement is specifically **app-originated, real-time** signatures, only Option B (KMS) gets close, and even then the honest guarantee is "the app's *identity* signed," not "the genuine code signed."

### Gaps
- **UNKNOWN:** whether **Cloud Run / Functions** (for a signing broker) are deployable on Spark; needs confirmation before recommending Option B's broker variant.
- Not verified in this session: current **GitHub Actions** secret storage guarantees and whether an org-level OIDC→cloud-keyless flow (like Sigstore/Fulcio) is available **for free** for a private repo — worth a follow-up if app-originated signing becomes mandatory.

## Q7 — What remains impossible (be explicit)

### Takeaway
On a **non-attested PaaS**, you cannot cryptographically prove that a specific piece of code produced an artifact. A fully compromised app that can reach *any* signing capability it is authorized for (env key, KMS, or a broker that signs caller-supplied input) **can mint valid forgeries and can omit honest archives**, and no app-side signature scheme changes that. The best achievable properties are: (i) **detectability of content tampering** by any party who is *not* app-equivalent, and (ii) **detectability of omission/replay** via an external append-only anchor under a *different* identity than the app. Everything else (real-time, app-originated, code-identity proof) requires TEE/attestation or a trusted external signer that the app cannot compel.

### Cited Findings
- Signatures provide integrity and non-repudiation, i.e., they bind bytes to a key — not to a program image ([Google Cloud, Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)).
- SLSA's own limitation: provenance "doesn't prevent tampering during the build" and doesn't address insiders; the guarantee depends on key isolation ([practical-devsecops](https://www.practical-devsecops.com/slsa-framework-guide-software-supply-chain-security/)). Even its draft threat model explicitly considers the signing key as reachable by `dep` code as a **threat to mitigate**, not something signatures fix by themselves ([SLSA draft threats](https://slsa.dev/spec/draft/threats)).
- Artifact **revocation** exists (Sigstore) but signatures "are stored forever"; the log preserves history, so revocation is a *trust-decision* layer, not erasure ([Sigstore "Don't Panic"](https://blog.sigstore.dev/dont-panic-a-playbook-for-handling-account-compromise-with-sigstore-ee299dca5144/)).

### Inferences
- Statements the system **can** make honestly after this work:
  - "These ciphertext bytes have not changed since the manifest was signed by key `Kv` (signature verifies)."
  - "Every archive the operator's anchored log knows about is unmodified; any unanchored archive is flagged."
- Statements it **cannot** make honestly:
  - "This archive was produced by *the genuine application code*."
  - "No archives have been omitted" — unless the app is *forced* to publish to an external sink under a different identity, and even then only for archives it attempted to publish.
  - "Signature proves non-repudiation against the *operator*" if the operator's own key signed it (non-repudiation is relative to the key, per GCP's definition) — this is a legal/process claim, not a cryptographic one here.

### Gaps
- **UNKNOWN:** whether **Render** offers any per-deploy attestation or signed build metadata that could be folded into the manifest (would strengthen "which code" claims); no source found.

## Q8 — Where sources disagree, and explicit UNKNOWNs

### Takeaway
The main *technical* disagreement is **Ed25519 verification semantics** (cofactored vs cofactorless; whether to enforce canonical `S`/`y` and reject small-order points) — this is genuine and implementer-dependent. The main *pricing/eligibility* caveats are that **Cloud KMS needs billing (Blaze)** and **AWS KMS excludes asymmetric signing from its free tier**. Several options (Functions/Run on Spark; KMS sign input rules; SP 800-57 cryptoperiod values; DSSE PAE bytes) remain **unverified here**.

### Cited Findings
- **Ed25519 disagreements:** implementations differ on checking order/canonicity of inputs ([crypto.SE](https://crypto.stackexchange.com/questions/55656/should-ed25519-signature-verification-check-the-order-and-canonicity-of-its-inpu)); RFC 8032 leaves cofactored vs cofactorless verification as a choice ([`Taming the many EdDSAs`](https://eprint.iacr.org/2020/1244.pdf)); OASIS adopts a strict `0 <= s < L` rule in its ADR ([OASIS ADR 0009](https://docs.oasis.io/adrs/0009-ed25519-semantics)). **These do not fully agree** — pick a strict, tested library and pin it.
- **KMS scope disagreement:** GCP's "Digital signatures" page lists only EC/RSA (plus PQC) for signing and omits Ed25519 ([Digital signatures](https://docs.cloud.google.com/kms/docs/digital-signatures)), consistent with the algorithms page ([Key purposes and algorithms](https://docs.cloud.google.com/kms/docs/algorithms)); the marketing product page phrases the suite as "RSA 2048/3072/4096 and EC P256/P384" without PQC ([product page](https://cloud.google.com/security/products/security-key-management)). Prefer the docs pages.
- **Pricing models differ** (both current as fetched in 2026): GCP bills **per active key version per hour** ($0.000082192/hr SOFTWARE) **plus** per-10k crypto ops ($0.03 SOFTWARE / $0.15 HSM) with rotation free ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)); AWS bills **$1/key/month** (+$1 each for first two rotations) with a 20,000-request free tier that **excludes** asymmetric Sign/Verify/GetPublicKey ([AWS KMS pricing](https://aws.amazon.com/kms/pricing/)). Don't compare headline numbers without the free-tier exclusions.
- **FIPS coverage caveat:** FIPS 186-5 approves algorithms, but library FIPS **validation** is separate; Ed25519-in-FIPS-186-5 does not imply a given Python/OpenSSL build is a validated module.

### Explicit UNKNOWNs (do not guess)
- `AsymmetricSign` input semantics: RSA = digest vs EC = message (VERIFY at `create-validate-signatures`).
- Whether Cloud Functions/Run (signing broker) work on **Spark** or require Blaze.
- Specific **NIST SP 800-57 Pt.1 Rev.5** cryptoperiod values for signature keys (fetch the PDF; Rev.6 is a draft, comments close 2026-02-05).
- Exact **DSSE PAE** byte construction (confirm from the DSSE spec repo).
- Exact current (2026) **GitHub Actions** free-tier/OIDC capabilities for private repos and cloud keyless signing.
- **Render** workload identity / any signed build metadata.
- Per-region availability of the full KMS classical algorithm list at SOFTWARE.
