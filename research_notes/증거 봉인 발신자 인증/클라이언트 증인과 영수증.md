# 클라이언트 증인과 영수증 (Client-side Witnesses and Signed Receipts)

Scope: designs in which the user's device (or an independent third party) holds evidence that a
server *attempted* to perform an account-deletion (withdrawal) operation, so that a compromised or
buggy server that silently omits steps becomes detectable — plus the privacy/legal implications of
keeping such receipts. Target system: a no-build-step web app (Firebase Auth + Firestore, free tier),
server-side deletion with an admin/service credential (revoke tokens → delete Firestore doc → delete
Auth account), optional Firestore tombstone `deleted/{uid}`, and a separate encrypted "evidence
archive" + GitHub issue on failure. Operator is Korea-based (PIPA) serving EU users (GDPR).
Constraint throughout: no paid services; the operator cannot force the user to keep a receipt.

---

## Receipt designs: signed statements, MACs, and double signatures

### Takeaway
A receipt is a small signed (or MAC'd) JSON statement the server returns on the deletion attempt. The
only design that lets the *admin* verify a receipt the *user* presents, while ALSO preventing the
user from forging one, is an **asymmetric signature by the app's deletion key (Ed25519 / ES256),
verified by the admin with a pinned public key**; MAC-based receipts are verifiable only by a key
holder and do not give non-repudiation; the strongest practical variant is a **double signature** —
the app signs the statement and an independent party (an admin/offline CLI key, and/or an RFC 3161
timestamp authority) countersigns to fix when the statement existed.

### Cited Findings
- JWS (RFC 7515) is the standard JSON container for content "secured with digital signatures **or**
  Message Authentication Codes (MACs)" — so the same `{header}.{payload}.{signature}` shape can carry
  either `EdDSA`/`ES256` (asymmetric) or `HS256` (HMAC/symmetric) receipts — [RFC 7515](https://datatracker.ietf.org/doc/html/rfc7515).
- Ed25519 in JOSE is specified by **RFC 8037** (which references **RFC 8032** for the raw EdDSA
  algorithm). NOTE: the task brief cited "RFC 8391/Ed25519"; RFC 8391 is actually the XMSS
  hash-based-signature scheme, not Ed25519 — treat that citation as **incorrect**, correct to RFC 8032/8037 — [RFC 8037](https://www.rfc-editor.org/info/rfc8037/).
- Digital signatures provide **non-repudiation** (only the private-key holder can produce a valid
  signature, so a verifier can hold the signer to it); **MACs do not** provide non-repudiation, because
  every party that shares the symmetric key can produce the same MAC — [Encryption Consulting](https://www.encryptionconsulting.com/hmac-vs-digital-signatures-understanding-the-right-tool-for-the-right-job/); [Crypto StackExchange](https://crypto.stackexchange.com/questions/5646/what-are-the-differences-between-a-digital-signature-a-mac-and-a-hash).
- RFC 3161 defines a Time-Stamp Protocol (TSP) using an X.509 **Time-Stamp Authority (TSA)**; "one of
  the major uses of time-stamping is to time-stamp a digital signature to prove that the digital
  signature was created before a given time" — i.e. a TSA countersignature can bind a receipt to a
  moment and prevent later back-dating — [RFC 3161](https://www.rfc-editor.org/info/rfc3161/).
- W3C Verifiable Credentials (VC) formalize a **three-party model — issuer, holder, verifier** — where a
  credential is tamper-evident and "cryptographically prove[s] who issued it"; this maps to a
  "deletion certificate" issued by the operator, held by the user, verified by a regulator/court — [W3C VC Data Model 2.0](https://www.w3.org/TR/vc-data-model-2.0/).
- Kroll et al., *Accountable Algorithms*: systems can "attest to the valid operation of a decision
  policy **even when all or part of that policy is kept secret**", and accountability is feasible
  without full disclosure of the underlying system — the theoretical basis for the operator asserting
  an operation happened without revealing the archive contents — [Penn Law Review, *Accountable Algorithms*](https://pennlawreview.com/2017/02/23/accountable-algorithms/); [SSRN 2765268](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=2765268).

### Why each alternative fails or wins (analysis)
- **MAC receipt (HMAC/HS256).** The admin (key holder) can verify integrity, but (a) the user cannot
  verify anything, (b) the key is symmetric, so the admin itself — or anyone who obtains the key —
  could forge receipts, and (c) it gives no non-repudiation ([Encryption Consulting](https://www.encryptionconsulting.com/hmac-vs-digital-signatures-understanding-the-right-tool-for-the-right-job/)).
  It also fails the "user must not forge and incriminate the operator" test only *if* the key truly
  never reaches the client; but if the same secret signs and verifies, the trust boundary is weak.
- **Server-signed receipt (Ed25519, admin verifies with a pinned public key).** User cannot forge
  (lacks the private key). Admin verifies offline with the public key. Fits the existing system, which
  already generates an X25519 keypair for the evidence archive and pins the public key in a backend
  env var (per project memory) — a signature keypair can reuse that operational pattern.
  **Limit:** if the signing private key lives on the (compromised) server, the same compromised server
  can emit valid receipts for deletions it never performed — a signature proves *who signed*, not that
  the *state change happened*.
- **Double signature.** App signs, then a second, independent signer countersigns: (i) the admin's
  offline CLI key (the evidence-seal tool already has an offline private key), or (ii) an RFC 3161 TSA
  that timestamps the receipt's hash. This raises the bar: a compromised app server alone cannot
  fabricate a countersigned receipt, and the TSA countersignature fixes time (anti-back-dating) — [RFC 3161](https://www.rfc-editor.org/info/rfc3161/).
  **Cost:** a second key/party to manage; TSA availability/free-of-charge is unverified here (see Gaps).
- **What the server should return.** A compact JWS whose payload includes at minimum: `uid_hash` (a
  salted commitment, never the raw uid — see Privacy section), `status`
  (`deleted` / `deletion_failed`), `server_time`, the client-supplied `nonce`/`challenge`, a `request_id`,
  the `commitment` (hash of the archived state or of a null-archive marker), a key `key_id`, and the
  signature. `status` must distinguish "I attempted and failed" from "I never received the request".
- **Client storage.** No build step and available storage mean: keep the JWS in **localStorage or
  IndexedDB**, and offer an explicit **download / copy / screenshot** affordance because the receipt
  must survive local logout and device change to be a meaningful witness — but see the "users never
  check" obstacle in the omission section.

### Inferences
- Because the app already pins an evidence public key in a backend env var (project memory
  `project_evidence_seal`), adding an Ed25519 receipt key follows an existing, free operational
  pattern; the admin already has an offline CLI whose private key could *be* the verifier's anchor.
- A pure server-signed receipt is the minimum viable design, but it only detects *omission of the
  receipt itself*, not a server that fabricates receipts. Double-signing with an offline/independent
  key is what actually converts "the app claims it deleted" into "an independent party attests to when
  the claim was made".

### Gaps
- Whether a **free, dependable RFC 3161 TSA** exists that is acceptable under a "no paid services"
  constraint is **UNKNOWN** (commercial TSAs and their free tiers were not verified in this pass).
- Whether reusing the *same* Ed25519 key for archive-envelope vs receipt signatures is sound or should
  be domain-separated was not researched (**UNKNOWN**).

## Freshness and replay: binding a receipt to one specific deletion request

### Takeaway
Bind every receipt to a **client-supplied, unpredictable, single-use random challenge (nonce)** and a
server-generated request id/time, all covered by the signature; without this, a receipt issued for one
attempt (or fabricated earlier) can be replayed as proof for a later, genuinely-omitted deletion. A
timestamp-only approach is weaker because it depends on loose clock synchronization and an accepted
window.

### Cited Findings
- A cryptographic **nonce** is "a number used once ... to protect against replay attacks" — [Okta, *What Is a Cryptographic Nonce?*](https://www.okta.com/identity-101/nonce/).
- In a **challenge-response** protocol, one party sends a challenge (e.g. a timestamp or nonce) and the
  other must return a response bound to it; the challenge-response exchange (client nonce, server
  nonce, proofs, signatures) is the standard anti-replay construction — [Rublon, Challenge-Response Authentication](https://rublon.com/blog/challenge-response-authentication/); [Systems Approach, *Authentication Protocols*](https://security.systemsapproach.org/authentication.html).
- Timestamps embedded in messages are an alternative freshness mechanism but require an accepted
  time window and clock-sync assumptions, which is why nonces are preferred where a round trip is
  available — [Systems Approach, *Authentication Protocols*](https://security.systemsapproach.org/authentication.html).

### Design sketch (implementation-oriented)
1. Client generates a 128–256-bit random `nonce` (CSPRNG) at the moment the user presses "delete",
   stores it before sending the request (so it survives a mid-flight failure), and sends it in the
   deletion request body.
2. Server includes, inside the signed receipt payload: `nonce`, `request_id`, `uid_hash`, `server_time`,
   `status`, `commitment`, `key_id`. Because the signature covers `nonce`, a receipt cannot be moved to
   another attempt.
3. The challenge must be **checked for freshness**: the server (or the admin on presentation) records
   seen `(nonce | request_id)` values and rejects duplicates. Otherwise an attacker replays a *valid*
   receipt for a *different, later* request.
4. To keep "attempt" distinct from "success", the sync response should carry the receipt even on
   failure (`status: deletion_failed`), so the user holds evidence of the *attempt* regardless of
   outcome — matching the existing "client mismatch / deletion failure" trigger in the project.

### Inferences
- A nonce makes the ordinary "user submits deletion" flow self-protecting, but replay protection needs
  a small server-side store of consumed nonces (expiring), which is an extra free-tier Firestore/Redis
  burden; alternatively, bind freshness to a short-lived server-issued challenge fetched immediately
  before deletion.
- Binding to the *specific* request also means the receipt should reference the same `request_id` the
  evidence archive would reference, so a later mismatch check is a direct equality test.

### Gaps
- No source found that specifies a recommended nonce length/window for this exact "deletion receipt"
  use case; the values above are standard-practice reasoning, not a cited standard (**UNKNOWN**).

## Detecting omission with receipts, and what the UI must do

### Takeaway
The detection logic is an **equality test**: if the user presents a receipt whose `commitment` has no
matching record in the (ideally independent, append-only) archive store, the mismatch is evidence that
the server skipped the sealing step. But this only works if the archive is not fully server-controlled,
users actually check, and the absence of a receipt is made *visible* — otherwise a compromised server
that simply never issues a receipt is undetectable and the user never notices.

### Cited Findings
- An **append-only, publicly verifiable, Merkle-tree-based transparency log** makes it possible for
  independent parties (monitors/auditors) to detect that something was missing from the log; logs are
  "publicly verifiable, append-only, and tamper-proof" — the property a *server-controlled mutable*
  archive lacks — [Certificate Transparency](https://certificate.transparency.dev/); [Wikipedia, Certificate Transparency](https://en.wikipedia.org/wiki/Certificate_Transparency).
- Practical GDPR-deletion practice reported by operators: because purging backups is impractical,
  teams "kept a record of every deletion request in a separate db" — i.e. a durable deletion ledger is
  a common, low-tech "witness" — [r/gdpr discussion](https://www.reddit.com/r/gdpr/comments/1rvwpzt/how_do_you_prove_that_data_deletion_actually/).
- Verifiable data structures (e.g. Trillian) provide append-only logs and verifiable maps used for
  transparency/accountability, including Key Transparency — [Trillian, *Verifiable Data Structures*](https://transparency.dev/verifiable-data-structures/).

### Practical obstacles (and honest limits)
- **The archive is server-controlled.** A compromised server can delete the matching archive record,
  or never write it. The receipt only yields a *detectable mismatch* if the archive (or at least its
  index/commitments) is written to somewhere the app server cannot silently rewrite — e.g. an
  append-only log, a separate credential/account, or a public artifact. Without that, a receipt proves
  the server *said* it did something, not that it did.
- **Users never check.** A receipt that lives in localStorage is only a witness if presented. Design
  must not assume the user ever returns.
- **Receipts are lost.** Logout, cache clears, device loss destroy localStorage/IndexedDB; a receipt
  that can be re-downloaded from the (possibly compromised) server is not independent evidence, so the
  user must be *nudged to save a copy* at the moment of deletion.
- **The server can refuse to issue a receipt — and then what does the user observe?** This is the core
  blind spot. If a "successful" deletion returns **no receipt**, the honest reading is *uncertainty,
  not success*. So the UI must invert the default: **never show "your account was deleted" as success
  unless a receipt was received and stored**; a missing receipt must be surfaced as an explicit
  "could not obtain deletion proof / status unknown" state, with the request id and a retry/report
  affordance. This converts an invisible omission into a visible user-observable anomaly, which is the
  only thing a compromised server cannot hide (it must either issue a receipt or show "no receipt").
- **Android/iOS free-tier caveat is not the issue here**; this is a browser app, but note per project
  memory that the receipt's `uid_hash` must never be the raw uid.

### Inferences
- The strongest cheap witness in this system is to **make the receipt itself the success signal**: the
  client treats "deletion succeeded" as a function of "receipt received *and* stored", not of the HTTP
  200. That single UI rule detects full-server-omission (no receipt) and can be implemented without any
  new backend dependency.
- Because the app already opens a GitHub issue (metadata-only) on failure, a *periodic* reconciliation
  (receipts presented → archive records) can double as a detection mechanism, but it, too, depends on
  users presenting receipts.

### Gaps
- No source quantifies how often end users retain or present such proofs; effectiveness against a
  never-checking population is **UNKNOWN** and likely low, which is an argument for the third-party
  witnesses below.

## Privacy and data minimization (GDPR Art. 17 / PIPA), and the regulatory framing of "deletion confirmation"

### Takeaway
The receipt and any archive/tombstone that references a deleted uid are themselves **residual personal
data** and must be minimized: store a **salted (keyed) hash of the uid**, keep the receipt
**primarily on the user's device**, make it **short-lived** where a server side is unavoidable, and
frame it to the user as a "deletion certificate". Neither GDPR nor (as far as found) PIPA literally
mandates issuing a *certificate to the data subject* — GDPR requires erasure + accountability
(Art. 5(2)), and Korea's PIPA/표준지침 require timely, irreversible destruction — so a certificate is a
*design choice* for accountability, not a mandated artifact.

### Cited Findings
- **GDPR Art. 17** requires the controller to erase personal data "without undue delay" on the listed
  grounds, and to take reasonable steps to inform other controllers where data was made public — [GDPR Art. 17](https://gdpr-info.eu/art-17-gdpr/).
- **ICO (UK GDPR)** guidance: individuals can request erasure verbally or in writing; the controller
  must respond **within one month**, telling the individual "whether you have erased the data ... or
  that you have refused"; backups must be put **"beyond use"** even if not immediately overwritten, and
  the controller "must be absolutely clear with individuals as to what will happen to their data ...
  including in respect of backup systems" — [ICO, Right to erasure](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/).
- **Accountability principle (Art. 5(2))** — the controller "shall be responsible for, and be able to
  demonstrate compliance with" the processing principles (incl. Art. 5(1)(f) integrity and
  confidentiality) — is the legal hook that justifies keeping a *minimal* deletion record — [GDPR Art. 5](https://gdpr-info.eu/art-5-gdpr/).
- **Korea PIPA 제21조(개인정보의 파기)**: a personal-information controller must destroy personal data
  "지체 없이" (without delay) once it is no longer needed, and destruction must be done so that the
  data cannot be recovered or regenerated (복구 또는 재생되지 않도록) — [개인정보 보호법 제21조 (law.go.kr)](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1027063705).
- **표준 개인정보 보호지침** prescribes concrete destruction timing (e.g. destroy within **5 days** in
  specified cases) and methods, operationalizing Art. 21 — [표준 개인정보 보호지침 (law.go.kr, 행정규칙)](https://www.law.go.kr/LSW//admRulInfoP.do?admRulSeq=2100000257592&chrClsCd=010201).
- **Crypto-shredding** (destroying the encryption key rather than the ciphertext) is an accepted
  deletion technique for making data unrecoverable; Google Cloud's own deletion pipeline describes
  "cryptographic erasure" in Cloud Storage and commits to deleting customer data within ~**180 days** —
  [Seald, crypto-shredding](https://www.seald.io/blog/data-destruction-using-crypto-shredding); [Google Cloud, Data deletion on Google Cloud](https://docs.cloud.google.com/docs/security/deletion).
- **Firebase re-auth semantics**: security-sensitive client actions such as `deleteUser` require
  **recent re-authentication**, and the client SDK can only delete the **currently signed-in** user —
  [Firebase Auth, Manage Users (web)](https://firebase.google.com/docs/auth/web/manage-users).
- **Data keyed on the uid survives auth deletion**: "Every Firestore document, Storage object, and
  Realtime Database node keyed on that UID stays until you delete it yourself" — so deletion is
  multi-step and any residual uid reference is residual personal data — [runxbuild, Deleting a Firebase Auth Account Properly](https://www.runxbuild.com/blog/delete-auth-account-from-firebase/); server-admin nuances — [Firebase Admin, Manage Users](https://firebase.google.com/docs/auth/admin/manage-users).

### Data-minimization options (comparison)
- **Salted/keyed uid commitment.** Receipt and archive store `HMAC(uid, salt)` or `H(uid ‖ salt)`
  rather than the uid. If the salt stays user-side (or is per-receipt and discarded), the archived hash
  is not linkable back to a person; if the controller retains the salt, the value is *pseudonymous*
  (still personal data, Art. 4(5)) — [GDPR Art. 5](https://gdpr-info.eu/art-5-gdpr/) (principle of data minimisation/accuracy framing).
- **Receipt stored only on the user's device.** Eliminates a server-side residual copy entirely; cost
  is that the operator cannot re-issue a lost receipt and detection depends on the user presenting it.
- **Short-lived receipts / TTL.** Where a server-side copy or a tombstone exists, set a TTL (the
  project already plans Firestore TTL on the archive; the tombstone is currently indefinite). Cost:
  after expiry the mismatch check is impossible.
- **Deletion certificate as a user-facing artifact.** Present the receipt to the user as a named,
  downloadable "deletion certificate" (VC-shaped: issuer=operator, holder=user, verifier=regulator/
  court) — [W3C VC Data Model 2.0](https://www.w3.org/TR/vc-data-model-2.0/). Selective disclosure
  (e.g. SD-JWT/BBS+) could reveal "deletion happened at T" without revealing the uid, matching the
  data-minimization goal — [W3C VC Data Model 2.0](https://www.w3.org/TR/vc-data-model-2.0/).

### Inferences
- The current tombstone `deleted/{uid}` (uid + time, *indefinite*) is itself residual data; adopting an
  `HMAC(uid, salt)` tombstone would let the "403 account_deleted" check keep working while reducing the
  residual footprint, at the cost of holding the salt (making it pseudonymous, not anonymous).
- Because GDPR Art. 5(2) rewards *demonstrable* compliance, a minimal, hashed deletion ledger is
  defensible; the safest framing is "we keep the least information needed to prove we erased you" —
  which is exactly a salted-hash receipt + short TTL.

### Gaps
- Whether **PIPA / 표준지침 explicitly require issuing a deletion *confirmation or certificate* to the
  data subject** (as opposed to only destroying the data and keeping internal records) was **not
  verified** — only the destruction obligation and timing were found (**UNKNOWN**).
- Exact **EDPB** guidance text on what a deletion response must "document" was not retrieved in this
  pass (**UNKNOWN**); only the ICO formulation (state whether erased or refused, within one month) was
  confirmed.

## Third-party / independent witnesses that do not require the client

### Takeaway
Witnesses that live *outside* the user's device and *outside* the app server's control are the only ones
robust to a user who never checks: an external scheduled prober, a scheduled "canary" account deletion,
and a public/append-only status artifact. Each detects *systemic* (scheduled, aggregate) omission but
**misses** per-user silent omissions, and all of them still depend on the prober/artifact being hosted
somewhere the compromised server cannot rewrite.

### Cited Findings
- Transparency-log monitors are the canonical "independent observer" pattern: an append-only log plus
  third-party monitors/auditors who detect *missing* or *unauthorized* entries — [Certificate Transparency](https://certificate.transparency.dev/); [Let's Encrypt, CT Logs](https://letsencrypt.org/docs/ct-logs/).
- Key Transparency / verifiable maps use append-only verifiable logs to let clients and auditors verify
  server state without trusting the server — [Trillian, *Verifiable Data Structures*](https://transparency.dev/verifiable-data-structures/); [Mollakuqe et al., *Algorithm for Key Transparency with Transparent Logs* (PMC)](https://pmc.ncbi.nlm.nih.gov/articles/PMC11585852/).
- Kroll et al. establish that accountable systems can attest to correct operation even when the policy
  is secret, which supports a prober/attestor that checks an operation occurred *without* exposing user
  data — [Penn Law Review, *Accountable Algorithms*](https://pennlawreview.com/2017/02/23/accountable-algorithms/).

### What each witness detects / misses
- **Scheduled external prober (synthetic monitor).** An independent cron periodically calls a
  dry-run/health/attestation endpoint (or the deletion path against a test tenant) and asserts the
  tombstones + archive entries + receipts are being produced. Detects: the server silently dropping the
  whole sealing pipeline (systemic). Misses: one user's deletion failing while the pipeline otherwise
  works; and it sees nothing if the prober itself is hosted in the compromised environment.
- **Canary account deletion on a schedule.** A dedicated, monitored account is really deleted on a
  schedule by an external runner; success is defined by observing the expected external artifacts
  (auth gone, tombstone present, receipt verifiable). Detects: systemic breakage and regressions.
  Misses: per-user data omission and any failure that the canary's privileged path bypasses; also
  creates its own residual records.
- **Public status artifact / append-only log.** A heartbeat or Merkle-root publication of the deletion
  ledger that a monitor can verify for *inclusion/consistency*. Detects: log tampering or truncation
  and relative omission (a receipt whose commitment is absent). Misses: an omission that never entered
  the log, and it costs a separate, non-server-controlled host — with project-memory constraints
  (no Blaze/Storage, GitHub issue bodies are metadata-only with a 65536-char limit), the free hosting
  options are limited.

### Inferences
- These witnesses catch the *class* of failure ("the sealing/receipt machinery is off") but not the
  *instance* ("this user's account). They are complements, not replacements, for the client-held
  receipt.
- Given the free-tier/GitHub limits from project memory, the cheapest genuinely-independent witness is
  an off-repo external cron that verifies a *published* commitment/heartbeat; anything hosted inside
  the same Render/Firebase project is not independent of a compromised app server.

### Gaps
- No free-tier, server-independent append-only store was confirmed for this stack in this pass
  (**UNKNOWN**); project memory documents why Storage/GitHub-repo options were rejected, but a
  drop-in free replacement was not identified here.

## Comparison table — mechanism → who holds evidence → attacker caught → user-visible behavior → privacy cost → implementation size

Implementation-size is a rough estimate for this specific stack (small Python backend, no-build
frontend): **S** ≈ a few dozen lines, **M** ≈ a module + tests, **L** ≈ new external component/ops.

| Mechanism | Who holds the evidence | Attacker caught | User-visible behavior | Privacy cost (residual data) | Impl. size |
|---|---|---|---|---|---|
| Server-signed receipt (Ed25519/ES256 JWS) | App server signs; **user's device** stores it; admin verifies with pinned public key | Server that omits the *receipt*; user forgery | "Deletion receipt saved" vs "no receipt" | Salted `uid_hash` + timestamp on the device; none server-side if device-only | M |
| MAC receipt (HMAC/HS256) | Admin/operator holds the key; user cannot verify | Integrity failures only; **not** non-repudiation | User sees a token but cannot check it | Same as above, but key management risk | S–M |
| Double signature (app + admin/offline CLI key, or app + RFC 3161 TSA) | User holds receipt; app signs; **independent party** countersigns | Fabricated receipts by a compromised app server; **back-dating** | Receipt shows two signatures / a timestamp | Adds a timestamp token; still salted hash | M–L |
| Client-signed challenge (client key) | User signs their own request; server countersigns | Proves the *user* attempted (anti-forgery by server), not that server acted | User sees a signed acknowledgement | Client keypair to manage | M |
| Append-only transparency log entry (CT-style) | Anyone can verify; monitors detect omission | Log tampering/truncation; *relative* omission | Public/monitor-visible inclusion proof | Hash-only entries; needs an independent host | L |
| External scheduled prober / canary deletion | **Independent prober** | Systemic omission of the whole pipeline; regressions | Status page / alert only (not per-user) | Canary account creates its own records | L |
| Public status artifact (heartbeat / published Merkle root) | Independent monitor | Server stopped, or log rewritten | Public status; not per-user | Minimal if hash-only | L |
| Deletion certificate as W3C VC | User (holder); operator (issuer); regulator/court (verifier) | Omission + unauthorized issuance; supports selective disclosure | User keeps a named, verifiable certificate | Salter-hash + selective disclosure minimizes | M–L |

### Bottom line for this system
The realistic, free, incremental stack is: **(1)** server returns a signed, nonce-bound receipt even on
failure (Ed25519, admin-verifiable with a pinned key); **(2)** the client stores it and treats
"success" as "receipt received and saved", surfacing "no receipt" as uncertainty; **(3)** add an
independent, off-project scheduled prober so a never-checking population still detects systemic
breakage; **(4)** keep only `HMAC(uid, salt)` + time, short TTL. State plainly that a compromised server
that refuses to issue receipts remains undetectable by any client-only design, and that full detection
requires an independent witness the server cannot rewrite.

- A free, **server-independent append-only store** for this stack — **UNKNOWN**.
- Any study quantifying **user behavior** (how many users retain/present a deletion receipt) — not
