# 누락 탐지와 투명성 로그 (Omission-Detectable Logging / Transparency Logs)

> **적용 대상 시스템(고정 전제)**: Render 위의 FastAPI 앱이 "탈퇴 실패/부분 완료" 시 Firestore(≤1MiB 청크 문서)에 증거 아카이브를 쓰고 GitHub 이슈(메타데이터만)를 연다. 쓰기 자격증명은 앱이 쥔 Google 서비스계정 키. 보안 규칙은 클라이언트만 막고 admin SDK는 규칙을 우회한다. 관리자는 오프라인 CLI와 앱이 읽을 수 없는 비밀을 쥘 수 있다. 위협: **공격자가 앱을 장악해 실패한 탈퇴의 아카이브를 애초에 생성하지 않거나(또는 삭제) 아무도 모른다.**
>
> 이 노트는 "탬퍼링"이 아니라 **누락(omission)** 을 탐지 가능하게 만드는 메커니즘의 실제 전제조건·한계·판정을 정리한다. 모든 사실에 출처를 붙이고, 확인 못 한 것은 **UNKNOWN**으로 표시한다.

## 핵심 질문 1 — 원리적으로 무엇이 누락을 탐지 가능하게 하는가 (탐지 클래스)

### Takeaway
**append-only 구조 자체는 누락을 탐지하지 못한다.** Merkle 트리·해시체인은 "이미 본 head를 기준으로 되돌리기/수정/삭제/재정렬"을 탐지할 뿐이며, 애초에 **추가되지 않은** 항목은 "일어나지 않은 사건"과 구별할 수 없다. 누락 탐지에는 반드시 (A) 그 사건이 일어났음을 로그 시스템 **외부에** 아는 독립 증인, 또는 (B) 사전에 주입된 기대치/카운터/커밋먼트 중 하나가 필요하다.

### Cited Findings
- Trillian은 투명 로그가 **inclusion proof**(항목이 특정 트리 head에 포함됨의 증명)와 **consistency proof**(한 head가 다른 head의 prefix임의 증명)를 제공하지만, **삭제된 leaf의 누락/대체는 "로그 내용을 가져간 monitor에게만" 가시적**이라고 명시한다(각주 3: "the omission/replacement would be visible to a monitor that retrieved the log contents") — [Trillian, Transparent Logging: A Guide](https://google.github.io/trillian/docs/TransparentLogging.html).
- CT의 consistency proof는 "tree #2가 tree #1에 항목을 덧붙인 결과(=tree #1이 prefix)"임을 증명한다 — [rozbb/ct-merkle README](https://github.com/rozbb/ct-merkle).
- tamper-evident 로그 시스템은 (1) 각 서명된 로그 **내부**의 탬퍼링 탐지와 (2) **서로 다른 로그 인스턴스가 불일치 주장을 하는 경우** 탐지, 둘 다 필요하다 — [Crosby & Wallach, "Efficient Data Structures for Tamper-Evident Logging" (USENIX Security '09)](https://www.usenix.org/legacy/events/sec09/tech/full_papers/crosby.pdf).
- Go 체크섬 DB는 로그 서버가 신뢰받지 않으며, 클라이언트가 "관측한 로그가 이전에 관측한 로그에서 레코드를 **떨어뜨리지 않는다**"를 스스로 검증한다고 서술한다(클라이언트가 로컬 timeline 유지) — [Go sumdb proposal](https://go.googlesource.com/proposal/+/master/design/25530-sumdb.md).
- 정족수/증인 모델: "witness cosigning"은 권위자의 비밀키가 침해돼도 **사후가 아니라 사전적(proactive)** 투명성을 제공한다 — [Syta et al., "Keeping Authorities Honest or Bust"](https://arxiv.org/html/1503.08768v4).
- AWS CloudTrail은 **API 활동이 없는 한 시간에도 빈 digest 파일(logFiles: [])을 배달**한다고 명시한다("you need to assert that no log files were delivered during the hour") — [AWS CloudTrail digest file structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html). 이는 "아무 일도 없었음"을 주장하는 **음성 증거**의 표준 구현 예시다.

### Inferences
- 누락 탐지의 필요충분 조건(실무적): **(독립 증인 또는 사전 커밋먼트) ∧ (로그 head의 pin 또는 관리자측 기대 카운트)**. 둘 중 하나라도 없으면 완전 침해된 앱은 조용히 아무것도 안 쓰고 끝낼 수 있다.
- 따라서 이 시스템의 경우, 앱이 스스로 트리거("탈퇴 실패")를 판정하고 스스로 기록하는 한 **앱 단독으로는 누락을 탐지 불가**하다. 클라이언트(사용자 브라우저)가 "탈퇴를 눌렀다"는 사실을 아는 유일한 독립 증인 후보다.
- 클래스 분류(구현 관점):
  1. **독립 증인**: 이벤트 발생을 아는 제2의 관측자(클라이언트 기기/제2 서비스/외부 스케줄러). 전제: 증인이 로그 시스템 자격증명과 **독립**이고, 관측을 로그 밖 채널로 남길 수 있어야 함.
  2. **append-only 구조 + head pin**: Merkle 트리/해시체인. 전제: 이전에 본 head를 **누군가 기억**해야 함(consistency proof). pin 없으면 전체 rollback 가능.
  3. **사전 커밋먼트**: 사전 주입 카운터/nonce/"탈퇴 N건 이상" 기대치. 전제: 커밋먼트가 앱 쓰기 권한 밖.
  4. **gossip/split-view 탐지**: 서로 다른 관측자 간 불일치 비교. 전제: 다수·독립 관측자, 저지연 교환.
  5. **주기적 체크포인트 관리자 검증**: 관리자가 주기적으로 head/카운트를 검증하고 퇴행 시 소리내어 실패. 전제: 체커 자체의 **liveness/heartbeat**(체커를 끄면 그것도 탐지돼야 함).

### Gaps
- "누락 탐지"를 정면으로 정리한 단일 표준 문서는 찾지 못함(대부분 "tamper-evidence"로 뭉뚱그림). 위 필요조건은 조각(Trillian 각주 3, sumdb timeline, CloudTrail empty digest)들을 종합한 **추론**이며 단일 출처로 인용 불가.
- 순수 정보이론적 한계(증인 없이 누락이 원리적으로 불가능함의 형식 증명)는 이번 조사에서 1차 출처를 확보하지 못함 → UNKNOWN.

## 핵심 질문 2 — 투명성 로그 설계별 보장·신뢰 앵커·운영 비용

### Takeaway
RFC 6962/Sigsum/sumdb/Rekor는 "**롤백·split-view·변조**"를 탐지·방지하는 데 강하지만, **"기록되어야 했는데 안 된" 누락**은 각 설계의 admission/제출 측에 독립 증인이 있을 때만 잡힌다. hobby 규모에서 **무료에 가까운 유일한 실전 옵션은 Sigsum(증인 cosigning + monitor)** 이고, WORM(Cloud Storage Bucket Lock/S3 Object Lock)은 "삭제"는 막지만 "누락"은 못 막는다.

### Cited Findings
- **RFC 6962 (CT)**: 로그는 Merkle 트리(RFC 6962 §2.1, §3.4 leaf/node hashing; leaf = SHA-256(0x00 ‖ …), node = SHA-256(0x01 ‖ …)), 로그 서명 공개키로 서명한 **Signed Tree Head (§3.5)**; 클라이언트 메시지: §4.1 add-chain, §4.2 add-pre-chain, **§4.3 get-sth**, **§4.4 get-sth-consistency**, **§4.5 get-proof-by-hash**, **§4.6 get-entries** — [RFC 6962](https://www.rfc-editor.org/info/rfc6962/); [RFCinfo RFC-6962 목차](https://rfcinfo.com/rfc-6962/). 보장: 트리 head pin 하에 append-only·inclusion. 신뢰 앵커: 로그 공개키 + monitor + gossip.
- **RFC 9162 = CT v2**로 RFC 6962를 갱신/대체 — [draft-ietf-trans-rfc6962-bis-35](https://datatracker.ietf.org/doc/html/draft-ietf-trans-rfc6962-bis-35). (정확한 절 번호는 이번 조사 미확보 → UNKNOWN.)
- **Trillian**: CT 아디이디어를 임의 데이터로 일반화; leaf Merkle hash 기본값 `SHA-256(0x00 ‖ leaf.LeafValue)`, identity hash로 중복 방지; **inclusion promise(SCT)** vs **inclusion proof** 구분; read/write-transparency — [Trillian 가이드](https://google.github.io/trillian/docs/TransparentLogging.html). 비용: MySQL/Spanner 등 별도 저장소 필요.
- **Sigsum**: 서명 체크섬의 투명 로그. Ed25519, **증인 cosigning**, **trust policy = 로그 키 + 증인 키들 + quorum 규칙**(예: 3명 중 2명 이상이 append-only를 확인해야 신뢰); `sigsum-monitor`가 로그에서 서명 체크섬을 다운로드해 "내 서명키가 쓰였음"을 탐지; proof는 witness cosignature 라인을 지우면 검증 실패; 테스트 정책/공개 증인 존재(`poc.sigsum.org/nisse`, `rgdd.se/poc-witness`, `witness1.smartit.nu/witness1`) — [Sigsum Getting started](https://www.sigsum.org/getting-started/). 신뢰 앵커: 사용자 소프트웨어·monitor에 설정된 **trust policy**. 비용: OSS·Go 툴체인, 테스트 로그/증인은 무료.
- **Go 체크섬 DB (sum.golang.org)**: Trillian 기반 투명 로그; 엔드포인트 `/latest`(서명된 tree size·hash), `/lookup/M@V`, `/tile/H/L/K`. `go` 명령이 `$GOPATH/pkg/sumdb/<name>/latest`에 최신 signed tree size/hash를 캐시하고, **불일치를 관측하면 stderr에 크게 불평하고 빌드 실패**; `go clean -modcache`도 latest는 못 지우며 `rm -rf $GOPATH/pkg`만 지운다(타임라인 기억의 핵심); 프록시가 gossip 소스가 됨 — [Go sumdb proposal](https://go.googlesource.com/proposal/+/master/design/25530-sumdb.md). 신뢰 앵커: sum.golang.org 키 + **클라이언트 로컬 timeline**. 비용: Google이 운영(자체 운영 아님).
- **sigstore/Rekor**: 서명 메타데이터용 투명 로그, inclusion·consistency proof + **SET(Signed Entry Timestamp)**; v2(2025-10 GA)에서 "proof와 함께 서명 타임스탬프를 반환하지 않고" 별도 타임스탬프 서비스로 분리, 타일 기반 로그로 전환 — [Rekor overview](https://docs.sigstore.dev/logging/overview/); [Rekor v2 GA](https://blog.sigstore.dev/rekor-v2-ga/). witness 필요성 및 Ethereum witness 실험 — [su3.io "Witnessing Sigstore's transparency log"](https://su3.io/posts/witnessing-sigstore-from-ethereum). 신뢰 앵커: Rekor 로그 키 + witness.
- **immudb**: "cryptographic proof & verification 내장", append-only, SDK가 **마지막으로 검증한 상태**를 추적해 새 상태를 매번 암호검증 — [immudb.io](https://immudb.io/); [GitHub codenotary/immudb](https://github.com/codenotary/immudb). 신뢰 앵커: 클라이언트가 보관하는 마지막 검증 상태(외부 anchor 아님). 비용: OSS 자체 호스팅(영구 디스크 필요).
- **AWS CloudTrail digest files**: 시간당 digest가 log 파일들의 SHA-256과 **이전 digest의 hash + 서명(previousDigestHashValue / previousDigestSignature)** 을 담아 체이닝 → **digest 파일 삭제 탐지**; 서명은 리전별 RSA 키, `ListPublicKeys` API로 공개키 조회; 검증 비활성화 시 **체인이 1시간 뒤 끊김**; 시작 digest는 previous 필드가 null — [digest file structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html); [integrity validation intro](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-intro.html). 신뢰 앵커: AWS 리전 공개키.
- **AWS S3 Object Lock**: governance 모드 = 특수 권한(`s3:BypassGovernanceRetention`) 보유자는 삭제/단축 가능; **compliance 모드 = root user 포함 누구도 재정의·삭제 불가** — [S3 Object Lock userguide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html); [S3 Object Lock feature](https://aws.amazon.com/s3/features/object-lock/). 비용: S3 free tier(5GB, 12개월)로는 장기 보존 부적합(UNKNOWN 세부).
- **GCS Bucket Lock**: 버킷 retention policy는 기존·신규 객체 모두에 소급 적용, **lock하면 정책 제거/단축 불가(비가역)**, bucket 삭제도 전 객체가 retention을 채울 때까지 불가, lock 시 프로젝트에 **lien**이 걸려 `resourcemanager.projects.delete` 차단 — [GCS Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock). 신뢰 앵커: Google.
- **CT monitor 실사례**: monitor가 로그에 포함된 인증서를 암호학적으로 검사하고 구독 기반 알림 제공 — [certificate.transparency.dev/howctworks](https://certificate.transparency.dev/howctworks/); [Cloudflare CT Monitoring GA](https://blog.cloudflare.com/certificate-transparency-monitoring-ga/).

### Inferences
- **누락 관점 판정**: 이들 로그는 CT에서조차 "제출되지 않은 인증서"의 누락을 잡지 못한다(monitor는 로그에 **있는** 것을 스캔). 누락은 "CA가 서명했는데 로그에 안 넣음"이라는 **제출 측 이탈**이며, 이를 잡으려면 별도 증인(브라우저/제2 로그)이 필요하다. sumdb가 "DB가 응답 못 하면 하드 실패"로 설계한 이유도 이 이탈 탐지 때문이다([proposal](https://go.googlesource.com/proposal/+/master/design/25530-sumdb.md)).
- 이 시스템에 가장 현실적인 무료 옵션은 **Sigsum**이다: 로그 자체를 우리가 안 돌려도 공개 테스트 로그/증인을 쓸 수 있고, `sigsum-monitor` 패턴이 "증거 아카이브 해시가 로그에 올라왔는가"를 관리자가 검증하는 모델과 정확히 일치한다. 단, **비밀 누출 문제** 때문에 아카이브 원문이 아니라 **해시/커밋먼트만** 로깅해야 한다(Sigsum은 체크섬을 로깅하므로 적합).
- immudb/Trillian은 별도 저장소(영구 디스크/DB)가 필요해 Render 무료 티어와 상충 → 이 프로젝트의 "Firestore-only, free" 제약에서 **부적합**.

### Gaps
- RFC 9162(CT v2) 정확한 절 번호와 RFC 6962와의 매핑 → UNKNOWN.
- Sigsum 공개 증인/로그의 **가용성 SLA·지속성·요율 제한** → UNKNOWN(테스트/데모 성격). 운영용 `sigsum-generic-*` 정책의 실제 증인 이력은 미확인.
- immudb를 Render 무료 인스턴스에서 영구 저장으로 운영 가능한지 → UNKNOWN.
- CT 로그 1개 운영의 실측 월 비용 규모(정성적으로 "대규모") → 구체 수치 UNKNOWN.
- free tier 한도(S3 Object Lock, GCS Bucket Lock 선행 Blaze 요건)의 최신 세부 → 부분 확인, 표로 정리했으나 플랫폼별 최신 단가 재확인 필요.

## 핵심 질문 3 — 해시체인의 anti-rollback / freshness

### Takeaway
해시체인/Merkle의 append-only성은 **이전에 관측한 head를 pin**할 때만 anti-rollback이 된다. pin을 앱 쓰기 권한 밖(관리자, 외부 카운터, 하드웨어)에 두고, **독립 witness가 cosign**하며, **체커 자체의 liveness**까지 감시할 때 비로소 freshness가 생긴다. forward-secure logging은 "과거 항목 위조"를 막지만 **애초에 추가되지 않은 항목의 누락은 막지 못한다.**

### Cited Findings
- forward integrity(forward-secure audit log): 현재 키가 침해돼도 **과거 로그 항목은 위조 불가**(키 진화). Bellare & Yee가 forward integrity를 정의 — [Forward Integrity For Secure Audit Logs (Semantic Scholar)](https://www.semanticscholar.org/paper/Forward-Integrity-For-Secure-Audit-Logs-Bellare-Yee/a63ffbb0e928e4cfefb245e65d370e2e2e4e81e8). LogFAS는 "online·fast detection 없이도 공개 검증 가능한 forward-secure·append-only 서명"을 산출 — [LogFAS (FC'12)](https://fc12.ifca.ai/pre-proceedings/paper_23.pdf). Balloon은 forward-secure append-only PAAS — [Balloon](https://www.researchgate.net/publication/300251362_Balloon_A_Forward-Secure_Append-Only_Persistent_Authenticated_Data_Structure).
- journald의 forward-secure log sealing: **과거 항목 무결성**을 보장하는 기법(공격자가 로그를 청소하는 것 방지) — [eprint 2023/867](https://eprint.iacr.org/2023/867.pdf). → 즉 목적은 "기존 항목 보호"이지 "누락 탐지"가 아님.
- witness cosigning: 다수 독립 witness의 cosignature를 클라이언트가 **통신 없이 효율적으로** 검증 가능, 권위자 키 침해 시에도 proactive 투명성 — [Syta et al.](https://arxiv.org/html/1503.08768v4). Trillian 기반 "System Transparency Logging"이 gossip-audit 모델의 증인 cosigning을 구현 — [SWITS 2021 paper](https://swits.hotell.kau.se/AnnualSeminars/SWITS%202021/SWITS_2021/SWITS_2021_paper_17.pdf).
- Sigsum의 정족수 규칙: witness들이 "로그가 오직 새 항목만 덧붙임"을 암호검증, **2/N 이상이 검증해야 신뢰**; witness를 제거하면 proof 검증 실패 — [Sigsum Getting started](https://www.sigsum.org/getting-started/)
- Go sumdb anti-rollback의 실전 패턴: 로컬에 latest tree size/hash를 캐시하고 `go clean -modcache`로도 못 지움(`rm -rf $GOPATH/pkg`만 가능) → **타임라인 불일치 탐지**; 프록시 gossip 지원 — [Go sumdb proposal](https://go.googlesource.com/proposal/+/master/design/25530-sumdb.md).
- CloudTrail: 검증을 끄면 **1시간 뒤 체인 단절**, 재개 시 시작 digest 생성; 예상치 못한 서비스 장애/버킷 정책 오류로 일부 digest 미배달 가능 → `get-trail-status`의 `LatestDigestDeliveryError` 확인, 이후 재배달 — [digest file structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html). (freshness/liveness 실패 모드의 실제 예.)
- CT는 주기적으로 현재 tree head를 서명(STH) — [draft rfc6962-bis](https://datatracker.ietf.org/doc/html/draft-ietf-trans-rfc6962-bis-35).

### Inferences
- **신뢰시계(trusted clock) 문제**: STH/checkpoint의 timestamp는 로그(또는 앱)의 시계를 신뢰한다. witness cosignature는 append-only만 증명하고 **시각을 증명하지 않는다**. 앱이 시계를 조작하면 backdating 가능 → freshness는 시각이 아니라 **단조 증가 카운터/head**에 의존해야 안전하다. (CloudTrail의 digestStart/EndTime도 AWS 시계 기반.)
- **단조 카운터를 앱 밖에** 두는 것이 핵심: 앱이 감소시킬 수 없어야 rollback이 탐지된다. 무료 옵션: (a) 공개 git repo의 커밋(=GitHub가 순서 보존, force-push는 히스토리로 탐지 가능), (b) 관리자 오프라인 서명 체크포인트, (c) 제2 서비스의 카운터.
- **witness/cosigner 실무**: Sigsum은 무료 공개 증인을 쓸 수 있으나 우리 증거 원문을 로깅하면 프라이버시 문제 → **커밋먼트(해시)만** 로깅해야 함. Trillian witness는 자체 인프라가 필요해 무료 제약에서 부담.

### Gaps
- 앱이 자체 시계를 조작하는 경우를 막는 검증 가능한 타임스탬프(예: RFC 3161 TSA, 공개 witness 타임스탬프)의 **무료 실현성** → UNKNOWN.
- forward-secure logging이 "누락"을 못 막는다는 명시적 문헌 진술을 1차 출처로 확보 못 함(대부분 "tampering/modification" 초점) → 위 결론은 추론.
- Trillian witness / CT gossip을 소규모 단일 운영자가 굴리는 구체 런북/비용 → UNKNOWN.

## 핵심 질문 4 — 저장 자격증명이 앱 자신일 때: append-only를 강제할 수 있는가 (Firestore/Google Cloud)

### Takeaway
**Firestore Security Rules는 서버 클라이언트 라이브러리(admin SDK)에 적용되지 않는다** — admin SDK는 ADC/서비스계정으로 인증하며 모든 규칙을 우회한다(문서 명시). IAM으로 막을 수 있으나 **Firestore IAM 권한은 프로젝트/DB 단위로만** 세분화되고 **문서/컬렉션 단위 조건은 없다**. 즉 "create-only(생성만, update/delete 불가)" **별도 최소권한 자격증명은 달성 가능**하다(커스텀 롤 + IAM Deny로 이중 방어). WORM/prefix 단위 최소권한은 **Cloud Storage에서만** 가능하지만 **신규 버킷은 Blaze 필요 → 무료 아님**.

### Cited Findings
- Firebase 공식: "**서버 클라이언트 라이브러리는 모든 Cloud Firestore 보안 규칙을 우회**하고 Google Application Default Credentials로 인증한다" — [Get started with Firestore Security Rules](https://firebase.google.com/docs/firestore/security/get-started).
- Google 공식(서버 클라이언트): Firestore IAM 권한 표에서 문서 연산 권한은 프로젝트 범위 `datastore.entities.create` / `.update` / `.delete` / `.get` / `.list` 뿐이며 문서/컬렉션 이름 조건은 언급 없음 — [Security for server client libraries (Firestore Native)](https://docs.cloud.google.com/firestore/native/docs/security/iam).
- 같은 문서: **커스텀 롤**로 원하는 권한만 지정 가능("If the predefined roles don't address your business requirements, you can define your own custom roles with permissions that you specify"); IAM Conditions로 **하나 이상의 데이터베이스 접근**을 조건화 가능("Configure database access conditions"); IAM 권한 캐시로 **롤 변경 반영에 최대 5분** — [동일 문서](https://docs.cloud.google.com/firestore/native/docs/security/iam).
- 문서 단위 IAM은 불가하다는 커뮤니티 근거: "IAM can(not) be used to control access to specific documents. To implement fine grained access control, have a look at Firestore [규칙]" — [StackOverflow](https://stackoverflow.com/questions/77176409/is-it-possible-to-only-give-access-to-certain-documents-in-firestore-native-mode); "conditional access based on resource name is not supported for Cloud Datastore / Firestore" — [reddit r/googlecloud](https://www.reddit.com/r/googlecloud/comments/167ieg8/possible_to_apply_iam_permissions_to_cloud/).
- **IAM Deny 정책**: allow가 부여하더라도 **deny가 우선**하는 하드 경계; 리소스당 최대 500개 deny 정책, condition 지정 가능(condition이 true이거나 **평가 불가**면 적용) — [Deny policies](https://docs.cloud.google.com/iam/docs/deny-overview); [Deny access](https://docs.cloud.google.com/iam/docs/deny-access). → 앱 SA에 `datastore.entities.delete`/`update`를 deny하면 롤에 있어도 차단.
- **GCS IAM Conditions는 resource name prefix를 지원** → 버킷 내 특정 prefix로 `storage.objects.create` 등 제한 가능 — [IAM Conditions overview](https://docs.cloud.google.com/iam/docs/conditions-overview); [GCS object prefix 조건 예](https://stackoverflow.com/questions/62711733/cloud-iam-conditions-for-gcs-objects); [dev.to: Granular access control to GCS objects using IAM Conditions](https://dev.to/meteopress/granular-access-control-to-google-cloud-storage-objects-using-iam-conditions-3m7n).
- **GCS WORM**: Bucket Lock(Cf. 핵심 질문 2) + Object Retention Lock/Object Hold — [Object holds](https://docs.cloud.google.com/storage/docs/object-holds). 신규 기본 버킷 프로비저닝에 Blaze 필요(프로젝트 메모리 reference와 일치).
- **Cloud Audit Logs**: **Admin Activity 로그는 무료·400일 보존·비활성화/삭제 불가**("always enabled, always free, retained for 400 days", `_Required` 버킷은 400일 보존·삭제 불가); **Data Access 로그는 기본 30일, 표준 $0.50/GiB 과금** — [Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit); [Annielytics 요약](https://www.annielytics.com/tools/cloud-kingdom/compliance-citadel/chronicle/google/); [C3X audit log cost](https://c3x.dev/blog/audit-log-cost-management/).
- 서버 클라이언트를 통한 Firestore 접근은 규칙을 우회하므로, 규칙은 "모바일/웹 클라이언트"용; 규칙 자체는 `service-<num>@firebase-rules.iam.gserviceaccount.com` + `roles/firebaserules.system` 바인딩에 의존 — [Firestore security/iam](https://docs.cloud.google.com/firestore/native/docs/security/iam).

### Inferences
- **가능**: 앱과 **다른** 서비스계정에 커스텀 롤 `datastore.entities.create`(+`get`/`list`)만 부여하고 `delete`/`update`는 주지 않음 → 그 자격증명은 **생성만** 가능(문서 존재 시 create 실패). 여기에 IAM Deny로 `datastore.entities.delete`/`update`를 앱 SA에 걸면 이중 방어. 단, **이 자격증명도 "아카이브를 만들지 않는" 누락은 못 막는다**(생성하지 않으면 아무 기록도 안 남음).
- **불가(무료)**: Firestore에서 컬렉션/문서 단위 최소권한, WORM은 불가. Cloud Storage로 가면 prefix 조건 + Bucket Lock으로 "삭제 불가"는 되지만 **Blaze 필요 → 무료 아님**. → 이 프로젝트의 "Firestore-only, free" 전제에서 삭제/수정 방지는 별도 SA+Deny로 달성 가능하나 **완전 WORM은 유료**.
- **강력한 독립 증인 후보**: **Cloud Firestore Data Access Audit Logs**를 켜면 모든 문서 쓰기/삭제가 Google 보관 로그에 남아 앱이 편집 불가. 그러나 **$0.50/GiB 과금 + 기본 30일** → 무료 요구와 충돌. Admin Activity(무료 400일)는 **문서 데이터 연산을 담지 않아** 탈퇴 아카이브 쓰기/삭제를 못 잡음(설정/구성 변경만).

### Gaps
- Firestore에 `datastore.entities.create`만 가진 롤이 **컬렉션 단위**로 제한 불가함을 공식 문서 문장으로 확정하지 못함(권한 표가 프로젝트 범위만 나열) → 강한 정황이나 1차 명시 문구 UNKNOWN.
- Firestore IAM 조건이 **컬렉션/문서 이름** 속성을 지원하는지 최신 여부 → UNKNOWN(커뮤니티는 "불가").
- Cloud Storage Data Access Audit Logs의 정확한 과금/보존과 Firestore와의 차이 → 부분 확인.
- "Spark(무료) 프로젝트에서 Cloud Storage 버킷 생성 가능 여부" → UNKNOWN(프로젝트 메모리는 Firebase 기본 버킷에 대해 Blaze 필요로 기록).

## 핵심 질문 5 — 단일 관리자가 실제로 돌릴 수 있는 주기적 체크포인트 설계

### Takeaway
GitHub Actions cron + **관리자 오프라인 키로 서명한 체크포인트 커밋**(카운트 + Merkle/hash head) + **head 퇴행 시 하드 실패** + **체커 liveness heartbeat**가 단일 운영자의 현실적 최소 구성이다. 단, 이는 "**로그에 있는 것의 퇴행**"을 잡을 뿐, **애초에 제출 안 된 누락**은 독립 증인(클라이언트) 없이는 못 잡는다. 그리고 체크포인트가 **앱과 같은 자격증명**으로 아카이브를 읽으면 독립성 0.

### Cited Findings
- CT/투명 로그 실사례의 monitor 패턴: 로그에 포함된 항목을 암호검증하고 알림 — [certificate.transparency.dev/howctworks](https://certificate.transparency.dev/howctworks/). Sigsum monitor는 로그에서 서명 체크섬을 받아 특정 키 사용을 탐지 — [Sigsum Getting started](https://www.sigsum.org/getting-started/).
- GitHub Actions cron 실무: 스케줄 워크플로 모니터링은 **마지막 단계가 heartbeat URL을 핑하고, 핑이 도착하지 않으면 경보**하는 방식 — [Hyperping: How to Monitor GitHub Actions Scheduled Workflows](https://hyperping.com/blog/how-to-monitor-github-actions-scheduled-workflows).
- **스케줄 워크플로는 비활성 저장소에서 정지**한다: 저장소에 **60일간 커밋이 없으면 GitHub가 스케줄 워크플로를 비활성화**하고 알림을 보냄 — [dev.to: Monitoring GitHub Actions scheduled workflows, a practical guide](https://dev.to/krissv/monitoring-github-actions-scheduled-workflows-a-practical-guide-31h7). → 체크포인트 자체가 주기적 커밋을 만들어 이 정지를 완화(단, 커밋이 곧 "살아 있음" 신호가 됨).
- `workflow_dispatch`를 함께 두면 수동 테스트 가능; 스킵된 실행은 Actions 로그의 "Scheduled events"에서 사유 확인 — [oneuptime cron 가이드](https://oneuptime.com/blog/post/2025-12-20-scheduled-workflows-cron-github-actions/view); [GitHub community discussion #185355](https://github.com/orgs/community/discussions/185355).
- 서명된 체크포인트/키 pinning에 해당하는 개념: CT 로그의 **STH 서명 + 로그 공개키**(신뢰 앵커 = 공개키) — [RFC 6962 §3.5](https://www.rfc-editor.org/info/rfc6962/); sumdb 클라이언트가 latest tree hash를 로컬 캐시해 불일치 시 loud fail — [Go sumdb proposal](https://go.googlesource.com/proposal/+/master/design/25530-sumdb.md).
- CloudTrail의 "빈 digest도 배달"과 "검증 끄면 1시간 뒤 체인 단절", `LatestDigestDeliveryError` 확인 패턴은 **체커 liveness/공백 탐지의 실제 구현 예** — [digest file structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html).

### Inferences
- **구체 설계(이 프로젝트 적용안)**:
  1. 앱은 모든 탈퇴 시도마다 (성공/실패 무관) **단조 증가 시퀀스 번호 + 항목 해시**를 원장 Firestore 문서에 append(덮어쓰기 금지, append-only 문서 ID 규칙).
  2. GitHub Actions cron이 **앱과 다른 읽기전용 자격증명**으로 원장을 조회 → (count, Merkle root/해시체인 head) 계산.
  3. **관리자 오프라인 개인키**로 그 체크포인트를 서명해 `checkpoints/` 에 커밋(또는 릴리스 asset). 이전 체크포인트 head를 **prefix로 검증**; 아니면 워크플로 exit≠0 + 이슈 생성 + 관리자 알림.
  4. 마지막으로 **heartbeat URL 핑**으로 "체커가 안 돌아도" 경보.
- **한계(정직)**: 위 1~4는 앱이 원장에 **아무것도 안 쓰면** 여전히 못 잡는다(카운트가 안 늘어도 "정상"으로 보임). 앱이 실패를 판정하니, 실패 자체를 안 만들면 끝. → **클라이언트 증인**이 반드시 병행돼야 함: 브라우저가 탈퇴 시도 시 로컬에 nonce/시각을 남기고, 이후 **앱 밖 채널**(예: 사용자가 직접 여는 이슈/관리자 CLI 입력, 또는 앱이 못 위조하는 서명된 영수증)로 "이 시도가 있었다"를 전달. 그러면 관리자/체커의 기대치 카운터가 생겨 누락이 드러난다.
- **파일럿 배치 간섭 방지**: GitHub Actions가 앱과 같은 SA를 쓰면 독립성이 사라진다 → **읽기전용 별도 SA** 또는 관리자 로컬 실행. 서명 키는 절대 Actions secret이 아니라 **오프라인 관리자 키**로(저장소 침해 시에도 위조 불가).
- **무료 제약**: GitHub Actions 무료 분(공개 무제한/비공개 월 한도)으로 충분. Firestore 읽기 5만/일 무료 한도 내에서 주기 조회 가능(항목 수에 따라 페이지네이션 필요).

### Gaps
- tlog-witness/Trillian witness를 소규모로 굴리는 구체 오픈소스 런북 → 이번 조사에서 1차 문서 미확보(UNKNOWN).
- GitHub Actions cron의 정확한 스케줄 지연/누락률과 무료 분 한도 최신 수치 → [Actions limits 문서] 미확인(UNKNOWN).
- "서명된 영수증"을 무료로 관리자에게 전달하는 채널(이슈 첨부 API 부재 제약)의 실현성 → 프로젝트 제약상 제한적(UNKNOWN).

## 종합 판정 — 완전히 침해된 앱(자기 자격증명 보유) 상대

### Takeaway
"삭제/수정"은 방어(IAM Deny, WORM, create-only)로 **예방** 가능하지만, "**애초에 안 씀**"이라는 누락은 **어떤 것도 예방하지 못하며, 오직 독립 증인/사전 커밋먼트가 있을 때만 탐지**된다.

### Cited Findings (판정 근거 재인용)
- admin SDK 규칙 우회 → 앱 자격증명은 규칙으로 못 막음 — [Firebase rules get-started](https://firebase.google.com/docs/firestore/security/get-started).
- append-only 로그의 누락/대체는 **monitor가 내용을 이미 가져간 경우에만** 가시적 — [Trillian](https://google.github.io/trillian/docs/TransparentLogging.html).
- IAM Deny는 allow보다 우선하는 하드 경계 — [Deny policies](https://docs.cloud.google.com/iam/docs/deny-overview).
- compliance-mode Object Lock은 root도 삭제 불가 — [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).
- CloudTrail empty digest = "그 시간에 활동 없음"의 음성 증거 — [digest structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html).

| Sigsum 공개 로그+증인+monitor | **탐지**(커밋먼트 사용 이력) / **무료 가능** | 체크섬만 로깅해 누락 위험·프라이버시 회피 가능 |

### Inferences
- 이 시스템의 **최소 실효 조합**: (1) 앱 SA와 다른 **create-only SA + IAM Deny(delete/update)** 로 삭제/덮어쓰기 봉인, (2) **클라이언트 증인**(로컬 탈퇴 시도 원장 + 앱 밖 전달), (3) **관리자 오프라인 서명 체크포인트**(GitHub Actions cron, head 퇴행 시 하드 실패, heartbeat). 넷 다 "무료"로 조합 가능. 단 (2)의 "앱 밖 전달"이 이 스택에서 가장 취약한 고리.
- 어떤 단일 메커니즘도 "완전 침해된 앱"에 대해 **누락을 예방**하지 못한다(Trillian 각주 3이 근거). 보고서는 "탐지"와 "예방"을 엄격히 분리해 서술해야 한다.

### Gaps
- 위 조합을 실제 Render+Firestore 무료 환경에서 **관측 반증**한 사례 없음(설계 추론). 실계정 왕복 미관측(프로젝트 메모리와 일치).
- "클라이언트 증인 → 앱 밖 채널"을 무료·프라이버시 안전하게 구현하는 구체 스킴(예: 서명 영수증 + 공개 로그)의 실증 → UNKNOWN.
- 정량 벤치마크(누락 1건 탐지에 필요한 조회 수/지연, Firestore 무료 한도 내 체크포인트 주기) → UNKNOWN.
